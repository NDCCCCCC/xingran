# 防「误下线」流程协议（FIX-PROTOCOL）

> 适用范围：本仓所有「下线 / 删除 / 判定废弃」用户可见功能（按钮、菜单、API 端点、
> 路由注册、前端调用点）的改动。
>
> 起因：PR #85 曾把周期工单 4 个按钮 / API（`enable` / `disable` /
> `generate` / `logs`）判为「废弃」并删除；1.5 小时后 PR #86 发现 service 层
> `PeriodicService` 实现完整、只是 HTTP 通路在路由重构（cd306b359）中丢失，
> 又恢复注册。本次事故说明「凭注释 / 凭路由缺失判废弃」会造成真实功能被误删。
>
> 本文件是**流程与检查项文档**，不改任何门禁脚本。URL ↔ 路由交叉校验门禁
> （`scripts/check-frontend-api-urls.mjs`）已存在，本条只补「下线前」的
> 人工/代码证据检查项，与之互补。

---

## 一、三条硬性原则（缺一不可）

1. **下线用户可见功能前必须先查 service 层实现与历史路由。**
   不得仅凭「前端没有按钮」「路由表里没有这条」「注释写了 deprecated」
   就判定废弃。必须确认 service 层是否仍有完整实现、git 历史里该路由 /
   按钮是否曾经存在。
2. **必须由代码证据而非注释判定「废弃」。**
   注释、`// TODO`、文档描述都是**线索**，不是废弃依据。废弃判定只能来自
   可编译 / 可调用的代码证据：service 方法是否被任何 handler / 定时任务 /
   其它包引用、前端是否有对应调用点、数据库表 / 迁移是否仍在使用。
3. **必须先与前端调用点交叉验证。**
   后端删除任何 API 前，必须检索前端 `src/` 下对该 URL 的调用
   （含 `lib/api.ts`、`lib/opsApi.ts`、`*Api.ts`、组件内 `post/get` 调用），
   确认无引用或已先下线前端调用点，且 URL ↔ 路由门禁通过。

---

## 二、下线前检查清单（逐项打勾，CI/PR 模板引用本节）

> **硬检查项 ①「先查 service 层」**：在 `internal/services/<module>/` 下检索
> 该功能对应的 service 方法 / 接口定义。若方法体存在且逻辑完整 → **禁止下线**，
> 应优先修复 HTTP 通路（路由注册 / handler 接线），而不是删功能。
> 命令示例：
> ```bash
> grep -rn "func .*EnablePeriodic\|func .*DisablePeriodic\|func .*GeneratePeriodic" internal/services/workorder/
> ```
> 本次事故中 4 个动作的 service 实现一直可用，误判的根因正是跳过了这一步。

- [ ] **① 先查 service 层实现**：目标功能在 `internal/services/` 是否有对应方法、
      是否完整、是否被定时任务 / 其它包引用。（见上方硬检查项）
- [ ] **② 查历史路由 / 历史提交**：`git log -S"<路由字面量>" -- internal/api/`、
      `git log --oneline -- <router 文件>`，确认该端点是否曾注册、何时消失、
      消失原因是否为「重构漏接」而非「功能废弃」。
- [ ] **③ 代码证据判定废弃**：列出 service 方法引用点、handler 绑定、表 / 迁移、
      菜单权限码播种。仅当**全部**无引用且前端无调用，才可判废弃；
      注释中的 `deprecated` / `废弃` 字样不计入证据。
- [ ] **④ 前端调用点交叉验证**：检索前端对该 URL 的调用
      （`grep -rn "<url>" xingran-react-frontend/src/`），确认按钮 / 页面 /
      API 封装的引用情况。
- [ ] **⑤ URL ↔ 路由门禁**：运行 `node scripts/check-frontend-api-urls.mjs`，
      确认删除后无「前端仍调用、后端已无路由」的不匹配。
      （该门禁已存在，本文件不修改它。）
- [ ] **⑥ 权限 / 菜单播种联动**：若端点带权限码，确认下线时同步处理
      `sys_menu` 权限播种与前端门控，避免留下孤儿权限点或门控失效。

## 三、判定表（快速对照）

| 观察到的现象 | 能否直接判「废弃」 | 正确处置 |
| --- | --- | --- |
| 路由表里找不到该端点 | ❌ 不能 | 先查 service 层与历史路由；多半是重构漏接，补注册 |
| 注释写了 `deprecated` / `废弃` | ❌ 不能 | 注释只是线索，按第二节逐项取代码证据 |
| 前端某个页面没有该按钮 | ❌ 不能 | 全局检索前端调用点（可能在其它页面 / API 封装里） |
| service 方法存在且逻辑完整 | ❌ 禁止下线 | 修复 HTTP 通路，参照 PR #86 的恢复做法 |
| service 方法存在但全仓无任何引用，且前端无调用，且门禁通过 | ✅ 可判废弃 | 走完整下线流程，同步清权限播种与前端门控 |
| service 方法本身已被删除、表已迁移废弃、前端无调用 | ✅ 可判废弃 | 走完整下线流程 |

  「service 层仍有实现却被误删」场景。
