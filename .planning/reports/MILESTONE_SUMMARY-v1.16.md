## 1. Project Overview

**XingRan-Next** is a Go backend + React frontend enterprise IT operations management system.
The v1.16 milestone is a dedicated **technical-debt cleanup cycle** — not a feature
shipment. It closed the long tail of deferred debug sessions, validated the regression
locks that protect downstream milestones, and shipped a 100%-passes validator pass.

### Headline outcomes (per PROJECT.md)

- **22 backend deferred debug sessions** closed via Phase 40 cohort A.
- **29 frontend deferred debug sessions** closed via Phase 41 cohort B.
- **6 audit-file规范化** — audit report files brought to a uniform structure so that
  later milestones can grep them programmatically.
- **`operlog` regression lock validated** — 165/165 validator cases pass; this lock protects
  audit behaviour for v1.17+, v1.18, v1.19 (and is the reason those milestones could
  confidently say "zero regressions to audit").

### Why v1.16 existed

By late May 2026 the project had accumulated:

- 18+ **open debug sessions** marked `root_cause_found` but not yet closed-out,
- Audit-trail files (`.planning/debug/*.md`) written in three inconsistent formats,
- Several Phase-level TODO items exposed by **Phase 31 / Phase 39 follow-up reviews**

without a dedicated milestone. v1.16 was created as a *cleanup* milestone instead of
routing each item into a feature milestone (which would dilute scope).

## 2. Architecture & Technical Decisions

Because v1.16 was cleanup-focused, the typical "feature architecture" section is replaced
by "patterns established" — this milestone's main architectural contribution is the
**technical-debt discipline pattern**.

### Established / Confirmed patterns

- **Pre-existing test failure baseline.** Every subsequent phase uses a baseline-run on
  the pre-phase commit to prove any new failure is not their fault. v1.16 codified this
  into a routine practice (per RETROSPECTIVE.md "Top Lessons" row 1).
- **Audit-file规范化 schema.** All `.planning/debug/*.md` files now follow a standard
  frontmatter + body structure. v1.17+ milestones can grep them for "deferred-to-next-milestone"
  tokens programmatically — driving later automation like `/gsd-audit-open`.
- **Regression lock is load-bearing.** The 165-case validator test set generated by v1.16
  became the test gate every future PR must pass. **Three future milestones (v1.17, v1.18,
  v1.19) explicitly credit this lock as the reason audit behavior did not regress.**

### Active invariants after v1.16 (carried into v1.17+)

- `operlog.OperType` value-set is stable (locked by `internal/utils/operlog/regression_test.go`).
- Sensitive-keyword masking has a known, documented camelCase/snake_case enumeration.
- Audit files have a parseable frontmatter (this milestone's main artefact).

## 7. Getting Started

### Why a new contributor should care about v1.16

Even if you're working on v1.20 (next cycle) and never touch v1.16 code directly, v1.16 is
load-bearing because:

1. **`operlog` regression lock** — if your code changes the audit library behaviour, this
   test set will fail and reject your PR. Check the lock before touching `operlog`.
2. **Audit-file frontmatter convention** — when writing a new `.planning/debug/*.md`
   session file, follow the v1.16 lock format so it stays grep-able.
3. **Pre-existing test failure baseline** — when running `go test ./...` you may see
   known failures (login_encryption_test.go, pkg/errors, services/operations) that
   pre-date your change. v1.16 codified this practice; do not "fix" them as a side
   effect of your work (per CLAUDE.md Scope Constrainment rule).

### Entry points to study v1.16 work

| Activity | Where |
|----------|-------|
| See which sessions were closed | `git log --since="2026-06-22" --until="2026-06-27" --author=... -- .planning/debug/` (look for `closes #<n>` or `tech-debt:` style commits) |
| Audit-file frontmatter convention | any recent `.planning/debug/*.md` — v1.16 reset all of them to consistent format |
| Validator pass-rate | `go test ./internal/utils/operlog/` + subsequent bulk-test scripts in `.scripts/` if any |
| Pre-existing failure baseline | `.planning/deferred-items.md` if it exists (typically maintained post-v1.16) |

### Key invariants established by v1.16 (Do Not Break)

- **Don't add new audit formats** — all `.planning/debug/*.md` files follow v1.16's
  standardized frontmatter (validators downstream depend on this).
- **165/165 is the validator floor** — any new test added must keep the suite at 100%
  pass; do not silently skip validator cases.
