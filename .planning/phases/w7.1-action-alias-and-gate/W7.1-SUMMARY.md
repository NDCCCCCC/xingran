## 1. 缺陷 A —— 动作类型别名（P0）

### 1.1 根因（沿用任务书铁证，不重新考古）

生产库 6 个任务（全部 2026-03-10 创建的测试数据）第一步是 `type="goto"`；worker 的
`ActionType` 常量表只有 `"navigate"`（`rpa-worker/internal/types/types.go:70`）。
`mapToAction` 原样转换（`engine.go:1019-1021`）→ `executeAction` switch 无 `goto`
case（`engine.go:459-461`）→ `default` 立即返回。

**铁证**：生产日志 `liveview attach(00:12:00.009)` → `gate waiting(00:12:00.094)`，
间隔 85ms —— 真实导航失败不可能这么快，动作压根没执行。

### 1.2 别名表取值（先取证再定表）

新增只读普查工具 `scripts/ops/rpa_action_type_census`，对生产库（10.62.10.34）实测：

```
=== 19 个任务，共 12 种 type ===
  OK     screenshot 39    OK  navigate 13    OK  wait 11    OK  fill 9
  OK     click 6         OK  condition 6    ALIAS goto 6   OK  loop 6
  OK     script 4        OK  extract 3      OK  scroll 3   OK  hover 1
ALIAS_SET=goto
```

非规范写法**只有 `goto`（6 步）**；前端 `RPA_ACTION_TYPES`（`src/types/rpa.ts`）只有规范写法。
`url` 作为历史惯用写法也纳入（后端 `extractURLFromScript` / `convertToWorkerAction`
都把 URL 放在 `value`，说明存量确有「URL 就是这一步主角」的形状），并按大小写不敏感覆盖
`goto / goTo / GoTo / GOTO`。

### 1.3 修复

**唯一事实来源在 `types` 包**（不是 executor）：

```go
// rpa-worker/internal/types/types.go
var ActionTypeAliases = map[string]ActionType{"goto": ActionNavigate, "url": ActionNavigate}
func NormalizeAction(a *Action) (aliasRaw string)   // 唯一入口
```

- `mapToAction`（嵌套动作路径）与 `TaskMessage.UnmarshalJSON`（**顶层 script 路径**）都调用它；
  归一化只在「Action.Type 赋值处」完成后就不再分散判断。
- 命中别名打 WARN `normalized action type goto -> navigate`（executor 侧统一打，含 raw_type /
  normalized_type / action_id），便于继续发现历史数据。
- 未知类型 `frobnicate` **不被改写**，继续走 `default` → 可读错误（不静默吞掉）。

**数据根治**：`internal/core/db/migrations/migration_261_rpa_action_type_alias.go`
- 逐任务解析 JSON，只在命中别名时 UPDATE，**其它字段一字不改**（selector/value/params/timeout/retry 全保留）。
- 双方言幂等：PG（`script::text` ← `CAST(? AS jsonb)`，`id = CAST(? AS uuid)`）/ SQLite（TEXT 直赋）分支；
  二次执行零 UPDATE（实测「扫描 19 个任务，改写 0 个」）。
- 已注册 4 处：`database.go` PG 分支 + sqlite 分支、`migrations/registry.go`、`scripts/dbprovision/main.go`
  （后者覆盖 `SKIP_AUTOMIGRATE=true` 的部署形态 —— 那条分支不会跑 261，而 261 必须在任何 goto 任务重跑前生效）。
- 一次性执行工具 `scripts/ops/rpa_action_alias_migrate`（调用**同一个**迁移函数，避免双实现漂移）。

**生产库已执行（2026-11-27 14:32）**：
```
迁移前: ALIAS goto 6
迁移后: OK navigate 19（无 goto/url 残留）
MIGRATION_261_OK
再跑一次: 扫描 19 个任务，改写 0 个（幂等）
```

### 1.4 真跑逐层挖出的另外六层（同一族缺陷，缺一层就仍然跑不通）

第一次只加别名表后真跑，6 个任务全部 failed，报错变体各不相同。逐层定位（每层都有真跑证据）：

| # | 层 | 现象（真跑实测） | 修法 |
|---|---|---|---|
| 1 | 顶层 script 不走 `mapToAction` | `TaskMessage.Script` 是强类型 `[]Action`，`json.Unmarshal` 直接按字段赋值 → `goto` 原样落进 `Type`。**alias 表加了等于没加** | `TaskMessage.UnmarshalJSON` 里逐动作调 `NormalizeAction`（`types` 包，两条路径共用） |
| 2 | URL 键位不匹配 | 6 个任务 URL 都在 `value`，`params` 只有 `waitUntil`；navigate case 读 `params["url"]` → 报 `missing url parameter` | `NormalizeAction` 提升 `value → params["url"]`（不覆盖已有值）；普查实证键位分布 `params.url=6 / value=7` |
| 3 | 参数键名历史写法 | `script` 用 `params.code`、extract 用 `extractType/outputVariable`、scroll 用 `distance`、loop 用 `itemName`、wait 用 `delay` | `paramKeyAliases` 按动作类型改名（只改名不改值、目标键已存在不覆盖） |
| 4 | condition 取值是枚举不是 JS | 两个任务写 `condition="exists"` + selector → `ReferenceError: exists is not defined` | 保守白名单 `elementStateConditions`（exists/visible/hidden/checked…）走元素状态检查，其余仍当 JS 表达式；分支再兼认 `trueActions/falseActions` |
| 5 | extract 缺 multiple 语义 | `extractType="multiple"` + fields[] → 「提取方式 multiple 不被支持」（而这正是那两个任务的目的） | 新增 `executeExtractMultiple`（容器内按 fields 逐条取，去退化成「只取第一条」的假成功） |
| 6 | 元素句柄继承了探测 ctx | 阶梯用 500ms `probe` 定位，命中后元素**继承**那个已过期 deadline → `el.Click/Input` 立刻 `context deadline exceeded`；且 7 级共用同一个 probe，第一级没命中后面全报 deadline | 每级各自一份 500ms 预算；命中后 `el.Context(context.Background()).Timeout(...)` 重绑 |
| 7 | rod 交互层在遮挡页卡死 | 同一按钮：`Eval click` 3ms 生效，`PageManager.Click` 耗满 30s 超时（百度结果页浮层） | 鼠标/键盘路径**失败时**退化到页面内触发（左键单击/输入），成功路径语义完全不变，必留 WARN；鼠标预算收紧到 5s，避免白等 30s |

第 6、7 层是**历史上一路没暴露**的：goto 任务在第一步（类型不支持）就失败，step2
的 fill/click 从来没执行过。别名修好后它们立刻成为新的失败点 —— 这也解释了「为什么
前两轮都只修了表象」。

## 2. 缺陷 B —— force 语义区分「配置错误」与「运行时失败」（P0）

### 2.1 根因（任务书铁证）

`unsupported action type` 属**不可重试的配置错误**，但该动作 `retry=2 > 0` → 进入重试分支
（`engine.go:219`）→ 先调 `liveActionGate(force=true)` → copilot 下 `needWait` 恒 true
（`takeover.go:344-347`）→ 永久阻塞。

生产铁证：每个 11 步任务都在 step 1 打出
`liveview gate waiting {"mode":"copilot","force":true}`，随后 10 分钟无任何动作，
最终 `context deadline exceeded`；页面停在 `about:blank`，screencast 一帧不发
（后端 30 分钟 `/liveview/frame` 请求数 = 0）。

### 2.2 修复

- `types.go` 新增 `NonRetryableError` / `ErrNonRetryable` / `IsNonRetryable`（**类型判定而非字符串匹配**：
  文案会漂移，`errors.As` 不会）。
- `engine.go` 重试分支**先判可重试性**：不可重试 → 打 WARN
  `non-retryable configuration error, skipping retry and human gate` + 刷新叠加层
  状态为 failed（用户在看画面时能读到「为什么停」）+ 直接 `createErrorResult`（fail-fast），
  **不 gate、不空转重试**。
- 全部参数/选择器类校验点改为 `NewNonRetryableError`（约 30 处）：缺 selector / 缺 url /
  缺 value / 缺 script / 未知动作类型 / 未知 extract 类型 / 未知滚动方向 / 未知断言类型等，
  文案统一改成一般员工能懂的中文（不出现 `ActionType` / `switch` / `enum`）。
- `takeover.go` 的 `case force:` **保留**，并加契约注释：force 只应来自可重试的运行时失败。

### 2.3 用户视角验收（缺陷 B，前后对比）

**对照 A（修复前的行为，闸门本体仍保留）** —— `TestGate_ForceCopilotBlocksUntilTimeout`：

```
对照 A：阻塞 3.001s 后以 context deadline exceeded 结束（生产对应 10 分钟 task_timeout）
对照 A 日志: INFO liveview gate waiting execution_id=w71-gate-force mode=copilot takeover_by= force=true
```

即：只要仍把配置错误送进这个闸门，结果必然是「卡到超时」，与生产日志逐字对应。

**对照 B（修复后）** —— `TestEngine_NonRetryableError_FailFast`（真 Chromium + 真 Hub）：

```
fail-fast 证据: 耗时=49.0579ms status=failed step=1/1
原因=该步骤的类型「frobnicate」不被支持，请在任务脚本里修正这一步
```

断言三条：① 日志无 `liveview gate waiting`（不进闸门）；② 日志无 `action failed, retrying`
（不空转）；③ 49ms 内 failed 且文案可读。

**「卡 10 分钟 → 立刻 failed」的量化对比**：生产形态 600s（`task_timeout` 10m）/
对照 A 3.001s（受测试 ctx 预算约束，同一形态）→ 修复后 **49ms**，约 **6000 倍**。

**反向保护（不能修过头）** —— `TestEngine_RetryableError_StillGates`：

```

```

元素不存在（可重试）→ 仍按原设计在 copilot 下停下等人 Continue，放行后真的进入重试
（日志有 `action failed, retrying`），最终 failed 且**没有**被误标成配置错误；
`TestGate_ForceAutoDoesNotBlock` 另锁「auto 模式不被 force 打断」。

## 3. 缺陷 C —— 空页面无帧要显式告知（P1）

### 3.1 根因

页面停在 `about:blank` 或空 DOM 时 Chrome **不产 screencast 帧**，前端只能无限显示
「等待画面…」。用户（一般员工）无法判断是「还没开始」还是「永远不会有」。

### 3.2 修复（三层，阈值统一 5s）

1. **worker**（`browser/screencast.go`）：`StartScreencast` 成功后起一个并行看门狗，
   `ZeroFrameWarnAfter`（默认 5s）内仍 0 帧 → 探查现场（`Page URL` + DOM 是否有可渲染内容）
   → 写 `ZeroFrameReport{detected, waitMs, pageUrl, domEmpty, framesSeen}` + WARN：
   `liveview 开流后无画面帧（页面可能停在空白页或无法渲染） waited=5s frames=0 page_url=about:blank dom_empty=true`。
   语义边界：**不自动补救**（不关流、不自动导航）—— 画面是事实，不靠猜。
2. **后端**（`services/rpa/liveview_hub.go`）：`Stats()` 增 `emptyPageHint` / `emptyPageWaitingMs`，
   判据 = 「已开流超过 `emptyPageHintAfter`(5s) 且 `frames == 0`」；janitor 在首次越线时
   向 `rpa_liveview_state` 推一条带 `emptyPageHint: true` 的消息（去重，避免每 2s 一条噪声）。
3. **前端**：
   - `types.ts` / `liveFrameParser.ts` 新增 `parseEmptyPageHint`（与 context 分开解析，避免被
     「整体替换 context」的清空语义带走）；
   - `liveFrameBus.ts` 新增 `onLiveEmptyPage` 订阅（同一 WS 信封先分情境再分提示）；
   - `LiveHud.tsx`：`emptyPage` 为真时把「等待画面…」换成
     **「当前页面暂无画面（可能停在空白页或正在加载）」** 并显示 **「刷新状态」** 按钮
     （`pointerEvents` 显式打开，否则 HUD 整体穿透会让按钮点不动）；
   - `index.tsx`：三条置真路径（本地 5s 计时 / 后端推送 / 刷新 state 读 stats）+ 收帧即清，
     「刷新状态」= 重新拉 state + 幂等重发 watch。

### 3.3 用户视角验收（缺陷 C）

**worker 真 Chromium**（`TestScreencastZeroFrame_BlankPage_Detected`）：

```
零帧判定现场: url=about:blank domEmpty=true framesSeen=0 waitMs=2000
WARN 原文: liveview 开流后无画面帧（页面可能停在空白页或无法渲染） waited=2s frames=0 page_url=about:blank dom_empty=true
```

**反向用例**（`TestScreencastZeroFrame_ContentPage_NoHint`）：有内容且带动画的页面
`有内容页面正常出帧 3 帧，未触发空页面判定` —— 不误报。

**后端契约**（`internal/api/v1/rpa/liveview_empty_page_w71_test.go`，真 hub + 真库）：
`0 帧越线 → emptyPageHint=true + 等待时长` / `收到帧 → 永不提示` / `阈值内不提前误报` / `阈值 = 5s`。

**前端渲染断言**（`__tests__/liveEmptyPage.w71.test.tsx`，8 例全绿）：
- 已推流 0 帧超时 → 显示「当前页面暂无画面（可能停在空白页或正在加载）」，**且不再出现「等待画面…」**；
- 「刷新状态」按钮存在、点一下真的调用回调；
- 有画面帧 → 无提示无按钮；未越线 → 仍是「等待画面…」；
- 文案面向一般员工：不含 `screencast / CDP / frame / DevTools`，且必须给出「空白页 / 加载」两种可能原因。

## 7. 遗留

1. **6 个 goto 任务的「完整执行」仍会中途失败，但原因在目标站改版，不在修复本身**
   - `多字段表单填写测试`：目标 `github/signup` 当前页面里**没有任何 `input[name=email]`**
     （实测探针 `email:false, inputs:[]`，表单在 iframe 内），且该 IP 被 github 判自动化
     （截图显示 `Access is temporarily restricted`）。
   - `循环批量搜索测试` / `综合端到端` / `页面导航与滚动`：百度结果页结构变化 +
     连续「搜索→再搜索」的时序，属外部因素。
   - 因此完整执行只作为**记录**（`TestW71_RealRun_SixGotoTasks_Full`，`W71_FULL=1` 启用），
     硬判据只要求「不再出现修复前的三层错误文案」。这一层如实记为**未达成**，
     不写成 PASS。
2. **rod 交互层兜底（第 7 层）是保守兜底而非根治**：真实鼠标/键盘路径在被浮层遮挡时
   会失败，现退化为页面内触发（`el.click()` / 设值 + 派发 input/change）。若要真正根治，
   需要「先滚入视口 + 关闭遮挡层」的策略，属下一轮 UI 稳定性议题。
3. **`WebGL/canvas` 类站点或持续动画页面可能让「零帧判定」阈值偏严**：5s 是按
   百度/github 这类页面实测定的；对首屏很慢的站点可能出现「先提示暂无画面、随后又出帧」。
   当前收帧即清提示，可接受；如反馈频繁可改为「提醒 + 继续等待」的双态文案。
4. **迁移只治已知别名（goto/url）**：新增历史写法需要「先跑 `rpa_action_type_census`
   再扩表」。两侧（`types.ActionTypeAliases` 与 `migrations.rpaActionTypeAliasCanonical`）
   必须同时改 —— 已由 `TestMigrate261_AliasSetMatchesWorker` 锁住集合大小与映射。
5. **未做**：生产后端/worker 的重新部署与真机浏览器复核。本轮所有验收都在本地真 Chromium
   + 真 PG/Redis 上完成，部署后需再走一次 §1.5 的 6 任务首步（命令已固化，可原样复用）。
