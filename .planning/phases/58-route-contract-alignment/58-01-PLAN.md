<objective>
对齐前端 API Key 管理页与后端的两个契约断裂，让 API Key 管理 CRUD 真实生效：

1. **CONTRACT-01（路由方法对齐，D-01）**: 前端 `apikey.ts` 的 getAPIKey/updateAPIKey/deleteAPIKey 当前用 GET/PUT/DELETE，后端 `apikey_router.go` 全 POST → 三个操作 404。本 plan 把前端三函数改 POST 对齐后端既有 Router Pattern，后端零改动。
2. **CONTRACT-02（字段命名对齐，D-02/D-03/D-04/D-05）**: 后端 camelCase（`ipWhitelist`/`inheritPerms`/`isActive`/`expiresAt`）vs 前端 snake_case，且 `api.ts` 拦截器无 snake↔camel 转换 → Create/Update 复合字段被 `encoding/json` 静默取零值丢弃（实证复现，非假设），List/详情/编辑表单复合字段显示 undefined。本 plan 把前端三接口 + `index.tsx` 字段访问全改 camelCase 对齐后端 json tag。

Purpose: 不只是消除 3 个 404，还要让 IP 白名单、继承权限、过期时间等安全控制字段真正写入 DB（当前是比 404 更严重的静默数据损坏——T-58-01）。
Output: 3 个前端文件修改（`apikey.ts` / `types/apikey.ts` / `index.tsx`），后端零改动。
</objective>
