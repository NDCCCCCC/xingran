# Plan 01 — W0：migration 226 骨架 + 测试基建 + 脚本 F 块解析（tracer）

## Context

### 本 phase 的真实缺口（Lead 最初的假设已被研究推翻）

研究结论（`87-RESEARCH.md` §C11 / §C12 / §B7）：

1. **前端零改造**。`internal/services/system/menu_service.go:181-190` 的 `GetTree` 是 `Find(&menus)`，**无 `menu_type` / `visible` / `status` 过滤**；前端 `src/pages/system/role/hooks/useRoleData.ts:103-111` 的 `processTreeData` 也不按 `menuType` 过滤 ⇒ **F 型按钮在角色页本来就可见可勾选**。真正的缺口是**数据**：`sys_menu` 里那 72 条 F 行根本不存在。
2. **播种清单 = 78 = 65（立即播）+ 7（挂起，OQ-6）+ 6（不播，OQ-2）**。本 plan 只立骨架，种子内容由 87-02 铺开。
3. **父菜单不能用名字定位**。库内是「live(`status=0`) + stopped(`status=1`)」**两套平行菜单树**（楼宇/楼层/工位/信息点/机房/专线/机房设备管理各 2 条同名 C 菜单，各挂一套同名 F 行；`network:command` 有 2 条不同名同 perms）⇒ 必须用 `perms + menu_type='C' + status=0` 定位；命中多条取**父集合全部**，授权按「持有任一父」。
4. **`GrantNewMenuToRolesHavingParent` 不可用**（`internal/core/db/migrations/menu_grant_helpers.go:26`）：PG-only（sqlite 直接 `return nil` ⇒ 假绿）+ 按 `menu_name` 匹配（会命中停用旧菜单 = **越权授予**）+ 依赖未实证的 `(role_id, menu_id)` 唯一约束（OQ-1）⇒ 改用 `migration_218` / `migration_221` 的 **`NOT EXISTS` + parent_id 精确授权**（双方言、可用 sqlite 完整测）。
5. **校验脚本的 F 型盲区**：Go migration 只被扫字符串字面量 → 全进 `untyped`（仅参与 c 类存在性）⇒ **d 类（菜单 F 型 vs TS）对 Go 侧永不生效**。本 plan 先把「Go 侧 F 型声明块解析」的骨架立起来，87-03 完成硬断言与门禁接入。

### 为什么是 tracer-first

本 phase 涉及三方契约（Go migration ↔ `sys_menu` 表 ↔ Node 校验脚本），任何一处架构错位（例如授权用错父定位口径）都会在 65 条种子铺开后放大成批量越权。因此第一个任务必须是**一条码端到端打通**的 tracer：sqlite 建表 → 执行迁移 → `sys_menu` 落 1 条 F 行 → `sys_role_menu` 落 1 条授权 → 重跑零增量。剩余任务是横向扩展。
