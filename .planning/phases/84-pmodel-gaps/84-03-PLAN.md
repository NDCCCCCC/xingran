# Plan 03 — PMODEL-04：迁移记录表 + GORM 漂移登记

## Context

迁移机制是「幂等重跑」不是「应用一次」：`internal/core/db/database.go` AutoMigrate（:805）先 GORM AutoMigrate（:985），再硬编码调用块逐个执行 `migrations.MigrateNNN`（PG :1016-1140 / sqlite :1145-1214），每次启动无条件重跑，全仓**无任何已应用版本记录**（无 gorm_migrations / sys_schema_migrations）。

**核心设计裁定（研究 §PMODEL-04）**：做「记录 + 对账」，**不做 skip 控制执行**——记录表不参与任何迁移是否运行的判断，现有幂等重跑语义零改变。`SKIP_AUTOMIGRATE=true` 旁路（core.go:276-296）行为：旁路只跑 215-220 子集（database.go:1402-1463），记录也应只含这些版本——旁路路径同样 upsert。

**硬约束**：记录失败只 WARN 不阻断启动（对齐 migration_223 非阻断档先例）；零新依赖；不给 `sys_role_menu`/`sys_user_role` 补模型列（只登记）。

## must_haves

truths:
- `sys_schema_migrations` 表存在，覆盖全部活跃版本（含历史 seed 033-224 + 225）
- 二次启动幂等：记录数不变，无重复行
- 记录失败只 WARN、绝不阻断启动；迁移执行语义（幂等重跑）零改变
- 只读对账能力存在：能输出 registry vs 库内记录的 missing/extra
- SKIP_AUTOMIGRATE 旁路路径同样留痕（只记录其真实执行的子集）
- `sys_role_menu` / `sys_user_role` 漂移登记为显式债务 note；模型文件零改动
- 不做迁移 skip 控制执行

## Threat note

记录表只写不读执行流（无 skip 语义），无 scope/权限面；但 **runAndRecord 绝不能因记录失败吞掉迁移本身的错误**——迁移失败仍必须返回 error（单测 TestRunAndRecord_NonBlocking 锁定方向，防止有人把 WARN 改成吞错）。
