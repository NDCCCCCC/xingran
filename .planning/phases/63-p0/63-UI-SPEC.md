## 1. STOP-01 — 分页文案契约（showTotal）

**唯一合法口径**（全项目所有分页表）：

```
total > 0  →  共 {total} 条 / {pages} 页        例：共 128 条 / 13 页
total = 0  →  （不渲染任何文案，showTotal 返回 ''）
```

- `pages = Math.ceil(total / pageSize)`，**不得**再使用 `Math.max(1, …)` 掩盖空数据。
- 落地点：`src/hooks/usePagination.ts:122` 的 `showTotal` 一处修改，`paginationProps` 的全部消费页自动生效。
- 手写 `showTotal` 的存量页（system 5 处、operations 6 处等显示"共 N 条"的页面）**本 phase 不改**——它们语义正确，收敛到统一口径归 Phase 67 存量迁移；但任何被 STOP-02/03 触碰的页面必须改用 `paginationProps`，即时获得统一口径。
- 树表（dept/menu，`pagination={false}`）不在 STOP-01 范围（审计标 P1），本 phase 不做。

## 2. STOP-02 — total 数据驱动契约（backups / discoveries）

- 契约：`paginationProps.total` 必须等于最近一次列表接口返回的 `data.total`；**列表数据到达后必须回填 total**，禁止解构 `setTotal` 为 `_setTotal` 后弃用。
- 最小修法：`src/pages/network/backups/index.tsx:79`、`src/pages/network/discoveries/index.tsx:34` 在数据返回处调用 `setTotal(data.total)`（`backups` 另需清理 `:660-663` 的页面级手动 `setCurrent/setPageSize` 双写，只保留 `paginationProps.onChange`）。
- 用户可见结果：能翻到第 2 页及以后且每页有数据；`showQuickJumper` 跳页可达；总条数与后端一致。

## 3. STOP-03 — OU 列表服务端分页契约

- `src/pages/ad-domain/ous/index.tsx:130-131`：删除固定 `pageSize: 100` 的一次性拉取语义，列表请求改为携带 `current` / `pageSize`（项目分页约定：`current` 从 1 起）。
- `:539`：表格 `pagination` 从 `{{ pageSize: 50, size: "small" }}`（纯前端分页、无 total、无 onChange）改为接 `paginationProps`（含后端 `total`、`onChange`、`showTotal` 统一口径）。
- 用户可见结果：OU 总数 > 100 时可翻到最后一页；切换 pageSize 生效且页码重置到第 1 页；无"数据被截断"的假象。

## 4. STOP-04 — 提交防重契约（confirmLoading）

**规则**：任何含异步提交的 `Modal`（含 `BaseEditModal`），确认按钮在提交请求未返回前必须处于 loading 且不可再触发 `onOk`。二选一实现（不新增封装）：

1. `onOk` 返回 Promise（antd 自动 loading 并拦截重复点击），**或**
2. 受控 `confirmLoading={submitting}` + `onOk` 内 `if (submitting) return` 守卫。

- 覆盖范围：04 分片 27 个 0 命中 Modal（pools:471、users:647、orders:706、periodic/templates:422、categories:257、configs:376、AccountPoolTab:418 为代表）+ system 15 处无防连点 Modal（01 分片 §3.3：user:814-820、role:344-352、menu:365-376、config:485-491、dict:849-892/:895-950、NoticeForm:122、profile:321-327/:372-378）+ operations 缺失处（02 分片：dedicated-lines `handleSave`、WorkstationDeviceTable:615-682 等 23 个中 15 个）。
- 提交期间取消按钮同样禁用（`cancelButtonProps={{ disabled: submitting }}`），避免"提交中点取消"产生半写状态。
- 用户可见结果：网络节流下快速双击"确定"只产生 1 次写请求、0 条重复记录；按钮呈 loading 态给出"正在保存"反馈。

## 5. STOP-05 — 危险操作确认契约（批量删除）

**规则**：任何批量删除入口在发请求前必须经过二次确认；确认弹窗必须回显将影响的数量 N。

- **首选实现**：复用既有 `BatchDeleteButton`（`@/components/shared/BatchDeleteButton.tsx`，内部 Popconfirm + 计数 + danger ghost），把 7 处裸 `batch-delete` 调用替换/接入它。
- 页面已有自建工具栏、不便替换按钮的，最小止血为 `Modal.confirm`：

| Element | Copy |
|---------|------|
| 确认标题 | 确认批量删除 |
| 确认内容 | 将删除选中的 {N} 项，删除后不可恢复，是否继续？ |
| okText | 删除 |
| cancelText | 取消 |
| ok 按钮语义 | `okType: "danger"`（antd `okButtonProps={{ danger: true }}`） |
| 确认中状态 | ok 按钮 loading（接 STOP-04 同一防重规则），成功后 `message.success("已删除")` 并刷新列表 |

- `BatchDeleteButton` 的既有默认文案（`BATCH_DELETE_CONFIRM` 常量 + 按钮 `批量删除 ({selectedCount})`）视为合法，无需改组件。
- `selectedCount === 0` 时按钮不渲染（`BatchDeleteButton` 现行为），不得出现可点击但无效的批量删除按钮。
- 覆盖范围：system 6 处（user:544-558、config:189-203、post:156-169、dict 类型+数据两处、role:132-149、notice:99-109）+ network 5 处（devices:510、credentials:188、ports:322、mac:226、useTemplateModals.ts:129）；重叠页去重后按实际文件清单执行。

## 6. STOP-06 — 假功能入口处置契约

**原则**：用户可见的每个可交互入口必须产生其文案所承诺的真实行为；做不到就**隐藏入口**，禁止用 `message.info("待实现")` 类占位维持假入口。

| 位置 | 现状 | 本 phase 处置（决策） |
|------|------|----------------------|
| `src/pages/operations/assets/index.tsx:203` 编辑按钮 | `message.info("编辑功能待实现")`，点击无实际功能 | **隐藏按钮** + `// TODO(P67): 资产编辑表单接入` 注释追踪。本 phase 不实现编辑表单（超出止血范围） |
| `src/pages/operations/assets/index.tsx:687-691` "下载模板" | 与"导入"同指 `setImportVisible(true)`，模板下载不存在 | **接真功能**：改为 `excelApi.downloadTemplate("asset")`（`ExcelImportLazy` / 后端 `excelApi` 已支持模板下载），文案"下载模板"承诺兑现 |
| `src/components/reconciliation/ReconciliationDrawer.tsx:67-70` "历史变更"/"例外规则"两个 Tab | `useState([])` 只读不写，永久空态 | **隐藏这两个 Tab**（数据接入前不展示永久空态），Tab items 按"有数据源才渲染"的条件化，留 TODO 追踪后续接入 `useReconciliationTimeline` / 例外规则接口 |

- 用户可见结果：不再存在"点击后仅弹提示/点击后无任何变化"的入口；Drawer 内不出现永久空 Tab。

## 7. STOP-07 — 表格滚动 / 固定列契约

**规则**：`fixed: "right"`（或 `"left"`）列所在的 `<Table>` **必须**同时设置 `scroll={{ x: <列宽合计 或 "max-content"> }}`，二者成对出现；缺 `scroll.x` 的 fixed 声明视为缺陷。

- 修复点（6 处）：`pages/system/user/index.tsx:272`、`config/index.tsx:291`、`dict` 两表（`:129`、`:231`）、`captcha-background/columns.tsx:96` 所在表、network/monitor 侧同类命中——统一补 `scroll.x`，不删除 fixed 声明（操作列贴右是用户预期）。
- 取值：有明确列宽定义的表用列宽合计像素；未逐一量宽的表用 `scroll={{ x: "max-content" }}`。
- 不在本 phase 给所有 12 个无 scroll 表补 scroll（审计标 P1，归 Phase 64/67）；只修"fixed 失效"这一症状面。
- 用户可见结果：宽表横向滚动时操作列始终贴右可见、可点击，不错位。
