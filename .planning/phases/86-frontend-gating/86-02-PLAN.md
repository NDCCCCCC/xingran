### 本波的两个特别项

1. **唯一可迁的旧式判定点**：`LocationAliasDrawer.tsx:62-65` 的 `useMenuStore((s) => s.permissions)` + 自造 `hasPermission` + 硬编码字面量 `"ops:location:alias:add"` / `"ops:location:alias:delete"`，以及 `workstations/index.tsx:122` 的 `menuPermissions.includes("ops:location:alias:list")` —— 这三个码**已在 TS 清单**（`permissionCodes.ts:139-144`），因此**必须迁为 `useActionPermission` 三态门控**（消除第二真相源 + 拿到未就绪 disabled 语义）。
   ⚠️ 其余 **6 处**旧式直判（`network/ports:130-132`、`vdi/VirtualMachineList:46,52,109,929-935`、`asset/reconciliation/exceptions:85-86`、`fix-suggestion:64-67`、`network/mac/history/MACHistoryPage:117-119`、`ad-domain/configs/ReconciliationTab:42,63-64`）的码**不在 TS 清单** → 归 86-04 登记 N/A 豁免，**不改**（其中 `ad-domain/configs/ReconciliationTab` 所在页已门控 → 只登记不进豁免清单，故豁免清单里带「旧式直判」字样的恰为 **5** 条，见 86-04 Task 4.4）。
2. **平面图保存（floor-plan / walls / doors / workstations）**：`floors/index.tsx:460` 的 `saveFloorPlan(data, currentFloor)` 是墙/门/平面图**以及工位位置**四个写域的唯一前端落点 —— `useFloorPlanEditor.ts:255` 的 `await saveWorkstations(data.workstations)` 会**同时更新工位位置**。四组码均在 TS 清单，但**一个动作对应四组码** → 决策取**最严**：`opsFloorPlan.edit` 为主判据（平面图整体保存），`opsWall.*` / `opsDoor.*` / **`opsWorkstation.edit`** 为子判据；实现上取四者的**逻辑与**（四码全持才可用）并在注释里写明该合并口径（避免出现「有任一码即可保存」的越权）。
   ⚠️ **漏掉 `opsWorkstation.edit` 会造成越权**：持 `opsFloorPlan.edit` + `opsWall.*` + `opsDoor.*` 但**无** `opsWorkstation.edit` 的用户，仍能通过平面图保存**改写工位位置**。
   ⚠️ 「**查看平面图**」行操作（`FloorTableColumns.tsx:111-116` → `onEditFloorPlan(record)`）打开的就是这个**可保存**的编辑器 → **必须并入同一合并口径**（与保存按钮同一决策对象），否则该入口会绕过门控直通编辑器。


⚠️ **三种「无 permission 位」的页面形态**：
- `PageTable` 的 `batchDelete={{ onDelete, target }}`（契约无 permission 位，`PageTable.tsx:60`）→ 条件传参 `batchDelete={permRemove.visible ? { onDelete: handleBatchDelete, target: "楼宇" } : undefined}`；
- `floors` 页的自研 `FloorSearchForm` 的 `onBatchDelete` prop（`FloorSearchForm.tsx:43,169`）→ **在页面层决定是否把该回调传下去**（传 `undefined` 或传 noop + 按钮 disabled），**不改 `FloorSearchForm` 的 props 契约**（`onBatchDelete: () => void` 是必填 → 页面层传一个「不可用时 noop」的包装，或把按钮的 `disabled` 提到页面层控制；**推荐**：页面层传 `onBatchDelete={() => { if (!permRemove.visible) return; handleBatchDelete(); }}` 并同时给 `FloorSearchForm` 增补一个**可选** `batchDeleteDisabled?: boolean` prop（加法扩字段，不改既有必填项语义））；
- `floors` 页的自研 `FloorSearchForm` 的 **导入/导出触发按钮**（`:160` / `:163`，回调由 `index.tsx:541` / `:542` 传入）→ 触发按钮在**子组件内部**，页面层**无处可插**条件渲染 → **必须**给 `FloorSearchForm` 增补两个通道：① `onImport` / `onExport` 由**必填改为可选**（接口**放宽** —— 既有调用方传了回调时行为零变更；**不传 ⇒ 该按钮不渲染**）；② 增补**可选** `importDisabled?: boolean` / `exportDisabled?: boolean`（按钮 `disabled` 位）。页面层写法：`onImport={permImport.visible ? () => setImportVisible(true) : undefined}` + `importDisabled={permImport.disabled}`（导出同理）→ ready 无权限时**按钮不渲染**，未就绪时**渲染且 disabled**。

> ⚠️ **floors 的导入/导出若不加这两个可选位就必然失败**：触发按钮在子组件内，页面层只有「回调不传 ⇒ 不渲染」+「disabled 位」两条通道能把门控结果送进去。**本波组件契约加法合计两处**（`batchDeleteDisabled` + `onImport/onExport` 可选化 + `importDisabled/exportDisabled`），**均须在 plan 报告中登记**；`src/components/shared/**` 仍**零 diff**（`FloorSearchForm` 属 `src/pages/operations/floors/components/`，非 shared）。
