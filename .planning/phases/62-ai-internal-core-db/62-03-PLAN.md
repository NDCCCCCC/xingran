<objective>
修复 init_data.go 种子层三档问题:共识 C2(默认 admin/admin123 + 死 salt "default",国密系统出厂带已知弱凭据)、共识 C5(种子幂等粒度过粗,首次启动中途失败永久遗留半成品)、opencode MEDIUM(菜单种子循环未处理非 RecordNotFound 错误,falls through 到 Create 产生重复菜单);顺带落地 codex MEDIUM 的 createUserRoleRelations 原生 SQL 消除(tradeoff 标注,见 Task 3)。

Purpose: 这是每次新装部署的第一道安全门面;当前实现让任何拿到 DB 的人都知道管理员密码,且一次启动抖动就能让部门树永久残缺。
Output: 环境变量可覆盖的初始密码 + 大声告警、逐棵子树幂等的部门种子、错误路径正确的菜单种子。

**Tradeoff 记录(用户锁定"拿不准的标注 tradeoff"):**
- C2 完整方案"首登强制改密"需改动登录链路(handler + 前端),超出本纯 db 修复 phase 范围 → 本计划落地"env 覆盖 + 大声 WARN + 死 salt 清除",强制改密记录为 deferred。
- C5 全量 db.Transaction 包裹 initData 会在启动期持长事务(9 个种子函数串行),失败回滚与既有"失败仅警告不阻断启动"策略(core.go initDBAndData 步骤 3)冲突 → 选择逐条 check-and-create 细粒度幂等,成本更低且兼容既有启动策略。
</objective>
