## 1. FIX-01 — 表格 loading 契约

**规则**：所有数据驱动的 `<Table>`（含 Modal/Drawer 内嵌表）必须接 `loading` prop；请求进行中为 `true`，返回/失败后为 `false`。加载反馈统一用 **Table 原生 `loading` 蒙层**，禁止为弥补缺失 loading 而引入骨架屏（Skeleton）或整页 `Spin` 包裹——表格 `loading` 是唯一口径（骨架屏推广归 Phase 66 PageTable 三态设计，本 phase 明确不引入）。

- 数据来源：接入 `useTableManager` / `usePagination` 的页面从 hook 取 loading；手写数据层的页面用既有 boolean state。禁止出现「数据在请求中但表格渲染空数组且无蒙层」的状态。
- **空数据与未加载的区分**：初次加载完成前 `data` 允许为 `[]`，但 `loading` 必须为 `true`（antd 在 loading 期间不渲染空态插画，天然区分「加载中」与「暂无数据」）；请求失败后 `loading=false` 且按 `## 4` 出错。
- 覆盖范围（扫描时点 2026-10-24，7 处 Modal/Drawer 内嵌表，全部无 loading 信号）：

| 文件 | 表用途 |
|------|--------|
| `pages/network/command/modals/DetailDrawer.tsx` | 命令详情内嵌表 |
| `pages/network/command/modals/DispatchModal.tsx` | 派发选择表 |
| `pages/network/discoveries/modals/ResultModal.tsx` | 发现结果表 |
| `pages/network/executions/modals/DetailDrawer.tsx` | 执行详情内嵌表 |
| `pages/network/executions/modals/ExecuteModal.tsx` | 执行目标选择表 |
| `pages/network/templates/modals/VariablesModal.tsx` | 模板变量表 |
| `components/network/port-write/BulkWriteDrawer.tsx` | 端口批量写入预览表 |

  执行时以 `grep -rl "<Table" pages/network pages/monitor components/network` 复扫为准：任何「含 `<Table` 且整个文件无 `loading=` 与 spread 注入」的文件一律纳入。03 分片当时口径为 25 表中 10 缺失，63 之后部分文件结构有变，**以执行时复扫清单为准，规则优先于清单**。
- 用户可见结果：慢网（DevTools 节流 Slow 3G）下打开任一 network/monitor 列表或内嵌表，表格区域显示 antd 转圈蒙层而非空白行区。

## 2. FIX-02 — 弹窗防误关契约（maskClosable / keyboard）

**规则**：所有**表单类 Modal**（含 `<Form>` 或任何可编辑输入的弹窗，含 BaseEditModal 消费者）必须同时显式声明：

```tsx
maskClosable={false}   // 点遮罩不关闭
keyboard={false}       // 按 ESC 不关闭
```

**决策（粗糙口径，非脏检查）**：本 phase 采用「全量关死遮罩/ESC 关闭路径」而非「`Form.isFieldsTouched()` 脏检查 + 确认弹窗」。理由：

1. Success Criteria 2 的验收是「不关闭**或**先确认，内容不丢」——关死路径即满足，且行为确定、可静态验收（grep 即可）。
2. 精细脏检查需要每处弹窗接 Form 实例并写确认分支，22 处逐个侵入的风险与工期不匹配；该契约随后**下沉 Phase 66 FormModal 内建**（confirmLoading/脏检查/destroyOnHidden 一并契约化），届时迁移页面自动获得。
3. 63 已确立「组件抽取不提前」原则，本 phase 不得为脏检查新建封装。

**存量修补清单**：

| 位置 | 动作 |
|------|------|
| `components/modal/BaseEditModal.tsx:44` | 默认值 `maskClosable = true` 改为 `false`，并同步新增 `keyboard` prop（默认 `false`）透传——共享封装默认值修正，全部消费者自动收紧；个别确需可关的调用点（只读详情类）可显式传 `true` 并注释原因 |
| network/monitor 22 个业务 Modal（03 分片 1.3 口径：`<Modal>` 22 个 / 17 文件，执行时以 `grep -rl "<Modal" pages/network pages/monitor` 复扫去重） | 逐个显式补 `maskClosable={false} keyboard={false}`；已由 BaseEditModal 承载的走默认值，不重复声明 |
| 已合规先例 | `components/captcha/CaptchaModal.tsx:116`、`components/network/port-write/BulkWriteDrawer.tsx:238`（`maskClosable={!isExecuting}` 条件写法合法——执行中不可关，空闲可关，保留） |

- 非表单类 Modal（纯详情展示、无输入控件）不强制，但补齐不禁止；`Modal.confirm`（函数式确认框）不在此列——其语义就是「可取消」，ESC/遮罩点击等价取消按钮，63 STOP-04 已处理其防重。
- 用户可见结果：在任一表单弹窗填入内容后点击遮罩区域或按 ESC，弹窗保持打开、内容完好；只能通过「取消/关闭」按钮（其确认行为归 Phase 66 脏检查，本 phase 直接关闭属可接受降级——关闭动作是用户显式意图）。

## 3. FIX-03 — 分页表排序契约（服务端白名单排序）

**判定标准**（checker 2026-10-24 复核源码，修正初版「后端不支持排序」的误判）：三个列表的后端**均已支持** `orderByColumn` / `isAsc` 白名单排序，前端只需接参，不构成里程碑 Out of Scope 的「后端接口改造」：

- cache：`internal/api/v1/monitor/cache_handler.go:144-145` 透传 `OrderByColumn/IsAsc` → `internal/services/monitor/cache_service.go:237-246` 按 `cacheAllowedSortFields` 白名单（`key/type/location/ttl/size/createdAt/updatedAt`，恰为前端 7 列全集）应用。
- job：`internal/services/scheduler/job_service.go:300` `base.ApplySort(db, params.BaseListRequest, jobAllowedSortFields)`，白名单 4 字段：`jobName/jobGroup/status/createdAt`；`:302` 的固定 `Order("created_at DESC")` 仅为无排序入参时的默认。
- job 日志：`internal/services/scheduler/job_log_service.go:117` `jobLogAllowedSortFields` 白名单 4 字段：`jobName/jobGroup/status/createdAt`。

→ **结论：白名单内列改服务端排序（全量正确结果），白名单外列移除 sorter。** 不做「前端排序 + 常显降级说明」——初版契约建立在错误事实上；「只对当前页生效」的半真排序比无排序更误导（用户看到排序箭头即默认跨页有序）。

**规则**：

1. **服务端排序统一范式**：复用既有 `useServerSort`（`@/hooks/useServerSort.ts:89`，先例：`pages/monitor/logs/columns/loginColumns.tsx`、`pages/knowledge/articles/index.tsx` 等）+ `createSorterMeta`，列表请求透传 `orderByColumn` / `isAsc`（URL 按路由自动持久化，见 hook 内建行为）。cache 列表 7 列全部接 `createSorterMeta`；job 主表仅 `jobName/jobGroup/status/createdAt` 4 列接；job 日志表仅 `status` 列接（前端列 `startTime` 映射 `orderByColumn: "createdAt"`，二者同义：`job_log_service.go:118-119` 无入参时默认即按 `created_at DESC`）。
2. **白名单外列移除 sorter**：job 主表 `invokeTarget/cronExpression/concurrent/nextRunTime` 4 列、job 日志表 `duration/jobMessage/exceptionInfo` 3 列——删除 `createSorter` 调用，表头不再渲染排序箭头（后端不支持这些字段的 ORDER BY，加白名单属后端接口改造，被 Out of Scope 排除；保留前端排序即回到「当前页半真排序」缺陷）。cache 7 列无此问题（全在白名单）。
3. **范围收敛**：本 phase 仅覆盖 REQUIREMENTS 点名的 cache / job 两页（含 job 日志表）。`pages/monitor/server/index.tsx:199-298` 的「本地+服务端双轨」是另一缺陷形态（03 分片 3.5 第 22 条 P2 面），且该页已有服务端排序轨，不在 FIX-03 点名范围，不动。
4. **不做降级说明文案**：初版方案中的常显 caption（`排序仅对当前页数据生效`）随降级方案一并取消——服务端排序后不再存在「仅当前页生效」的歧义；白名单外列移除 sorter 后也不存在「点了才知道只排当前页」的假入口。
5. 用户可见结果：在 cache/job 表点击白名单内列表头，排序结果跨页全量正确（后端 ORDER BY）；白名单外列不再显示排序箭头，不会产生「排序了但结果不对」的误导。

## 4. FIX-04 — 统一错误出口契约

**决策：不新建 showError helper，指定既有 `handleApiError`（`utils/errorHandler.ts:136`）为唯一合法错误出口。** 理由：

1. 它已满足全部形态要求：内部 `extractErrorMessage` 提取后端 message → `getAppMessage().error("动作失败: 原因")` → message 实例经 `utils/antdMessage.ts` 桥接自 `<App>` 上下文（63 已禁静态 message，此桥接是既有合法通路）；内部同时 `console.error`（`:101`）保留开发期日志——「收敛 console 吞错」不等于消灭日志，日志由出口内部统一产出。
2. 63 UI-SPEC Copywriting 已预认可此出口（「错误提示 沿用 utils/errorHandler.ts → handleApiError 出口」），本 phase 将其升格为强制契约。
3. Phase 65/66 契约组件（ConfirmDelete / PageTable / FormModal 及 `useMutationAction` 类 hook）复用的正是这个模块级函数——无新增公共件、无双出口风险。**本 phase 新建公共件数量：0**（任务书预留的「唯一新公共件」额度不使用，以复用既有 `handleApiError` 代替——这是比新建更优的落点）。

**catch 三分支规则**（全部 52 处及后续新增 catch 的唯一合法写法）：

```ts
catch (error) {
  if (isFormValidationError(error)) return;      // ① 校验错误：静默（Form 自带行内提示）
  handleApiError(error, "动作名");                // ② 业务错误：统一出口（toast + 内部日志）
  // ③ 成功提示不在此层：try 内 message.success("xxx成功")，用组件内 App.useApp() 或页面既有通道
}
```

**契约细则**：

| 维度 | 规则 |
|------|------|
| 文案模板 | `${context}失败: ${后端message}`（`handleApiError` 内建，不逐处手写）；context 为动作名（如 `删除缓存`、`执行任务`），沿用各页既有动作命名 |
| 时长 | antd message 默认（3s），不逐处自定义 |
| 防轰炸 | 同一 catch 只出一条 message（现样板即如此）；列表加载类失败**优先置 error state 渲染 `ErrorAlertWithRetry`**（`@/components/shared/ErrorAlertWithRetry.tsx`，11 处既有先例），toast 仅用于操作类（增删改/执行）失败——数据区错误不靠 toast 表达 |
| 分流 | `isFormValidationError` 判定必须前置于 `handleApiError`，防止表单校验错误弹 toast（03 分片 3.4 第 15 条） |
| 豁免 | 测试文件（`__tests__` / `*.test.*`）不在此列；`console.warn` 用于纯调试性、非用户可行动的分支可保留但不得作为错误唯一出口 |
| 覆盖范围 | **本 phase = network+monitor 域 52 处**（REQUIREMENTS 口径，逐域清单见 03 分片 3.6 第 25 条 20 处 monitor + 3.4/3.6 相关条目；执行时以 `grep -rEn "console\\.(error\\|warn\\|log)" pages/network pages/monitor components/network components/CronSelector` 复扫去重）。其余域 235 处（system 49、operations 34、duty 14、workorder 10、components 等）列入 Phase 67 存量迁移，本 phase 不触碰 |

## 5. FIX-05 — 图标按钮可访问名契约

**规则**：任何 icon-only 按钮（只渲染图标、无可读文本的 `<Button>`）必须携带 `aria-label`（人类可读动作名）与 `title`（悬浮提示，与 aria-label 同文案）；非 icon-only 按钮不强制。触达读屏的最小充分集是 `aria-label`（`role` 天然继承自 `<button>`，无需手写 `role`；`tabIndex` 保持原生流，不额外设置）。

**范围收敛策略（决策）**：全前端 icon-only 按钮约 250 处、aria 仅 20 处，不可能本 phase 一次补齐。按「封装一处 > 逐个补属性、高频域 > 低频域」收敛：

| 层 | 覆盖内容 | 本 phase 动作 |
|----|---------|--------------|
| ① 共享封装（杠杆最大） | `components/shared/ActionButtons.tsx` —— 表格行内操作按钮的既有统一封装，network 全片已接入 | 组件内部为每个 icon-only Button 输出 `aria-label={label}` + `title`，**改一处全片行内按钮生效**（属既有组件增强，非新组件；Phase 67+ 其他域接入后自动受益） |
| ② 本 phase 同域页面（与 FIX-01/03/04 同为 network+monitor，域内闭环） | `pages/network`、`pages/monitor`、`components/network` 工具栏/卡片上的散置 icon-only Button（刷新、清空、导出等） | 逐个补 `aria-label` + `title`（文案 = 既有动作名：`刷新`/`清空缓存`/`导出` 等） |
| ③ 其余域（system 51 处、operations/duty/workorder/ad 等） | 页面级散置 icon-only Button | **不在本 phase**，列 Phase 67 存量迁移（与 FIX-04 其余域 console 收敛同批）；01 分片 §3.8 第 161 条已给出 system 域清单 |

**否决 IconButton 新封装**：icon-only 按钮散布在工具栏、卡片、Table columns 三种上下文，属性诉求不一（danger / size / disabled），新建 `<IconButton>` 会与 `ActionButtons` 形成第二套行内操作封装，违反「抽取不造重复范式」；aria 是逐按钮一行的声明成本，封装收益仅存在于「忘了写」的场景——该场景由代码评审 grep 检查项兜底（见验收）。

**验收检查项（可脚本化）**：
- `components/shared/ActionButtons.tsx` 中每个 icon-only `<Button>` 均有 `aria-label`；
- `grep -rEn "aria-label" pages/network pages/monitor components/network` 命中数 > 0 且行内操作经 ActionButtons 的路径无裸 icon Button；
- 抽样读屏验收：NVDA/VoiceOver 聚焦任一 network/monitor 行内删除/详情按钮朗读出动作名而非「按钮」。

- 用户可见结果：读屏器用户在 network/monitor 任意列表页，行内与工具栏图标按钮均能朗读其功能名。
