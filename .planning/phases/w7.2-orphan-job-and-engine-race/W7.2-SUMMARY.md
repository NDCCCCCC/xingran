## 1. 任务 A：孤儿 RPA job 回收机制（P0）

### 1.1 根因（方向性缺口，不是「漏了一个 case」）

**表层**：生产库 `sys_job` 的 RPA 分组有 10 条孤儿 job —— 对应的 `sys_rpa_schedules` 行已被软删或物理删，而 job 仍 `deleted_at IS NULL` / `status=0`。调度器启动时会被加载进 cron，到点调用 `rpa_schedule:<已删 id>` → handler 里 `TriggerNow` 查不到 schedule → 报错刷日志。

**深层**（这才是本波次要修的东西）：`SyncEnabledJobs` 的同步是**单向**的 —— 只从业务表推向执行表（`Ensure`/`Remove` 都按 id），**从不对账执行表里「业务表已经没有」的行**：

```go
// 修复前 internal/services/rpa/schedule_service.go:464-484
func (s *scheduleServiceImpl) SyncEnabledJobs(ctx context.Context) error {
	var all []rpamodels.Schedule
	s.db.Find(&all)          // ← GORM 软删自动排除 → 被删的 schedule 根本进不了循环
	for i := range all {
		if sched.Status != ScheduleStatusEnabled {
			s.jobSyncer.RemoveScheduleJob(ctx, sched.ID)   // 只处理「存在但停用」的
			continue
		}
		s.jobSyncer.EnsureScheduleJob(ctx, sched.ID, sched.Name, sched.CronExpr)
	}
	return nil                // ← 从不扫 sys_job 侧找「schedule 已消失」的孤儿
}
```

于是：**绕过 API 的数据操作**（本轮 UAT 期间用 SQL 直接插/删 schedule）、或 `Delete` 中途失败，都会留下永久孤儿 —— **没有任何机制会回收它们**。这不是「某个函数写漏了」，而是同步方向缺了一半。

### 1.2 修复（三处）

#### 修复 1：补上反向对账（prune）

**位置**：`internal/scheduler/rpa_schedule_tasks.go`（实现方）+ `internal/services/rpa/schedule_service.go`（调用方）

- 新增 `RPAScheduleJobSyncer.PruneOrphanJobs(ctx)`：扫 `sys_job` 中 `job_group='RPA'` 且未软删的所有行 → 从 `invoke_target` 解析 `scheduleID`（格式固定 `rpa_schedule:<uuid>`）→ **用 `Unscoped()` 查 schedule（含软删行）** → 三种情况判定为孤儿并摘除：
  - 不存在（物理删）→ 摘除
  - 存在但 `deleted_at != NULL`（软删）→ 摘除
  - 存在但 `status != 0`（停用）→ 摘除
  - 存在且启用 → 保留
- 每摘一条打一条 **INFO** 日志（摘了哪条、为什么），便于运维审计：
  ```
  [rpa_schedule] 孤儿调度任务已摘除: RPA调度:W71-VERIFY-failfast (job=f8775416-…, schedule=1c782840-…, 原因=调度记录已不存在（物理删除）)
  ```
- **对账失败不阻断启动**：只记 ERROR 日志（与调用方 `RegisterRPAScheduleTasks` 的容错口径一致）。
- **正向同步即使遇错也跑完再返回**，保证对账一定有机会执行（否则一条脏 schedule 会让本次启动完全跳过对账，孤儿继续残留）。
- **复用既有 job 查询逻辑**：摘除一律走既有 `RemoveScheduleJob`（内部用 `findJob` 定位），**没有新写一套 job 查询**；仅当 `remark` 被人工改写导致 `findJob` 失配时，按 `job.ID` 兜底摘除并打 WARN。
- 只读扫描 `FindOrphanJobs` 与真实清理**共用同一份判定实现**（`findOrphanJobs`），运维工具的 dry-run 报告与真实清理不可能出现两套口径。

#### 修复 2：`Delete()` 顺序加固（防新的孤儿）

**位置**：`internal/services/rpa/schedule_service.go`

```go
// 修复前：先软删 schedule，再摘 job —— 摘 job 失败就留下永久孤儿
db.Delete(...)              // 软删
jobSyncer.RemoveScheduleJob(...)  // ← 失败则 schedule 已不可见、job 还在 → 永久孤儿

// 修复后：先摘 job，成功后才软删
jobSyncer.RemoveScheduleJob(...)  // 失败 → 不删 schedule，返回「可重试」错误
db.Delete(...)                    // 软删
```

失败语义：
- 摘 job 失败 → **不删 schedule**，返回错误 → 调用方/运维可重试（幂等）
- 软删 schedule 失败 → job 已摘、schedule 仍在 → 下次对账会补摘（幂等）

**两种失败都不产生孤儿**；孤儿兜底由 prune 对账负责。

#### 修复 3：一次性清理工具（代码路径，禁止双实现）

**位置**：`scripts/ops/rpa_orphan_job_prune/main.go`

工具**不自带判定逻辑**：清理走与后端启动时**完全相同**的代码路径（`rpav1.ScheduleService.SyncEnabledJobs` → 同一个 `RPAScheduleJobSyncer` 的 prune 实现），保证「工具清掉的」与「后端启动会清的」是同一批。支持 `-dry-run`（只报告）、`-dsn`（显式连接串），退出码语义化（0=完成且验证一致 / 1=失败或不一致 / 2=参数错误）。

## 2. 任务 B：Engine 并发共享字段竞态（P0）

### 2.1 根因

`rpa-worker/internal/executor/engine.go` 的 `Engine` 结构体持有 4 个**共享可变**字段：

```go
type Engine struct {
	currentExecutionID string   // ← 共享可变
	currentWorkerID    string
	currentStep        int
	currentTotal       int
}
```

而 `Worker` 只 `NewEngine` 一次（`rpa-worker/internal/worker/worker.go:186`），`max_concurrency` 默认 5~8 → **最多 N 个 goroutine 同时执行同一个 `*Engine` 实例**：

```go
e.currentExecutionID = task.ExecutionID   // :85  多个 goroutine 同时写
e.currentWorkerID    = workerID            // :86
e.currentStep        = i + 1               // :177
e.currentTotal       = len(task.Script)    // :178
...
ExecutionID: e.currentExecutionID          // :420  截图进度上报（可能读到别人的 id）
ExecutionID: e.currentExecutionID          // :645  人工干预进度上报
go e.subscribeForHumanInput(ctx, e.currentExecutionID, e.currentWorkerID, ...)  // :659
```

**危害**：进度上报写到别的执行记录上；人工干预订阅挂到别人的 `execution_id`（人工干预信号永远收不到）。这是 W2-A 遗留 #4 提过但未修的债。

### 2.2 第一步：复现（复现**成功**，非「未复现」）

**新增**：`rpa-worker/internal/executor/engine_concurrency_race_test.go`

- 真 Chromium（`browser.TestChromePath()`，无则 skip）+ 真 fixture 页面（`startFixture`）+ 真 HTTP 上报通道（httptest 承接 `/rpa/workers/progress`），**同一 `*Engine` 实例并发跑 2 个不同 `execution_id` 的执行**（`max_concurrency = 2`）。
- 时序可控：A 的动作1 = `wait(5s)`；B 在 t≈0.8s 启动（落在 A 的 wait 窗口内）→ B 覆写共享 `currentExecutionID`；t≈5.0s A 进入 `pause` 分支读取共享字段。
- 断言口径：动作描述/暂停消息带归属标记（`act-A-` / `act-B-`），于是**每一条**进度上报都能反查它属于哪个执行 —— 断言覆盖全部上报，而不只是某一条。
- 用例选 `pause` 分支而非 `screenshot` 分支：两者都读共享 `currentExecutionID`，但 rod 的并发 fullPage 截图在同一个 Chrome 下不稳定（实测 `Unable to capture screenshot` 与 `context deadline exceeded`），那是浏览器层的并发噪声，与本用例要判定的「上报归属」无关；`pause` 分支的截图是 best-effort（失败不中断动作），判定更稳。

**修复前的实际运行结果（两个用例都失败，失败原因正是归属串号）**：

```
--- FAIL: TestEngine_ConcurrentExecute_ProgressExecutionIDRace (19.45s)
    engine_concurrency_race_test.go:268: 进度上报串号了：message="act-A--pause" 属于 exec-A-0001，却挂到 execution_id=exec-B-0002 上
--- FAIL: TestEngine_ConcurrentExecute_ScreenshotReportBelongsToOwner (16.92s)
    engine_concurrency_race_test.go:318: 人工干预进度上报串号：message="act-X--pause" 属于 exec-X-0001，却挂到 execution_id=exec-Y-0002 上
FAIL
```

**结论：竞态真实存在，且危害可复现**（A 的上报挂到了 B 的执行 id 上）。

### 2.3 修复

**位置**：`rpa-worker/internal/executor/engine.go`、`engine_actions.go`

1. **删除** `Engine` 上的 `currentExecutionID` / `currentWorkerID` / `currentStep` / `currentTotal` 四个字段 → `Engine` 回到**无状态**（可安全并发）。
2. **新增** `executionCtx` 结构体（每次 `Execute` 一份，**局部变量**）：
   ```go
   type executionCtx struct {
       executionID string
       workerID    string
       step        int
       total       int
   }
   ```
3. **显式传参**（而非从 Engine 取）：`Execute` → `executeAction` → `executeLoop` / `executePause` / `executeCondition` 全部带上 `execCtx`；nil 安全由 `execCtx.orDefault()` 兜底（单测可直接调用动作级函数）。
4. `subscribeForHumanInput` 已是显式传参，只需传本次执行的 `execCtx.executionID` / `execCtx.workerID` —— 人工干预订阅不再可能挂到别人的执行上。

## 3. 任务 C：架构裁定（纯文档）

**交付**：`.planning/notes/261127-rpa-schedule-vs-sysjob.md`（456 行 / 35181 bytes）

用户提问：「`sys_rpa_schedules` 调用 `sys_job` 写，能解决双写问题吗？`sys_rpa_schedules` 能否直接使用 `sys_job` 代替？」

### 结论 1：不能单表替代

字段级证据（逐字段核对模型定义）：

| `sys_rpa_schedules` 有 | `sys_job` 无 |
|---|---|
| `TaskID`（关联 RPA 任务，**业务必需**） | — |
| `Timezone` / `StartDate` / `EndDate` | — |
| `RunCount` / `LastRunTime` / `Description` | — |

| `sys_job` 有 | `sys_rpa_schedules` 无 |
|---|---|
| `MisfirePolicy` / `Concurrent` / `PrevRunTime` | — |

- 给 `sys_job` 加 RPA 专属业务列 → 污染被 8 个非 RPA 分组共用的通用表；且分组语义一旦被列语义污染，「派生镜像的边界」再也切不干净。
- 把 RPA 业务塞进 `sys_job.remark` 的 JSON → 无法索引、无法查询、前端列表要解析 JSON；且该路已有先例证明走不通：RPA 镜像行的幂等查找键**已经**塞在 `remark` 里（`rpa_schedule_id=`），查找是 `remark LIKE '%…%'` 而非等值索引，`remark` 被人工改写还会导致 `findJob` 失配。
- 反向也不行：不能把 `misfire`/`concurrent` 等执行策略塞进业务表（那会造出第二处双写）。

### 结论 2：「让 `sys_rpa_schedules` 调 `sys_job` 写」不解决双写

- 核心论点：那只是把双写**换了个方向**，双写本身还在，一致性问题原样保留。
- 补充论证（文档 §3.1）：现状**已经就是**「`sys_rpa_schedules` 调 `sys_job` 写」—— `Create`/`Update`/`Delete`/`SetStatus` 全是先写业务表再同步 job。所以这个提议**在现状里已经实现过，而且没解决问题**。
- 真正的解 = **把双写降级为「单写 + 对账」**：
  - 唯一真相源 = `sys_rpa_schedules`（业务语义都在这里）
  - `sys_job` 的 RPA 组 = **可随时重建的派生镜像**（丢了也能从业务表全量重建）
  - 对账（prune）保证派生表不会长出孤儿 ← **这就是任务 A**
  - 派生表不允许被外部直接写：运维改数据必须走 API，或改完后触发一次对账

### 结论 3：判据（供未来评审复用）

> 一张表是「派生镜像」的**充要条件**是：「**清空它 + 跑一次同步，能完全恢复**」。

- `sys_job` 的 RPA 组**满足**（前提是任务 A 的 prune 机制到位，否则清空重建会漏、旧孤儿永远回不来）→ 它**可以是**派生表。
- `sys_rpa_schedules` **不满足**（`TaskID` 只在它这里，清空后无法从 `sys_job` 恢复）→ 它**必须是**真相源。

## 6. 遗留

| # | 遗留 | 说明 |
|---|---|---|
| L1 | **RPA 组 job 的执行策略是镜像方默认值** | `createJob` 固定写 `MisfirePolicy=ExecuteOnce` / `Concurrent=false`，业务表里没有对应字段 → 想改「错过窗口怎么办」只能改代码。文档 §7 已列为相邻问题，**本波次未解决**。 |
| L2 | **`remark` 被人工改写时 `EnsureScheduleJob` 无兜底** | prune 有「按 job.ID 兜底摘除」，但正向 ensure 没有对应的「按 invoke_target 兜底查找」。文档 §7 已列。 |
| L3 | **调度器 `Start()` 不区分 `job_group`** | 通用 `Scheduler` 行为，按归属协议**不改**（会影响另外 8 个分组）。因此派生表一旦有脏数据就会被放大 —— 这也是为什么任务 A 的对账必须在**写入侧之外**再加一道兜底。 |
| L4 | **生产库当前启用态 schedule 数为 0** | 清理后 `count(schedule where status=0) == 0`，即 RPA 定时调度当前**没有任何启用中的调度**。派生镜像与真相源一致（0 == 0），但也意味着这套机制在生产上暂无活跃负载 —— 首次真实验证要等有启用调度时再看。 |
| L5 | **rod 并发 fullPage 截图在同 Chrome 下不稳定** | 实测 `Unable to capture screenshot` / `context deadline exceeded`。**浏览器层的并发缺陷**，与任务 B 的共享字段问题独立。本波次未修（任务 B 只保证归属正确）。 |
| L6 | **网络设备采集 scrapligo nil pointer panic（既有生产缺陷）** | `scrapligo/transport.(*Standard).Write` 在 `Channel.GetPrompt` goroutine 里空指针 → 整个后端进程崩溃 → systemd 重启。**部署前 restart counter 就已是 3→6**，与本波次无关。修它需动设备采集链路，超出本卡范围。 |
