# Plan 100-03: 下载链收敛 + downloadFilePost JSON 检测 + invariants 递归扫描

## Context

V130R-12 三件事（100-RESEARCH.md §3 实测）：① `src/lib/api/networkApi.ts` 持有 4 份平行下载实现——私有 blobAxios(:14-33，含权威版没有的硬编码 Content-Type 头 :18)、私有 triggerBrowserDownload(:183-192)、exportMACHistory(:142-176 GET) 与 batchExport(:206-239 POST) 各自内联 blob 请求 + 弱 JSON 嗅探（`size<1024 && type含json`，:156-166/:218-228）+ 手写文件名提取；MACHistoryPage.tsx:377-382 还有第 4 份手写 a/click 触发链。② 权威 `download.ts` 的 `downloadFilePost`(:79-92) 只有 status 码检查——200+JSON 错误体会被存成 .xlsx（用户拿到伪造成功文件）。③ invariants 的 `listApiFiles()`(:124-128) 非递归，`src/lib/api/` 子目录的 networkApi.ts 与 macHeatmapApi.ts 双双逃过 D-12 扫描。

**Decisions honored:**
- **D-100-6**: networkApi 内嵌 axios 下载链全部收敛到权威 `download.ts`（blobAxios + downloadFile/downloadFilePost），禁止平行实现；「收敛」非「函数删除」——exportMACHistory/batchExport 保留为薄壳，batchExport 的 `Promise<string>`（返回实际 filename）契约不变，9 个页面消费者零改动
- **D-100-7**: `downloadFilePost` 补 JSON 错误体检测——content-type 含 `application/json` 即解析错误体并 throw；附回归测试（mock blob/json 两分支）；判据锁定 content-type，**禁止把 size<1024 启发式搬进 download.ts**（RESEARCH Anti-Patterns）
- **D-100-8**: invariants `readdirSync` 改递归扫描，EXPECTED_FILES 13→15，Windows 路径分隔符归一

**Discretion 裁决（planner，记录备查）：**
- **JSON 检测同时作用于 downloadFile（GET）**：exportMACHistory 现有 CR-01 嗅探（GET 路径）随收敛消失（RESEARCH §3.4「收敛后嗅探逻辑随迁移自然消失」+ Anti-Pattern「以强判据替换而非搬运」）——若 GET 路径裸收敛，200+JSON 错误体将重新漏网存成 .xlsx，属已修缺陷回归。故在 download.ts 内实现一个共享检测 helper，downloadFile 与 downloadFilePost 同挂；D-100-7 的字面义务（POST + 两分支回归测试）全额履行，GET 侧为防回归的同构加强。
- **downloadFile/downloadFilePost 返回类型 void → Promise<string>**（返回实际 filename）：batchExport 一行收敛的必要条件；TS 源兼容（现有调用方均忽略返回值——opsApi.ts excelApi.export、asset export 等），type-check 验证。

### Task 1: download.ts JSON 检测 + filename 返回值（D-100-7，TDD）

**read_first:**
- `xingran-react-frontend/src/lib/download.ts`（全 93 行）——blobAxios :23-34、extractFilenameFromBlobResponse :37-52、triggerBrowserDownload :55-64、downloadFile :67-75、downloadFilePost :79-92
- `xingran-react-frontend/src/lib/download.test.ts` —— 既有 mock 基建：axios create 工厂 mock(:26-46)、blobAxios 打桩(:57-61)、triggerBrowserDownload 的 window/document 桩（沿用现有模式）
- `xingran-react-frontend/src/lib/api/networkApi.ts` :155-166 —— CR-01 嗅探现形（迁移后被 content-type 强判据替换的对象）
- CLAUDE.md「API Response Format」—— 错误 envelope `{code, message, data, ...}`，解析 `message` 字段

**action:**
先写测试（RED）再实现（GREEN）：

1. **download.test.ts 新增 4 用例**（沿用既有 blobAxios 打桩模式，mock `blobAxios.post`/`blobAxios.get` 返回可构造的 `{status, headers, data}`）：
   - POST + `content-type: application/json` + body `{"code":500,"message":"导出失败"}` → `await expect(...).rejects.toThrow("导出失败")`，且 triggerBrowserDownload 未被调用
   - POST + `content-type: application/json` + 非法 JSON body → rejects.toThrow（回退默认文案「下载失败」）
   - POST + 流式 content-type + Blob data → resolves，triggerBrowserDownload 以提取的 filename 调用（防检测误伤）
   - GET（downloadFile）+ application/json 错误体 → rejects.toThrow（GET 侧同构防护）
2. **download.ts 实现**：
   - 新增内部（不导出亦可，按文件内风格）async helper：读 `String(response.headers["content-type"] ?? "")`，含 `application/json` 时 `await response.data.text()` → `JSON.parse` → `throw new Error(parsed.message || 默认文案)`；parse 失败吞掉异常用默认文案 throw。**默认文案沿用各函数现有 `下载失败: ${filename}` 形态**。
   - `downloadFilePost`(:79-92)：status 检查之后、文件名提取之前插入 helper 调用（RESEARCH §3.4：优先生效于 status 分支之后的主漏网场景 = 200+JSON）；返回类型改 `Promise<string>`，末尾 `return filename`。
   - `downloadFile`(:67-75)：同构插入 helper；返回类型改 `Promise<string>`，`return filename`。
3. **既有用例回归**：download.test.ts 现有断言若 mock 响应缺 `headers` 字段，helper 需对 `headers` 缺失/undefined 容忍（`response.headers?.["content-type"]` 宽松读取），保证既有 blob 用例零改动通过。
