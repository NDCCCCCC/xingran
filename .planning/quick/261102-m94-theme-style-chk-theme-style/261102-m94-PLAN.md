<objective>
修复 PostgreSQL 上「保存暗色模式失败」：数据库报错 `new row for relation "sys_user_preference" violates check constraint "chk_theme_style" (SQLSTATE 23514)`。

根因（已调查确认，不再重复排查）：前端自 Phase 65 多主题移除后不再发送 `themeStyle`；后端 DTO 用普通 `string` 接收，`omitempty` 让省略字段跳过校验并留下空字符串；`UpdateUserPreferences` 的 UPDATE 分支用 `map[string]interface{}` 显式写出 `"theme_style": ""`，把「请求未携带该字段」误当成「显式置空」，而 PG 上该列带 CHECK 约束且不允许空串。本地 SQLite 不复现，是因为 SQLite 分支走 GORM AutoMigrate 建表（不生成 CHECK 约束），且 Create 分支因模型 `default:minimal` tag 让 GORM 省略零值字段、侥幸由数据库填默认值——只有 PG + UPDATE 路径会炸。

产出：服务层「省略即不修改」语义 + 落库前允许集合自检、绑定校验与数据库约束对齐、一条幂等的双方言数据归一化迁移、覆盖「空值不被写成空串」的回归测试。

**设计决策（本次定稿，勿再翻案）**

1. **空值语义 = 省略即不修改（保留原值），不是显式置空。** 请求字段为空（字符串零值 / 数值零值）表示本次未携带：Update 分支（已有行）兜底取该行当前值并原样写回（幂等 no-op）；Create 分支（无历史行）无原值可保留，兜底取规范默认值。理由有三：其一，PG 的 CHECK 约束证明这些列的值域**不含空串**，「显式置空」在该数据模型里根本不是合法状态，把「未携带」映射成「置空」必然越界；其二，保留原值语义上更安全——用户只切了一次暗色模式，不应连带把布局密度、主题风格重置回默认值；其三，Create 分支用默认值而非空串，是为了让「先 GET（无记录，拿到默认值）再 PUT」与「直接 PUT 建行」两条路径落库结果一致。
2. **绑定校验必须与数据库约束逐字对齐。** `themeStyle` 的 oneof 列表里多出一个数据库 CHECK 从未允许过的历史遗留值 `ink-amber`（全项目仅 `internal/services/system/settings_service.go` 出现一次），留着它等于允许客户端构造一个必然 500 的请求；`pageSize` 的 `min=5,max=100` 允许 30 这类值通过绑定却撞 `chk_page_size`，是同一类潜在 500。两处都收紧为 400。
3. **不加也不放宽任何 CHECK 约束；但要加一条数据归一化迁移。** 放宽约束等于把本次 bug 合法化 + 削弱数据完整性；把历史遗留值加进约束等于认可一个前端已删除、无 UI 的值——约束本身是正确的，错误在应用层写出了越界值。PG 上该迁移是 no-op（CHECK 在写入时就拦住了空串，PG 库里不存在违规行）；它真正修的是 SQLite 分支：GORM AutoMigrate 不生成 CHECK 约束，历史上被本 bug 写入过空串的行会残留，导致 GET 返回越界值。**不去 SQLite 补 CHECK 约束**：GORM 的 Migrator 不支持 CHECK 类型，用原始 SQL 重建表风险过高，超出本次范围。
4. **测试必须真正覆盖「空值不被写成空串」。** 现有测试表的建表 SQL 没有 CHECK 约束，所以失败在 SQLite 上表现为「静默写空串」而非报错，测不出根因。做法是给测试表显式加上与 PG 一致的 CHECK 约束——SQLite 原生支持 CHECK，只是 GORM AutoMigrate 不生成，手工写出来即可让测试环境与 PG 等价。

Purpose: 让「前端省略可选字段」这一 Phase 65 之后的正常请求形态，在任何方言下都不再触发数据库约束冲突。
Output: 服务层修复 + 绑定对齐 + 迁移 233 + 三层回归测试。
</objective>
