# v1.52 —— 共享工作区与 PR 交付纪律

> 来源：2026-11-02 Phase 129 / 130 的真实踩坑（每条都对应一次实际事故，不是假想）。
> 每条按 **现象 → 根因 → 机制** 写：**机制是可执行的命令/工具**，不靠记性。

## 0. 背景：共享工作区

本仓库是**多 agent 并行**的工作区（前端 webfe / 脱敏 qualguard / 后端设备取证等
同时在改）。由此产生的两类事故：

- **本地绿、CI 红** —— 你看到的绿可能来自**别人或你自己未提交的改动**；
- **我的改动混进了别人的文件** —— 目录级工具会波及无关文件。

⇒ 下面 6 条都是为消除这两类事故。

---

## 1. 推之前逐文件比对 blob sha

**现象**：用精确推送（只取指定 commit 的文件）同步分支时，某个文件在远端与预期不一致
（今天用到 3 次，**每次都抓到真实差异**）。

**根因**：推送是**按路径**取文件内容，不是按"我以为的"内容；工作区/暂存区/远端
三者可能已经分叉。

**机制**：推之前逐文件比对 blob sha（`git ls-tree` 取远端侧，`git hash-object` 取本地侧）：

```bash
# 本地（要推的 commit 里的文件）blob sha
git ls-tree <commit> -- <path>
# 工作区文件 blob sha
git hash-object <path>
```
不一致就**先查清**再推，不要"看起来一样"就放过。

---

## 2. 用 Git Data API 更新远端分支 ⇒ CI 不会自动看到新 commit

**现象**：远端分支被更新了，但 CI 没跑（或跑了旧 commit）。

**根因**：Git Data API 改的是**分支引用**，不会产生 PR 事件；CI 的触发条件是
PR 事件（push 到 PR 分支也可能不触发重新构建）。

**机制**：
- 触发 PR 事件 ⇒ **重建分支最可靠**（删远端分支后重新推，让 PR 重新开）；
- ⚠️ **`rerun` 不行** —— 它重跑的是**旧 commit**，不是新代码；
- 所以：**改远端分支后，先确认 CI 跑的是哪个 sha**（看 CI 页面的 commit 标识），
  再判断"绿/红"。

---

## 3. 验证要跑「CI 的全部步骤」，而不是逐项列举

**现象**：本地逐项验证都过了，CI 却红 —— 漏了 `format:check` 这一步。

**根因**：**逐项列举必漏**（谁记得 CI 有几大步？换了 CI 配置还会漏新的）。

**机制**：**以 CI 的配置为准** —— 直接读 workflow 文件列出全部步骤，逐条在本地跑：

```bash
ls .github/workflows/ && grep -n "run:" .github/workflows/*.yml   # 列出 CI 的全部执行步骤
```
新增 CI 步骤时，同步更新本地验证清单（而不是靠记忆）。

---

## 4. 共享工作区里「本地绿」不可信 ⇒ 用 `verify-pure-commit.sh`

**现象**：本地 `go test` 全绿 ⇒ CI 红 ⇒ 原因是修复**漏了 `git add`**，
commit 里跑的还是旧版用例；共享工作区的未提交改动（别人的并行编辑 +
目录级 gofmt 的副作用）同样会污染本地结果。

**根因**：本地工作区 ≠ commit 内容；且工作区里混着多方未提交改动。

**机制**：**凡是要进 PR 的提交，推送前用独立 worktree 检出该 commit 跑一遍目标测试**：

```bash
scripts/devtools/verify-pure-commit.sh                    # 验证 HEAD，默认三包
scripts/devtools/verify-pure-commit.sh <commit>           # 验证指定 commit
scripts/devtools/verify-pure-commit.sh <commit> ./pkg/... # 指定包
```
脚本做三件事：`git worktree add --detach` 检出目标 commit 到临时目录 → 在其中跑 `go test`
→ **trap EXIT 无论成败都清理** worktree + prune。
⚠️ **不碰共享工作区**；⚠️ **不用 `git worktree remove --force`**（共享仓库安全网会拦，
正常路径 worktree 干净，无需 --force）。

### 4.1 配套：提交后核对 commit 里的**实际内容**

工作区是绿的**不代表 commit 是绿的** ⇒ 改完测试/代码后，用 commit 视角复核：

```bash
git show <commit>:<path> | grep -n "<你改的那一行>"
```
⚠️ 今天正是靠这一步定位到「工作区已改成 untagged，commit 里还是带 tagged 的旧版」。

---

## 5. 绝不目录级 `gofmt -w <dir>`（共享工作区会波及他人）

**现象**：在共享工作区里跑 `gofmt -w internal/services/portcollection/`，
**目录内所有** .go 文件都被格式化 —— 波及 14 个我没碰过的文件
（今天两次：23 个 + 14 个），把无关改动留在共享工作区里，增加他人负担。

**根因**：目录级格式化在**独占仓库**里安全，在**共享工作区**里天然会波及他人 ——
不是"没记住"，是**工具用法与工作区形态不匹配**。

**机制**：
- **只对自己的文件跑 gofmt**（明确列出文件路径，不用目录通配）；
- 更稳：**提交前用 `gofmt -l <自己的文件列表>` 只检查不写**（不修改任何文件）；
- 若确需格式化他人文件 ⇒ **不要做**，交由文件属主处理。

---

## 6. 工作区里有他人未提交改动时：不擅自 revert、不代为提交

**现象**：发现一批未提交改动（别人的并行编辑），本能反应是"revert 掉恢复原状"。

**根因**：共享工作区多方同时在改 ⇒ 你看到的"未提交改动"可能**正在被编辑**；
revert 会**覆盖别人的工作**（不可逆）。

**机制**：
- **不 revert、不代为提交** —— 保持原状并**告知**（本次即如此处理：逐字节复核证明是
  纯格式化副作用后交由 lead 在无并行编辑时统一收口）；
- 复核「这批改动是谁的」用**决定性证据**，不要靠推断：
  ```bash
  # 差异是否 100% 由某个工具造成：工作区版本 == HEAD 版本经该工具处理后的结果
  git show HEAD:<file> | gofmt | diff -q - <file>
  ```
  （今天用这条一次判定 14/14 纯格式化、零语义改动）；
- 精确推送（只取指定 commit 的文件）⇒ 未提交改动**不会**被带进 PR ✅
  （但合并前仍应再查一次工作区状态）。

---

## 9. 断言命令形态必须用完整精确串

**现象**：同一个项目里**两次**因子串断言失配：

1. `assert.NotContains(t, joined, "tagged")` —— 「untagged」本身含「tagged」子串 ⇒ **误报**（把「应该拒绝」的用例报成失败）；
2. `assert.Contains(t, joined, "switchport trunk allowed vlan 10,20")` —— 中间插入了 `only` ⇒ **子串不匹配** ⇒ 旧断言与新实现不匹配，但看不出是哪里变了（测试失败时若继续改代码而不是改断言，就会改错）。

**根因**：子串断言把「包含」当成「等于」用 ⇒ 命令形态**增加了关键字**（如 only）或**包含了其他字段**（如 untagged 含 tagged）时就会失配。

**机制**：
- **断言命令形态用完整精确串（含关键字与顺序）**：
  - 优先 `assert.Equal(t, []string{...}, got)` 整组比较（最严格，顺序也能锁）；
  - 次选 `assert.Contains(t, joined, "switchport trunk allowed vlan only 10,20")` 精确形态；
  - **禁止** `"allowed vlan 10,20"` / `"tagged"` 这类**省了关键字或不含关键字的子串**。
- 断言**正向**反映新行为、**逆向**反映旧行为 —— 两种失配都是错。
- 新增或修改命令形态的渲染时，**必须同时断言三种模式**（replace / add / remove），
  否则会留下「某个模式从未被断言」的空隙 —— **P0 的真正根因**
  （本轮锐捷 replace 就是因为「replace 形态从未被任何测试断言」而静静漏到真机）。

## 10. 防御性分支必须有其自身的直达测试

**现象**：某段防御代码长期不被执行 —— 因为**另一条路径会先拦住它**：

`CheckActionSupport` 只走 `lookupSupport`（判定「支持/不支持」），
而 `SupportEvidence` 的厂商级分支是**另一条路径**（「**为什么**拒绝」的文案来源）
⇒ 写路径上矩阵先拦截 ⇒ 该分支**从未被执行** ⇒ 那段代码会**无条件老化**。

**根因**：把「上游会拦住」当成了覆盖 ⇒ 但覆盖是**副作用**，不是**契约** ——
上游的拦截逻辑一改（或新增一条调用路径），这段防御分支就会静默失守。

**机制**：
- 凡是为**兜底/防御**而写的分支，**必须有直调该路径的测试**（直接调那个函数），
  **不能依赖上游拦截来「顺便覆盖」**；
- 直调测试要断言**该分支自己的语义**（错误类型 + 文案要点），而不只是「不报错」——
  否则测的是上游，不是这段代码；
- 判断某分支是否真的被覆盖：**看 diff coverage 报出的 UNCOVERED 行**（PR 门禁会指出来），
  而不是「这个函数有人调过」；
- 同理适用于**错误分类**：写路径与直调路径的**错误类型/文案必须一致**，
  否则用户从不同入口得到不同结论（例：矩阵先拦截时文案正确，
  直调渲染层却返回「不支持的厂商」⇒ 两条路径行为不一致）。

## 8. 结论不得跨型号外推

**现象：**同一厂商、不同型号的真机行为可以差很大（华为 **S8700** 的 `port ?`
**无** trunk/hybrid 子命令，而 **CE/S57** 系列常见有；锐捷 **RS8607E** 与 **RG8607E** 已实测形态一致）。

**根因：**“某型号不支持 X”是**型号级**结论；拿它去否定其他型号，就是把推测写成了事实。

**机制：**
- 能力矩阵的拒绝理由必须**带型号**（如「S8700 接口视图 port ? 无 trunk 子命令」），
  不得写成厂商级推断；
- 取证记录、能力矩阵注释、取证报告三处都带型号；
- 新型号要启用已有结论时，先确认关键字形态**一致**（锐捷 RS8607E ↔ RG8607E 就是这种情况），
  并把这一点写进矩阵注释（不要只在测试里看见）。

## 11. 写操作「返回 2xx」不等于「操作生效」⇒ 必须回读验证

**现象（2026-11-03 实测）**：用 `PATCH /repos/{o}/{r}/pulls/{n}` 传 `head` 字段想把 PR
切到新分支 ⇒ API 返回 **HTTP 200**，但**该字段被静默忽略** ⇒ PR 的 head 分支**纹丝不动**。

**根因：** GitHub 对部分字段「**接受但忽略**」—— HTTP 200 只说明**请求被受理**，
不说明**状态已改变**。若工具把 200 当成功，就会进入「报成功、其实没做」的循环，
最坏情况是**空等一整轮 CI**（本次白等约 90 分钟）。

**机制：**
- 任何**写操作**之后，凡是「后续步骤依赖这个写生效」的，都必须**回读校验**：
  读回真实状态并断言等于期望值，不符则**以非 0 退出码失败**（fail-closed）；
- 工具的输出必须区分「请求被受理」与「状态已改变」两种语义
  （对应本机偏好：工具面向 AI agent 设计 ⇒ **语义化退出码 + 不静默放过**）；
- 这与第 10 条同源：**覆盖是副作用不是契约** ⇒ **2xx 是副作用不是契约**，
  真正的契约是「回读到的状态符合预期」；
- 已落地：`scripts/devtools/gh/pr-retrigger.cjs` 在切 head 后**回读 PR 并断言**，
  不符即 `exit 1` 并打印两条替代路径（新建 PR / 推到 PR 原有 head 分支）。

⚠️ 与「能力规则的存废必须与其所依据的前提绑定」同源：
**前提（型号、设备行为）变了，规则就要重新评估，不能把「拒绝」或「支持」固化为安全默认值。**
