# UI 走查清单（v1.56 W7 起强制）

> **一句话**：日志通 ≠ 功能可用。每一条都必须回答「用户**看到了什么**、**点了什么**、**之后变成了什么**」。
> 判定 PASS 的唯一依据是**浏览器里能观察到的变化**；API 200 / DB 有行 / 日志有输出只能作为**附证**，不能单独构成 PASS。

## 0. 通用前置（每次走查都做一遍）

| # | 动作 | 判定 |
|---|---|---|
| 0.1 | 用**非超管账号**登录（超管会掩盖权限/数据范围类缺陷） | 登录后右上角显示的是该账号的 nickname |
| 0.2 | 打开 DevTools → Console 清空 | 走查全程不允许出现未处理的红色报错 |
| 0.3 | Network 面板过滤 `fetch/XHR` | 每个操作都能对应到明确的请求，且状态码与预期一致 |
| 0.4 | 记录当前 URL | 跳转类走查要用它断言「落地路由」 |
| 0.5 | 若页面有长连接（WS/SSE）→ Network → WS 标签页可见 | 不是「以为连上了」而是能看到帧 |

## 1. 每个新页面：进入 → 可点 → 有变化

| # | 步骤 | 必须观察到 | 常见假 PASS |
|---|---|---|---|
| 1.1 | 从**菜单**点进来 | 页面标题/面包屑与菜单名一致 | 直接手敲 URL 进（掩盖了路由/菜单授权问题） |
| 1.2 | 清点关键按钮 | 至少 1 个主操作按钮**可见且未 disabled** | 按钮存在但 `pointer-events:none` / 被遮罩盖住 |
| 1.3 | 点主操作按钮 | 出现**可视化反馈**：弹窗 / Toast / 列表新增一行 / 按钮 loading | 只看到 Network 200 但界面毫无变化 |
| 1.4 | 取消/关闭该反馈 | 界面回到原状，无残留遮罩层 | 遮罩残留导致后续点击全失效 |
| 1.5 | 刷新页面 | 步骤 1.3 产生的结果**仍在**（落库而非仅内存） | 刷新后消失 = 只改了前端 state |
| 1.6 | 空数据态 | 显示中文空态提示，不是白屏/转圈不动 | 一直转圈（请求未 settle） |

## 2. 跳转类：断言**落地路由**（不是「点了没报错」）

> W7 缺陷 1 的原形：向导页「返回任务列表」写死 `/operations/rpa/tasks` —— 该路径不存在，
> SPA catch-all 把它甩到 dashboard。**用户看到的是仪表盘**，而日志/接口全程无异常。

| # | 步骤 | 必须观察到 |
|---|---|---|
| 2.1 | 点返回/跳转按钮 | 地址栏**立即**变为目标路由（`/vdi/rpa` 这类真实路由，不是 `/operations/...` 这种猜测路径） |
| 2.2 | 核对落地页身份 | 落地页标题/面包屑/表格列 = 目标页，**不是 dashboard、不是空白页** |
| 2.3 | 点浏览器后退 | 回到来源页（说明是真导航，不是被 catch-all 吞掉后重定向） |
| 2.4 | 在目标页再点一次入口 | 往返 2 次都稳定（防止一次性的初始化时序掩盖问题） |
| 2.5 | 源码侧核对 | 该路由必须来自 sys_menu seed 推导出的真实路径；**不允许手写第二份路径字符串** |

**判定红线**：只要落地页是 dashboard / 首页 / 白屏，一律 **FAIL**，无论接口返回什么。

## 3. 状态类：接管 / 释放 / 模式切换 —— 断言**UI 与后端同步变化**

> W7 缺陷 2 的原形：点「接管」→ 角标显示「已接管 · ninedrunk」，但**遮罩仍在**、鼠标点不动。
> 因为后端按 username 记接管者、前端按 nickname 判「我是不是接管者」，两边口径不同。

| # | 步骤 | 必须观察到 | 反面（真实发生过的假 PASS） |
|---|---|---|---|
| 3.1 | 初始态 | 有遮罩 + 角标「自动执行」+ 按钮「接管」 | —— |
| 3.2 | 点「接管」并二次确认 | 遮罩**消失** + 角标变「已接管 · <名>」+ 按钮变「释放接管」 | 角标变了但遮罩还在（判定口径不一致） |
| 3.3 | 移动鼠标 / 点击画面 | 远端页面**真的有反应**（点击计数器 +1 / 输入框出现字符） | 只有前端本地动画，远端没变 |
| 3.4 | Network 里看 input 请求 | `POST .../liveview/input` 全部 2xx | 403（说明前端以为自己是接管者，后端不认） |
| 3.5 | 点「释放接管」 | 遮罩**重新出现** + 角标回「自动执行」+ 按钮回「接管」 | 释放了但遮罩不回来（歧义态） |
| 3.6 | 换另一个账号（或被踢）看同一执行 | 遮罩存在 + 角标显示**对方**名字 + 自己没有「释放接管」 | 别人接管时自己还能操作（权限穿透） |
| 3.7 | 两个账号昵称≠账号名时重跑 3.2~3.6 | 结果完全相同 | 只在「昵称恰好等于账号名」的账号上通过 = 口径脆弱的证明 |

**判定红线**：角标与遮罩**必须同时**变化。只变角标 = FAIL；只变遮罩 = FAIL。

## 4. 流类：开流 → 断言**至少收到 1 帧**

> W7 缺陷 3 的原形：页面一直「等待画面显示中」，帧从未到达。
> worker 日志：`Page.startScreencast 失败: context deadline exceeded`。
> 原因是池内 page 闲置超过创建期 Timeout，ctx 早已过期。**标签写「推流中」完全不代表有帧**。

| # | 步骤 | 必须观察到 | 常见假 PASS |
|---|---|---|---|
| 4.1 | 打开实时画面 | 画面**真的出现内容**（能看到远端页面的像素，不是纯黑/纯灰/loading） | 只看到「推流中」标签就收工 |
| 4.2 | 看帧率小字 | fps > 0 且带宽 > 0 | 0 fps / 0 Mbps 说明一帧都没有 |
| 4.3 | 让远端页面**变动**（滚动/输入） | 画面随之变化（说明是真实流不是首帧定格） | 只有第一张静图 |
| 4.4 | 离开页面 90 秒以上再回来 | 重新出帧（证明 page 复用/闲置不会致死） | 第二次进就永远「等待画面…」 |
| 4.5 | 连续开关 3 次 | 每次都能出帧 | 第一次好后面前几次都不行 |
| 4.6 | worker 日志 | 无 `startScreencast 失败` / `context deadline exceeded` | 只在 UI 看标签、不看服务端 |

**判定红线**：**「收到至少 1 帧」**是唯一 PASS 条件。标签、日志、接口 200 都不算。

## 6. 反模式（明确禁止的「假验收」）

| 反模式 | 为什么不行 |
|---|---|
| 「接口 200 所以功能好了」 | 200 只能证明请求到达，不能证明 UI 消费了响应 |
| 「PG 有数据所以保存成功」 | 可能是别的路径写进去的；用户可能看不到 |
| 「日志有记录所以执行了」 | 日志是服务端视角，用户可能看到一个错误弹窗 |
| 「单元测试全绿」 | W7 三条缺陷全部**单测绿灯**（因为测试用的是刚创建的 page、刚登录的账号） |
| 「我在 dev 环境用 curl 测了」 | curl 不做前端解包、不做权限门控、不渲染遮罩 |
| 「点了没报错就是成功」 | 静默失败（跳到 dashboard、遮罩不消失）恰恰**没有任何报错** |
