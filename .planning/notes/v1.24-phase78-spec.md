| 病灶 | 位置 | 后果 | 只修前端的后果 |

## 1. 后端设计

### 1.1 新增严格权限中间件（pkg/middleware/permission.go）

```go
// RequireStrictPermissions 要求命中指定权限之一，且**不做任何权限降级**。
//
// 与 RequirePermissions 的差异（关键）：
//   - RequirePermissions：精确匹配 → F 型子权限继承（Step 2）→ 模块级降级（Step 3）
//   - RequireStrictPermissions：仅精确匹配（Step 1）
//
// 用途：写操作（create/update/delete/batch/reset）必须严格，
// 否则只读角色会因「持有页面本体权限」而被 Step 3 放行。
// 超管 bypass 与 30s TTL 缓存沿用现有实现，不新增语义。
func RequireStrictPermissions(permissions []string, core *core.Core) gin.HandlerFunc {
	return func(c *gin.Context) {
		userID, ok := getUserIDAsString(c)
		if !ok {
			response.Error(c, response.ErrUnauthorized, "用户未认证")
			c.Abort()
			return
		}
		// 超级管理员直接通过（沿用 isSuperAdmin）
		if isSuperAdmin(core, userID) {
			c.Next()
			return
		}
		for _, permission := range permissions {
			if checkUserPermissionStrict(core, userID, permission) {
				c.Next()
				return
			}
		}
		response.Error(c, response.ErrForbidden, "没有访问权限")
		c.Abort()
	}
}
```

配套的严格检查（**只做 Step 1 精确匹配**）：

```go
// checkUserPermissionStrict 仅做精确匹配（sys_menu.perms = ?），
// 不做 F 型子权限继承、不做模块级降级。
func checkUserPermissionStrict(core *core.Core, userID, permission string) bool {
	cacheKey := "strict|" + userID + "|" + permission
	if allow, hit := mwCacheLookup(&mwPermCheckCache, cacheKey); hit {
		return allow
	}
	var count int64
	err := core.DB.GetDB().Raw(`
		SELECT COUNT(DISTINCT rm.menu_id)
		FROM sys_user_role ur
		INNER JOIN sys_role_menu rm ON ur.role_id = rm.role_id
		INNER JOIN sys_menu m ON rm.menu_id = m.id
		WHERE ur.user_id = ? AND m.perms = ? AND m.status = ?
	`, userID, permission, models.MenuStatusNormal).Scan(&count).Error
	allow := err == nil && count > 0
	mwCacheStore(&mwPermCheckCache, cacheKey, allow)
	return allow
}
```

**约束**：
- **不得**改动现有 `checkUserPermission` / `RequirePermissions` 的行为（v1.19/v1.20 冻结面 + 39 处路由组在用）
- 缓存 key 加 `strict|` 前缀避免与既有 key 冲突
- 30s TTL 语义沿用（`mwPermCacheTTL`），**不新增**失效逻辑（`InvalidateMiddlewarePermCache` 未接线是已知债，不在本 phase）
- 超管 bypass 沿用 `isSuperAdmin`（`role_key='admin'`）

### 1.2 `/system/users` 路由拆分（internal/api/router.go:157-162）

现状（ANY-of 组）：

```go
users.Use(middleware.RequirePermissionsWithQuery([]string{
    string(permission.UserList), string(permission.UserAdd),
    string(permission.UserEdit), string(permission.UserView),
}, []string{"ops:workstation:list", "ops:building:spaces:list"}, core))
```

改为**读组 + 写子组**（写操作用严格中间件 + 单一权限点）：

```go
users.Use(middleware.RequirePermissionsWithQuery([]string{
    string(permission.UserList), string(permission.UserView),
}, []string{"ops:workstation:list", "ops:building:spaces:list"}, core))

// 写操作：独立子组 + 严格权限（不做模块级降级）
usersWrite := users.Group("")
usersWrite.Use(middleware.RequireStrictPermissions([]string{string(permission.UserAdd)}, core))
usersWrite.POST("", handler.Create)
usersWrite.POST("/import", handler.ImportUser)
usersWrite.POST("/:id/update", handler.Update)
usersWrite.POST("/:id/delete", handler.Delete)
usersWrite.POST("/:id/status", handler.UpdateStatus)
usersWrite.POST("/:id/reset-password", handler.ResetPassword)
usersWrite.POST("/batch-delete", handler.BatchDelete)
```

**逐动作权限映射**（用 `pkg/permission/config.go` 已定义但从未被引用的常量）：

| 动作 | 权限点 | 常量 |
|---|---|---|
| 新增 | `system:user:add` | `permission.UserAdd` |
| 编辑 | `system:user:edit` | `permission.UserEdit` |
| 删除 / 批量删除 | `system:user:remove` | `permission.UserRemove`（已定义未引用） |
| 重置密码 | `system:user:resetPwd` | `permission.UserResetPwd`（若已定义；若没有则先在 config.go 补常量，命名与 `sys_menu.perms` 完全一致） |
| 导入 | `system:user:import` | `permission.UserImport`（同上处理） |

⚠️ **兼容风险（必须在返回中说明并给处置建议）**：
- `xtgl`（系统管理）角色**没有 `system:user:export`** → export 接口**不加保护**（或另立条目），否则 xtgl 点导出会 403
- 任何「有 `system:user` 页面权限但无对应 F 权限」的历史角色 → 升级后写操作 403（**这是预期的正确行为**，但需在返回中列出受影响角色清单）
- 超管 `admin` → bypass，不受影响

**同源债登记（不在本 phase 修）**：`roles` / `menus` / `depts` / `posts` 4 个组同样是 ANY-of → 登记为 v1.25 债，并在返回中列出各自的写操作路由清单。

### 2.2 三态门控 helper（PERM-02）

新建 `src/components/shared/useActionPermission.ts`：

```ts
export type PermissionGateState = "ready" | "loading" | "error";

export interface ActionPermissionResult {
  /** 三态：权限集是否已就绪 */
  state: PermissionGateState;
  /** 就绪且含该权限码 → true */
  allowed: (perm?: string) => boolean;
  /** 未就绪时的提示文案（用于 disabled + title/aria） */
  notReadyHint?: string;
}
```

判定规则（**三态，不可简化**）：

| state | 条件 | 渲染行为 |
|---|---|---|
| `loading` | 权限集尚未加载完成（显式 loading 位） | 渲染按钮但 **disabled** + `title`/`aria-label` 提示 |
| `error` | 权限接口失败 | 渲染按钮但 **disabled** + 提示 |
| `ready` | 权限集已加载 | 含权限码 → 可用；不含 → **不渲染** |

⚠️ **禁止**用 `permissions.length === 0` 判「未就绪」——空权限集与未加载完在数据上不可区分，会导致接口失败时管理员也看不到按钮且无提示。

权限数据源：`useMenuStore((s) => s.permissions)` + `useMenuStore` 的 loading/error 位（需核对 store 是否有显式位；若无，**新增**显式 `permissionsLoaded` / `permissionsError` 位并在 `menuStore.ts` 的 `fetchAll` 里维护）。
