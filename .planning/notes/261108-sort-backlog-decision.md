**本 Phase 决策：3 处均不改动服务端排序契约**（服务端排序契约零回归）。原因：
三处都已有清晰、无争议的默认排序，且 menus/depts 的 `order_num ASC` 是全项目统一惯例
（migration_228 已注册 4 页面排序菜单，改动会波及前端已消费的顺序）。擅自新增排序规则
属于定义产品行为，超出本 REQ 授权范围。文档把可选方案与待确认问题清单留档，供产品拍板后
另立 REQ 落地。

## 1. 我的值班统计

### 现状
- `internal/services/duty_stats_service.go:79`：统计查询 `Order("schedule_date ASC")`（按排班日期升序）。
- 这是按时间轴呈现统计数据的自然顺序，前端「我的值班统计」页消费该顺序。

### 可选方案
- **方案 A（推荐）**：保持 `schedule_date ASC` 不变，不做产品规则变更。理由：时间升序是值班统计
  最不易产生歧义的顺序；新增排序维度（如按值班类型/时长聚合）属于新功能，不是「排序收尾」。
- 方案 B：增加 `orderBy` 请求参数，允许前端在 `schedule_date ASC/DESC` 间切换。影响：需改
  service 入参 + handler 绑定 + 前端表格，且要定义默认与非法值兜底。
- 方案 C：按「值班池/班次」分组后再按日期排序（分组聚合）。影响：改变返回数据结构，是较大
  功能变更，非排序问题。

### 推荐方案 + 理由
**方案 A**。已有明确默认且与前端消费方式一致；改动收益低、回归面大。

### 对现有服务端排序契约的影响
零（不改代码）。若未来采纳方案 B/C，需在 service 层新增白名单校验（防 SQL 注入），
并同步前端包装 API 函数入参。

### 需产品确认的问题清单
1. 「我的值班统计」是否需要用户可切换的排序（时间倒序/正序）？还是固定时间升序即可？
2. 是否需要「按值班类型/班次」分组聚合？若是，属于新功能而非排序收尾。
3. 统计列表是否需要与「值班池成员 order」联动？（当前不联动，成员顺序仅用于 FIX-05 轮询分配。）

## 2. 节假日排序

### 现状
- `internal/services/duty_holiday_service.go:41`：节假日明细 `Order("holiday_date ASC")`（日期升序）。
- `:78`：年份下拉列表 `sort.Sort(sort.Reverse(sort.IntSlice(years)))`（年份**倒序**，最新年份在前）。
- 两处排序语义不同但各自合理：明细按时间升序，年份选择器按「最近优先」倒序。

### 可选方案
- **方案 A（推荐）**：保持「明细日期升序 + 年份倒序」组合不变，显式在文档中固化该契约。
- 方案 B：年份选择器也改升序（`years` 正序）。影响：下拉默认聚焦最旧年份，运维选当年需滚动。
- 方案 C：两处都提供 `orderBy` 参数由前端控制。影响：同 #1 方案 B，扩大契约面。

### 推荐方案 + 理由
**方案 A**。年份倒序是「选最近年份」的常见 UX，明细日期升序符合日历阅读习惯；两者不矛盾。
擅自统一为升序反而降低可用性。

### 对现有服务端排序契约的影响
零（不改代码）。注意：年份倒序在 service 层用 `sort.Reverse` 完成，非 DB `ORDER BY`，
不受「服务端排序契约」迁移影响。

### 需产品确认的问题清单
1. 年份选择器「最新在前」是否符合产品预期？（当前实现是倒序）
2. 节假日明细是否需要按「节假日类型」（法定/调休/自定义）分组排序？
3. 跨年查询时，明细是否要按「年 → 月 → 日」分段展示，还是纯 `holiday_date` 平铺？

## 3. 菜单 / 部门树形排序

### 现状
- 菜单：`internal/services/system/menu_service.go` 6 处 + `menu_cache_impl.go` 2 处，
  全部 `Order("order_num ASC")`。
- 部门树：项目惯例同样是 `order_num ASC`（与菜单同一套 `BaseModel`/排序约定，
  migration_228 注册的 4 页面排序菜单即消费该顺序）。
- `order_num`（同级序号，升序）已是全项目树形排序的**无争议默认惯例**。

### 可选方案
- **方案 A（推荐 / 等价于最小实现）**：保持 `order_num ASC`，不改代码，本 Phase 以「结论文档
  固化惯例」作为最小落地。理由：这是项目既有惯例，改动会波及全部已注册菜单与部门树消费方，
  且 migration_228 刚落地 4 页面排序菜单，回归风险高。
- 方案 B：增加同级拖拽排序（前端 drag & drop + 批量更新 `order_num`）。影响：需新端点、
  operlog、批量事务、并发冲突处理 —— 是一个完整功能，不是「排序收尾」。
- 方案 C：允许 `order_num` 相同时按 `created_at`/`name` 次级排序。影响：需给所有 `Order` 调用
  加第二排序键，属契约细化，需产品定义次级键优先级。

### 推荐方案 + 理由
**方案 A**。`order_num ASC` 已是明确惯例，符合 REQ「若某处已有明确无争议的默认，可以落地
最小实现并说明」的授权 —— 这里「最小实现」即**不改动 + 书面固化**，避免任何服务端排序契约回归。

### 对现有服务端排序契约的影响
零（不改代码）。若采纳方案 B/C，必须同步评估 `menu_cache_impl.go` 缓存失效顺序、
部门树前端递归渲染、以及 migration_228 注册菜单的既有 `order_num` 值。

### 需产品确认的问题清单
1. 同级节点是否需要管理员「拖拽自定义顺序」？（=方案 B，需独立 REQ 与工作量评估）
2. `order_num` 相同时的次级排序键是什么（当前依赖 DB 返回顺序，未显式定义）？
3. 菜单可见性（`visible 1=可见`）与树形排序是否要联动（隐藏项是否占位）？
