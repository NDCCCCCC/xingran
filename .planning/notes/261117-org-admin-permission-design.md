# 机构管理员权限方案设计（纯设计，不含开发）

> 触发问题：为每个机构设置管理员时，`数据范围` 无法满足要求，必须「每个机构建一个角色」；
> 无法做到「建一个角色，人员属于哪个机构就拥有哪个机构的管理员权限」。
> 选「本部门及下级部门」也不行：武汉中支的刘洋属于**综合管理部**，他要当**武汉中支**的管理员。
>
> 本文只做方案设计与取舍论证，不改任何代码。
> 关联 tree：`tree-11ec71374c7c2743`

---

## 一、结论先行

**根因不是"数据范围选项太少"，而是"可见集的锚点被硬编码成了用户自己的 `dept_id`"。**

现有 5 个数据范围档位，锚点只有两种：
- `All(1)` —— 无锚点（全库）
- `Self(5)` —— 锚点 = 用户本人
- `Custom(2)` —— 锚点 = 角色上**手工勾死**的部门清单（`sys_role_dept`）
- `Dept(3)` / `DeptChild(4)` —— 锚点 = **用户自己的 `sys_user.dept_id`**

角色是**全局共享、跨机构复用**的对象，而"机构"是**每个用户各不相同**的属性。
一个共享角色 + 一个与用户绑死的锚点 ⇒ 想让刘洋管武汉中支，只能让整个角色都管武汉中支 ⇒ 只好每个机构建一个角色。这就是死结。

**推荐方案（三层，逐层可选）：**

| 层 | 做法 | 解决什么 | 是否必须 |
|---|---|---|---|
| **L1 机构锚点层** | 可见集锚点从「用户 `dept_id`」改为「**用户所属机构**」（复用已有的 `OrgOf` 语义：沿 `ancestors` 由近到远命中 `sys_manager_org` / 或改用独立 `org_scope` 字段），再用现有 `queryDeptChildIDs` 展开 | 一个「机构管理员」角色即可覆盖**所有**机构；刘洋因属武汉中支 → 自动获得武汉中支子树 | **必须** |
| **L2 岗位维度** | 给 `sys_post` 加 `org_scope`（0=不参与 / 1=本机构及下级），被授予该岗位即获得该机构维度授权 | 授权动作从"分角色"下沉为"加岗位"；岗位全局唯一 ⇒ 一个「中支管理员」岗位覆盖所有中支，天然是**跨机构授权模板**；一人多岗位天然支持兼任 | **建议**（并补前端岗位分配界面） |
| **L3 显式机构授权（可选）** | `sys_user_org_scope(user_id, org_id/dept_id, include_child, expire_at)` | 解决 L1 覆盖不到的场景：任职部门**不在**目标机构子树内（省公司派驻）、**跨机构兼任**、**临时代理/带有效期** | 可选扩展 |

**关键工程约束（见 §六，务必遵守）：L1 的机构维度绝不能塞进现有的 `MAX(r.data_scope)` 排序。** 现有 `getUserMaxDataScope` 取数值最大值，而 `6 > 1`；若新增枚举 `6`，一个同时持有 `All(1)` 角色的用户会被收窄成机构范围 —— 这是静默降权事故。因此机构维度必须作为**独立维度**解析后与角色维度取**并集**（宽者胜），而不是参与 MAX 排序。

## 三、缺口根因：三层错配

1. **粒度错配**：`DeptChild(4)` 的锚点是"用户所在的部门"，而需要的是"用户所属的**机构**"。
   刘洋的 `dept_id` = 综合管理部，`ancestors` = `…,武汉中支,…`。
   `DeptChild` 只会给他 `综合管理部 + 其下级`，永远不含武汉中支的其他部门。
   而"综合管理部"几乎必然**没有下级部门**，所以这一档对刘洋等于只看得见自己部门——正是用户描述的"无法满足"。

2. **可变性错配**：角色是共享对象，锚点与用户绑死。
   同一角色分给 10 个中支的管理员，只能取**一个**固定范围（当前唯一办法是 `Custom(2)` 手工挂清单）。
   ⇒ 想覆盖 N 个机构就得有 N 个角色（× 菜单权限复制 N 份），角色表迅速不可维护，且机构调整（新设/合并/撤销）时**必须人工逐个重配**。

3. **表达力错配**：`Custom(2)` 是"静态列出部门"，缺两层能力——
   - **动态锚定**（"我在哪个机构就管哪个机构"）
   - **子树展开**（`Custom(2)` 不展开，必须把每个子部门逐个勾上）

## 四、岗位功能的深度分析：为什么它是正确的切入点

系统里三个对象的分工现状是这样的：

| 对象 | 现在承担 | 缺什么 |
|---|---|---|
| 角色 `sys_role` | **功能权限**（菜单/按钮，`sys_role_menu`）+ 一个静态数据范围档 | 缺"按机构动态锚定"的能力 |
| 部门 `sys_dept` | 组织树、人员归属（`sys_user.dept_id`）、`ancestors` 物化路径 | 没有"机构"层级语义（`is_external_org` 只是弱标记） |
| 岗位 `sys_post` | 全局扁平字典；经理规则里作 `org_head`/`post_holder` 锚点 | **不参与任何鉴权** |

关键洞察 —— **岗位"没有机构字段"不是缺陷，恰恰是它最适合做跨机构授权模板的原因**：

1. **岗位必须全局唯一，否则就重蹈覆辙。** 若给 `sys_post` 加 `org_id`，就得为每个机构建一个"中支管理员"岗位 —— 完全复刻"每机构一角色"的病。反过来，保持岗位无机构字段，用**任职人所属机构**做动态锚点（这次正好复用 `OrgOf`），一个岗位即可覆盖全部机构。

2. **多对多天然支持兼任。** `sys_user_post` 一人多岗：刘洋可以同时是「武汉中支机构管理员」和「综合管理部部门管理员」，两个维度各产出一段可见集，取并集即可。角色体系做不到这点（角色多档位只能取 MAX，很别扭）。

3. **系统里已经有"岗位 × 机构"的成功先例，可以对齐语义。** `manager_rule_service.go:697-732` 的 `pickPostHolder(postID, targetOrgID)` 已经在回答"**在某个机构内，谁是某岗位的任职人**"；`OrgOf` 已经在回答"**这个用户属于哪个机构**"。权限侧若沿用同一套解析，就能保证"谁是武汉中支的管理员"在**经理同步**和**权限判定**里给出同一个答案 —— 避免两套口径打架。

4. **零语义包袱。** 岗位当前完全不参与鉴权，扩展它不会与任何既有授权语义冲突（这是稀有优势）。

5. **可审计。** "谁是哪个机构的管理员"变成一张可查询的任职列表（`sys_post ⋈ sys_user_post ⋈ 机构`），比"N 个角色散落在角色表里"清楚得多，也天然能支撑日后"机构管理员上送/审批"。

**代价（必须一并解决）：** 前端没有岗位分配界面（`user/index.tsx` 只写 `title` 文本）。不做这一步，L2 层等于空转。

## 五、推荐方案详细设计

### 5.1 总体结构

```
             ┌──────────── 角色维度（保持原样，零回归）────────────┐
sys_user ──▶ │ sys_user_role → MAX(data_scope) → datascope.Resolve │──┐
             └──────────────────────────────────────────────────────┘  │
                                                                        ├─▶ 合并规则
             ┌──────────── 机构维度（新增，独立解析）────────────────┐  │   (并集，宽者胜，
sys_user ──▶ │ 来源A：角色 org_scope=1                            │──┤    All 优先，
             │ 来源B：岗位 sys_post.org_scope=1（sys_user_post）   │  │    全空则 fail-closed)
             │ 来源C：sys_user_org_scope 显式授权（可选）           │  │
             │   ↓ 锚点 = OrgOf(user) 的 dept_id                    │  │
             │   ↓ 展开 = 复用 queryDeptChildIDs(anchor)            │  │
             └──────────────────────────────────────────────────────┘  │
                                                                        ▼
                                                     ScopeResult{All, DeptIDs, Hook, FailClosed}
                                                     → 注入 request ctx → 各域挂 SQL（已有机制）
```

**核心改动只有一句：机构维度把 `queryDeptChildIDs` 的入参从「`sys_user.dept_id`」换成「`OrgOf(user).dept_id`」。** 其余展开逻辑、`ScopeResult` 结构、`ScopedDB` 挂载、各域谓词全部复用。

### 5.2 为什么**不改** `DataScope` 枚举为 `6`（关键取舍）

直觉做法是"加一个下拉项「本机构及下级机构」= 6"。**不可行**，因为：

- `getUserMaxDataScope` 用 `MAX(r.data_scope)`（`pkg/middleware/permission.go:547-552`），语义是"数值越大越窄"。
- 现有 `All=1`、`Self=5`。新增 `6` 后，**同时持有 `All(1)` 与其他（6）的用户**的 MAX 会变成 `6` ⇒ 从"全库"静默降为"某机构子树"。虽然不越权，但会直接打断既有超管/全局角色用户，属于隐形的破坏性变更。
- 枚举扩位还会波及前端下拉、Swagger 枚举、DTO 校验、异常枚举 fail-closed 分支（`pkg/datascope/datascope.go:172-176`）。

**替代做法（推荐）：`org_scope` 作为独立维度字段，不参与 MAX。**

| 表 | 新增列 | 取值 | 说明 |
|---|---|---|---|
| `sys_role` | `org_scope` | `0`=不参与（默认） / `1`=本机构（含下级机构） | 与 `data_scope` 正交：`data_scope` 管"横向档位"，`org_scope` 管"机构锚点" |
| `sys_post` | `org_scope` | `0`=不参与（默认） / `1`=本机构（含下级机构） | 只允许 0/1，**不允许** All/Custom，避免"岗位授予全库范围"的越权风险 |
| `sys_user_org_scope`（可选，L3） | `user_id, dept_id, include_child, expire_at, remark` | — | 显式授权，支持跨机构/兼任/临时 |

> 若产品上坚持要"下拉里直接看到这个选项"，也可在**前端下拉**里呈现为「本机构及下级机构」，但**后端落库仍写 `org_scope=1` 且 `data_scope` 保持原值**，避免进入 MAX 排序。表里不出现新枚举值，是这次设计的硬约束。

### 5.3 机构锚点解析（唯一新增的解析逻辑）

```
resolveOrgAnchor(userID) -> (deptID string, ok bool):
  1) 取 sys_user.dept_id；为空 -> not ok
  2) 若 dept_id 自身命中 sys_manager_org -> 返回该机构 dept_id
  3) 否则把 sys_dept.ancestors（根→父序）反转，由近到远找第一个命中 sys_manager_org 的节点
  4) 全不命中 -> not ok（**不回退到 dept_id**，见 §7-3）
```

- 这段逻辑与 `manager_rule_service.go:573-593` 的 `OrgOf` **同构**，应抽成共享实现。
- **分层约束**：`pkg/datascope` 不得 import `internal/*`（见 `pkg/query/scoped_registry.go:4-7` 的硬约束）。所以该 SQL 实现要落在 `pkg/datascope`（自带 `sys_user`/`sys_dept`/`sys_manager_org` 三张表的只读查询），或由 `internal` 侧注入 `OrgResolver` 接口回调。推荐前者，保持 `pkg/datascope` 仍是"可见部门集展开的单一真实源"。

**机构子树 = 部门子树（可直接复用，无需递归 `sys_manager_org`）：**
机构节点本身就是 `sys_dept` 上的节点；下级机构的 dept 节点必然落在上级机构 dept 节点的 `ancestors` 子树内。因此
`机构子树部门集 ≡ queryDeptChildIDs(org.dept_id)`。
⇒ 不需要为机构维度写递归 CTE，直接复用 `pkg/datascope/datascope.go:229-245`。
（前提是机构层级与部门层级一致 —— 加一条**一致性校验**，见 §7-5。）

### 5.4 合并规则（唯一的不变量，必须写死并测试）

设：
- `roleScope = datascope.Resolve(userID, MAX(data_scope))`（**现有逻辑，一行不改**）
- `orgGrants = ∪ { queryDeptChildIDs(OrgOf(user).dept_id) | 任一来源启用且锚点命中 }`

合并：

```
1. roleScope.All == true                       -> All（保持超管/全局零回归）
2. effDeptIDs = ∪(roleScope.DeptIDs, orgGrants)
3. effDeptIDs 非空                             -> {DeptIDs: eff, ResourceHook: None}
4. effDeptIDs 为空 且 roleScope.Hook == SelfUser -> {DeptIDs: [], Hook: SelfUser}   // 保持仅本人
5. 其余                                        -> FailClosed（空集，读空/写 403）
```

要点：
- **宽者胜，绝不复用 MAX。** 并集保证"新增机构维度只会放宽、绝不会收窄"，从根上避免 §5.2 的静默降权。
- **fail-closed 优先。** 机构维度全空**不**等于 All；`OrgOf` 未命中时不回退到 `dept_id`（否则会产生"看似生效、范围却错"的静默错误，比显式失败危险得多）。
- **Self 与机构维度的关系**：两者并存时机构维度胜出（`Hook` 置 `None`），因为岗位/角色是显式授予的更大范围。这与"多角色取 MAX 中窄"的旧行为不同，需要单独说明白（见 §9-2 待决策）。

### 5.5 刘洋案例逐条走查

| 步骤 | 结果 |
|---|---|
| 刘洋 `sys_user.dept_id` | 综合管理部 |
| `sys_dept.ancestors` | `…, 武汉中支` |
| `OrgOf(刘洋)` | 由近到远 → 综合管理部未命中 `sys_manager_org` → 命中**武汉中支** ⇒ 机构 = 武汉中支 |
| 分配方式 A（角色） | 「机构管理员」角色 `org_scope=1`；刘洋加此角色 ⇒ 可见集 = `queryDeptChildIDs(武汉中支)` = 武汉中支全部部门 ⇒ **正是需求** |
| 分配方式 B（岗位） | 「中支管理员」岗位 `org_scope=1`；给刘洋加此岗位 ⇒ 同上。同岗位分给长沙中支的老王 ⇒ 他自动得长沙中支，**一个岗位覆盖全国所有中支** |
| 兼任 | 刘洋再加「部门管理员」岗位（另设 `org_scope=0` + `data_scope=4` 的角色），两维度并集 |
| 跨机构（省公司派驻） | 刘洋部门在省公司、不在武汉中支子树 ⇒ `OrgOf` 得省公司 ⇒ 失效 ⇒ 走 L3 `sys_user_org_scope` 显式挂武汉中支 |
| 机构新设/合并 | 机构目录改一次，所有持该岗位/角色的管理员范围**自动跟随**，无需逐个重配角色 |

### 5.6 落地改动面（仅清单，不开发）

后端：
1. `internal/models/role.go` + `internal/models/post.go`：各加 `OrgScope int`（默认 0）。
2. `pkg/datascope/datascope.go`：新增 `OrgAnchorResolver`（`OrgOf` 下沉）；`ScopeResult` 结构**不变**（只多一个构造入口 `ResolveWithOrgGrants`），保证 `scope_filter.go` / `vm_data_scope_filter.go` 零改动。
3. `pkg/middleware/permission.go`：`DataScopePermission` 在 `Resolve` 之后追加机构维度合并（`getUserMaxDataScope` 一字不改）。
4. `internal/services/system/{role_service,post_service}.go` + `internal/models/system/requests/*`：字段透传与校验（岗位只接受 0/1）。
5. 迁移：`migration_2xx_add_org_scope.go`（两列，幂等 `HasColumn/AddColumn`，非阻断）；L3 若采纳再加 `sys_user_org_scope` 建表。
6. 校验：机构层级一致性（`sys_manager_org.parent_org_id` 的 dept 必须落在父机构 dept 的 `ancestors` 链上）。

## 六、备选方案对比

## 七、风险与边界

1. **MAX 陷阱（最高优先）** — 机构维度绝不可入 `MAX(data_scope)`。否则 `All(1)` 用户会因新维度被收窄。方案已用"独立维度 + 并集"规避，需写回归测试锁死。
2. **缓存 key** — `scopeCacheKeyOf` 用 `sha1(排序后 deptIDs)` 派生（`internal/services/operations/scope_filter.go:63-78`）。机构重组会换 key，天然不串数据；但中间件 30s + 菜单 30min 的陈旧窗口需配合 `InvalidateMiddlewarePermCache` 接线。
3. **锚点未命中不得回退** — 用户部门链上没有机构 ⇒ fail-closed 并给前端明确提示"该用户未归属机构，请先配置机构目录"。回退到 `dept_id` 会造成"以为管了全中支、实际只看到自己部门"的静默事故。
4. **一人多机构 / 多来源** — 一律并集；机构越多可见集越大，需注意 `DeptIDs` 规模（中支子树通常几十到几百，`IN ?` 可接受；省级公司子树大时考虑改 `EXISTS` / 预展开）。
5. **机构层级与部门层级不一致** — 若 `sys_manager_org.parent_org_id` 与 `ancestors` 打架，"机构子树 ≡ 部门子树"的等价性就不成立。必须加一致性校验并在机构页报错。
6. **写侧同步** — 读侧收窄不代表写侧安全。`router.go` 的 `*Writes` 组已挂 `DataScopePermission`（`:326,417,978,…`），确认机构维度同样作用于写路径；`132-write-scope` 的 403 语义需回归。
7. **非 `ScopedDB` 路径** — Excel 导入/导出、仪表盘、通知目标、工单派单等未必经 `pkg/query.ScopedDB`。机构维度生效后需逐个确认这些路径是否也该收窄（尤其**导出**，越权导出比越权读取更敏感）。
8. **语义变更提示** — 旧行为是多角色取 MAX（就窄不就宽，实为"取交集"）；新增维度是"取并集放宽"。两者并存时用户困惑，需在角色/岗位表单加 tooltip 说明。

## 八、待决策项（需你确认后再进入开发排期）

1. **机构锚点是否允许回退**：建议**不**回退（fail-closed + 提示）。若希望平滑，可加一个"回退到 `dept_id`"的降级开关，但默认关。
2. **角色维度与机构维度的并集是否也要改造 `MAX`**：本文保持 `MAX` 不动（零回归）。若未来要统一"多角色并集"，那是独立议题（涉及存量语义变更）。
3. **`sys_manager_org` 的归属**：目前属"经理同步"域。是继续共用（权限侧只读），还是另建一张 `sys_org` 做机构目录、让经理同步改用视图？**建议共用 + 加一致性校验**，成本最低且避免两套机构口径。
4. **L3 是否本期落地**：若短期内确无"派驻/跨机构兼任/临时代理"场景，可先只做 L1+L2。
5. **岗位 `org_scope` 是否允许承载 `data_scope` 的档位**（如"仅本人""本部门"）：本文建议**不允许**，岗位只表达"机构维度"，功能档次仍由角色承载，语义最省事。

# 修订 v2：机构与部门在代码层无实际区分时的方案修正

> 触发追问：**"当前项目中，机构和部门在代码侧面无实际区分，这种情况下你提到的方案是否可用？"**
> 结论：**方案可用，但 §5 的骨架必须换。** 原文 L1 把 `OrgOf`（依赖 `sys_manager_org`）当成硬依赖，这是硬伤。

## v2-1 你的判断成立，而且比"无区分"更精确

真实状况是**三层"半成品"，没有一层能承担权限语义**：

| 事实 | 证据 | 对方案的含义 |
|---|---|---|
| `sys_dept` **没有**层级类型字段（`dept_type`/`org_type`/`level` 全不存在） | `internal/models/dept.go:4-23` | 无法从部门节点本身判断"这是机构还是科室" |
| 唯一相关标记 `is_external_org`，语义是"**有职场的物理位置**"，且已被强占用 | `internal/models/dept.go:16`；`internal/services/operations/location_alias_service.go:292-307`（`is_external_org != 1` 直接拒绝建 alias） | 它答的是"这里有没有楼宇/机房"，**不是**"这是哪级机构"。中支若无常驻职场就不会被标记 |
| `sys_manager_org` 是**经理同步域的旁挂表**，**无种子数据**（`init_data.go` 零命中），靠人工或"从部门架构生成"按钮（`manager_rule_service.go:1445-1481` 只取 `is_external_org=1` 的部门做候选） | `internal/core/db/migrations/migration_220_manager_rule_tables.go`；`manager_rule_service.go:1445-1481` | 全新库上它是**空表**；空表 ⇒ `OrgOf` 全员未命中 ⇒ 本方案赋能的全员 `fail-closed`（全员什么都看不到） |

⇒ **任何以 `OrgOf` 为硬依赖的权限方案，在未治理机构数据的环境里都会静默失效。** 这与 §7-3 我自己警告过的"不得回退"形成矛盾：不回退则全员空集，回退则范围错误。两条路都错。**说明依赖本身就是错的设计。**

## v2-2 修正的核心：锚点从「机构实体」降级为「部门子树根 + 解析模式」

关键认识 —— **机构层级只是部门树的一个投影，不需要独立实体。** `ancestors` 已经完整编码了层级；"中支是几级""综合管理部属于哪个中支"这两件事，部门树全都能回答。

所以：**不需要新建机构表、不需要填 `sys_manager_org`、不需要把 `is_external_org` 改语义。** 只需把"锚点从哪来"变成一个**可选解析模式**。

把原设计的 `org_scope` 字段改名为 `anchor_mode`（语义更准）：

| `anchor_mode` | 名称 | 锚点怎么算 | 前提 | 适合 |
|---|---|---|---|---|
| `0` | 不参与（默认） | — | 无 | 存量零回归 |
| `1` | **相对层深** | 从用户 `dept_id` 沿 `ancestors` 上溯到**第 N 层**（`anchor_param`=目标深度） | 组织树规整、各级深度一致 | **"所有中支的管理员"**：一个岗位/角色覆盖全部中支，零数据治理 |
| `2` | **显式锚点** | `anchor_param`=固定 `dept_id`，展开其子树 | 无 | 单机构管理员、过渡期；等价于"Custom + 自动展开子树"（修掉 `Custom(2)` 不展开的缺陷） |
| `3` | **外部机构标记** | 沿 `ancestors` 由近到远找第一个 `is_external_org=1` 的节点 | 组织树已按"有职场"标过机构 | **零新增数据**即可用；若中支普遍有职场，这是最省事的首选 |
| `4` | **经理机构** | 复用 `OrgOf`（`sys_manager_org`） | 机构表已治理 | 与经理同步共用口径，非默认 |

`anchor_param`（`int` 或 `varchar`）统一存参数，一张字段覆盖 4 种模式。

**展开一律复用现有实现**：拿到锚点 `dept_id` 后走 `queryDeptChildIDs(anchor)`（`pkg/datascope/datascope.go:229-245`），**不新增任何子树递归代码**。四种子树的等价性在 v2-4 说明。

**合并规则完全不变**（这是原文最有价值的部分，保留）：

```
1. roleScope.All                                    -> All
2. eff = ∪(roleScope.DeptIDs, 各来源 anchor 展开集)
3. eff 非空                                          -> {DeptIDs: eff, Hook: None}
4. eff 空 且 roleScope.Hook==SelfUser                -> Self
5. 其余                                              -> FailClosed
```

`MAX(data_scope)` 仍一字不改；`anchor_mode` 仍**绝不参与 MAX**（原因见 §5.2，这条结论在 v2 中依然成立且更重要）。

## v2-3 用户级显式覆盖（`sys_user_scope_grant`）—— 从"可选"升为"推荐"

原 L3 是可选，v2 里应该**前移**，因为它是唯一**不依赖任何组织数据质量**的兜底：

| 列 | 说明 |
|---|---|
| `user_id` | 被授权人 |
| `dept_id` | 锚点部门（展开其子树） |
| `include_child` | 是否含下级 |
| `expire_at` | 可空；空=永久。支持临时代理 |
| `source` / `remark` | 审计：来自岗位、来自角色、人工特批 |

它解决原文 §5.5 里全部"难例"：省公司派驻、跨机构兼任、临时代理、机构数据未治理期间的过渡授权。**并且它让"刘洋"这个案例在完全不做组织治理的前提下也能立刻落地。**

## v2-4 刘洋的三条落地路径（按成本从低到高）

| 路径 | 配置动作 | 前提 | 评价 |
|---|---|---|---|
| **① 显式授权**（最快，1 分钟） | 在刘洋身上加一条 `sys_user_scope_grant(dept_id=武汉中支, include_child=true)` | 无 | 立刻可用；但要逐人配，适合过渡与小规模 |
| **② 岗位 + 模式 3**（推荐） | 建「中支管理员」岗位，`anchor_mode=3`；给刘洋加该岗位 | 武汉中支节点已 `is_external_org=1` | **一个岗位覆盖所有中支**，零新增数据；中支普遍有职场时命中率高 |
| **③ 岗位 + 模式 1**（无标记也要覆盖） | 建「中支管理员」岗位，`anchor_mode=1, anchor_param=中支深度`；给刘洋加该岗位 | 组织树深度规整 | 完全不需要 `is_external_org` 标对；但组织不规整（如"中支含分公司本部"）会判错，需配预览校验 |

三条路径都给刘洋 **武汉中支子树** 的可见集（`queryDeptChildIDs(武汉中支)`），因为 `OrgOf` 的空表问题被绕开了。

**"机构子树 ≡ 部门子树"在 v2 中是否还成立？**
成立，且不再需要 `sys_manager_org.parent_org_id` 与 `ancestors` 的一致性校验 —— 因为锚点本身就取自 `sys_dept` 或显式 `dept_id`，**层级与子树天然同源**。原文 §7-5 那条风险在 v2 里自动消解。这是 v2 比 v1 更干净的另一个理由。

## v2-5 三道"防静默"防线（v2 新增，必做）

"锚点算不出来"是这类方案唯一的失败模式，且失败是**静默的**（用户以为生效、实际空集或错范围）。必须三处设防：

1. **配置期校验**：保存角色/岗位的 `anchor_mode` 时，若依赖条件不满足（模式 3 组织树里 `is_external_org=1` 的命中率为 0；模式 1 的 `anchor_param` 超出树深），**拒绝保存**并提示。这是最重要的防线——把错误挡在配置时，而不是运行期。
2. **推导预览**：角色/岗位详情页展示"该岗位当前 12 名任职人 → 9 人解析到锚点、3 人未解析（列出姓名与原因）"。让管理员一眼看到覆盖缺口。
3. **运行期告警**：未命中一律 `fail-closed`（**绝不回退到 `dept_id`**，原文 §7-3 结论保留）+ 结构化日志 `(user_id, source, anchor_mode, reason)`，并计入一个可观测计数。

# 修订 v3：支持"三层机构、同一岗位自适应到对应层级"

> 触发追问：**"机构层级有三层：分公司-中支-支公司（如湖北分公司 / 武汉中支 / 硚口支公司）。现阶段方案可以做到中支，但要管理到支公司就不行了吧？"**
> 结论：**你的判断成立，而且比字面上更准确——不是"做不到支公司"，而是"一个岗位无法自适应到不同层级"。** 根因是 v2 模式 1 的 `anchor_param` 是个**固定深度数字**。

## v3-1 先把"能做到 / 做不到"拆清楚

"管理到支公司"其实是**两个完全不同的需求**，v2 的能力边界只在第二个上：

| 需求 | 例子 | v2 能力 | 说明 |
|---|---|---|---|
| **(a) 管到武汉中支，且天然含其下的硚口支公司** | 中支管理员锚点=武汉中支，子树自动含硚口支公司 | ✅ **能做** | 子树展开本就是全层级，`queryDeptChildIDs(武汉中支)` 必然包含硚口支公司 |
| **(b) 一个岗位让各支公司的人各自管各自的支公司** | 「支公司管理员」岗位分给硚口的人 → 他得硚口支公司；分给汉阳的人 → 他得汉阳支公司 | ❌ **v2 做不到** | 模式 1 的 `anchor_param` 只能填一个固定数字，设 2 只认中支、设 3 只认支公司；模式 2 要逐机构配 `dept_id`，又退回"每机构一个角色" |

所以准确表述是：**v2 能"管到某一层的某一家"，但不能"用一个岗位覆盖某一层的所有家"。** 而后者正是你上一轮提出的原始诉求（"建一个角色，人员属于哪个机构就拥有哪个机构的管理员角色"）——在 v2 里它只对**单层**成立，对**三层**不成立。

**补充一个反直觉发现**：v2 的模式 3（`is_external_org` 最近节点）**其实是自适应的**——因为它是"沿 `ancestors` 由近到远找第一个命中某判据的节点"，不依赖固定深度。但它的**层级不由你控制**：中支有职场就停在 中支，永远到不了支公司；而且它答的是"哪里有楼宇"，不是"这是第几层机构"。**算法是对的，判据是错的。** 这直接指明了 v3 的方向。

## v3-2 核心：把"固定深度"换成"层级标记 + 最近层级节点"

`sys_dept` 新增一列 `org_level`：

| 值 | 含义 |
|---|---|
| `0` | 非机构（普通部门/科室）——默认值，存量零回归 |
| `1` | 分公司（如 湖北分公司） |
| `2` | 中支（如 武汉中支） |
| `3` | 支公司（如 硚口支公司） |
| `4+` | 预留（网点/班组） |

> 注意：**这不是新概念**。`sys_manager_org.org_type` 早就是 `0=分公司 / 1=中支 / 2=支公司`（`manager_org.go:12-16`），`orgTypeByOrgDepth` 也已在按"机构祖先链深度"推导（`manager_rule_service.go:1569-1583`）。它的问题只是：**躺在经理同步域、无种子数据、且是"机构表上的属性"而不是"部门树上的层级"。** v3 把它下沉为 `sys_dept` 的一等属性，`sys_manager_org.org_type` 随后与之对齐（或直接改读 `sys_dept.org_level`）。

新增解析模式 **`anchor_mode = 5`「最近层级节点」**：

```
resolveAnchor(userID, targetLevel):
  1) 从 sys_user.dept_id 起，若该节点 org_level == targetLevel -> 命中自身
  2) 否则取 sys_dept.ancestors（根→父序），**反转由近到远**逐级检查
  3) 第一个 org_level == targetLevel 的节点即为锚点
  4) 全链未命中 -> not ok（fail-closed，不回退）
  5) 锚点确定后 -> queryDeptChildIDs(anchor) 展开子树（复用现有唯一实现）
```

**这个算法与 v2 模式 3 完全同构，只是把判据从"`is_external_org=1`"换成"`org_level == N`"。** 代码上应合并成一个"锚点谓词可配置"的实现，避免两套并行逻辑漂移。

## v3-3 三个岗位走查（同一套组织树，互不干扰）

组织树：`湖北分公司(1) → 武汉中支(2) → 硚口支公司(3) → 综合管理部(0)`；`湖北分公司 → 长沙中支(2)`。

| 岗位 | `anchor_mode=5, anchor_param` | 刘洋（武汉中支/综合管理部） | 老王（硚口支公司/综合部） | 小李（长沙中支/综合部） | 覆盖结论 |
|---|---|---|---|---|---|
| 「分公司管理员」 | `target=1` | 锚点=湖北分公司 → 全湖北 | 锚点=湖北分公司 | 锚点=湖北分公司 | 一个岗位覆盖所有分公司 ✅ |
| 「中支管理员」 | `target=2` | 锚点=**武汉中支**（跳过综合管理部 level0）→ 武汉中支+硚口支公司**全含** | 锚点=**武汉中支**（由近到远跳过 level3 的硚口） | 锚点=长沙中支 | **一个岗位覆盖所有中支** ✅ |
| 「支公司管理员」 | `target=3` | 链上无 level3 → **未命中 fail-closed** | 锚点=**硚口支公司** → 硚口+其下科室 | 链上无 level3 → 未命中 | **一个岗位覆盖所有支公司** ✅ |

关键点：
- 刘洋对「中支管理员」岗位命中武汉中支 —— **正好是你最初的需求**，且现在对三层全部成立。
- 老王对「中支管理员」岗位**不会**停在硚口支公司（那是 level 3 ≠ 2），会继续上溯到武汉中支 —— 这正是"中支管理员必须管得住下属支公司"的语义。
- 刘洋对「支公司管理员」岗位**未命中**，`fail-closed`。这是**正确的**：他不在任何支公司下，不该有支公司级权限。
- 三个岗位可以同时给同一个人，可见集取**并集**（原文合并规则不变）。

## v3-4 两条必须遵守的边界

1. **`anchor_param` 是"岗位设计者"设的，不是"任职人"能改的。** 层级越高（target=1 分公司）破坏力越大。因此**高层级 target 的岗位，其"分配岗位"权限必须收紧**（谁能给某人授「分公司管理员」= 授予全湖北可见，等同于半个超管）。这条在 v2 里也存在，但 v3 让"一个岗位覆盖一大片"变得更容易后，风险显著放大。建议：`anchor_param <= 2` 的岗位分配走审批或限超管；`target=1` 默认仅超管可配。

2. **锚点层级 ≠ 可见层级。** 「支公司管理员」锚点=硚口支公司，展开子树 = 硚口支公司+其下所有科室（level 0 节点）——这是对的。但**不该**出现"锚点向上越级"（如某岗位 target=3 却因组织树错误命中一个 level 3 节点位于别的分公司下）。这靠配置期校验 + 一致性检查兜住（见 v3-6）。

## v3-5 `org_level` 的数据从哪来（这是 v3 的唯一真实成本）

v3 比 v2 多了一笔**数据治理账**，必须付，因为"这节点是第几层机构"这件事系统从来没记录过。四个填充来源，按优先级：

| 来源 | 做法 | 评价 |
|---|---|---|
| **① AD DN 推导** | AD DN 天然编码层级：`OU=硚口支公司,OU=武汉中支,OU=湖北分公司,DC=...`，按 OU 段数与命名规则推 `org_level` | **最可靠、可批量**；但代码里目前**没有**这个逻辑（`dept_sync_service.go` 只在 `:123` 提了一句"DN 层级要求父 OU"），需新增 |
| **② 从 `sys_manager_org.org_type` 反填** | 若机构表已治理过，按 `dept_id` 一一回填 `org_level = org_type + 1` | 零风险；但机构表**无种子数据**，全新库为空 |
| **③ 部门编辑页手工标** | 前端 `EditModal.tsx` 已有 `isExternalOrg` 下拉，旁边加一个 `orgLevel` 下拉 | 稳、可逐个校正**公司本部特例**（见下）；但 N 个机构要人工点一遍 |
| **④ `dept_code` 前缀约定** | 如 `HQ-`/`ZB-`/`ZG-` 前缀推层级 | 脆弱隐式约定，**不推荐作为唯一来源**，可作初稿辅助 |

**公司本部特例（必须承认的现实）**：`orgTypeByOrgDepth` 注释明写"特例（如中支同时含分公司本部）由页面手工调整"（`manager_rule_service.go:1573`）。即"武汉中支"节点下既可能是中支本部、也可能挂着分公司本部人员——**纯靠深度推导会判错，必须允许手工覆盖 `org_level`**。所以来源 ③ 不是可选项，而是**必要兜底**。

## v3-6 v3 新增的两道校验（并入原三道防线）

1. **配置期校验（强化）**：保存 `anchor_mode=5` 的岗位时，检查该 `target` 层级在组织树中**是否存在至少一个节点**；命中率为 0 直接拒绝保存。
2. **一致性告警（新增）**：`org_level` 与 `parent` 关系矛盾时告警——如"父节点 level=2，子节点 level=1"（跨级反向）、"level=3 节点的 `ancestors` 链上无任何 level=2 节点"（支公司悬空）。这类脏数据会让"最近层级节点"定位到错误锚点，是 v3 唯一的**错范围**风险来源（比 v2 的"空集"更危险，因为不报错还给了错权限）。

## v3-7 v3 与 v2 的差异一览

| 项 | v2 | v3 |
|---|---|---|
| 能否一个岗位覆盖**单层**所有机构 | ✅ | ✅ |
| 能否一个岗位覆盖**三层**中的任意指定一层 | ❌（固定深度/逐机构配） | ✅（`target` 层级 + 最近节点） |
| `anchor_param` 语义 | 固定深度数字（"往上第 N 层"） | 目标机构层级（"最近的分公司/中支/支公司"） |
| 是否依赖组织树深度规整 | ✅ 依赖（深度不一致就判错） | ❌ **不依赖**（只看层级标记，不看第几层） |
| 是否依赖 `is_external_org` | 模式 3 依赖 | 不再是主路径（被 `org_level` 取代） |
| 新增数据治理 | 无 | **必须**：`sys_dept.org_level` 填充 + 特例校正 |
| 主要失败模式 | 空集（安全） | 空集 + **锚点判错（错范围，更危险）** |
| 保留不变 | `MAX` 零改动、合并规则、`queryDeptChildIDs` 复用、`ScopeResult`/`ScopedDB` 零改动 | 同左 |

## v3-8 修正后的落地顺序

| 期 | 内容 |
|---|---|
| **P0** | `sys_dept.org_level` 一列 + 前端手工标注（必要兜底）+ 从 `sys_manager_org.org_type` 反填脚本 + 一致性告警 |
| **P1** | `anchor_mode`/`anchor_param`（角色/岗位）+ **模式 5「最近层级节点」** + 模式 2（显式锚点，单机构立刻可用）+ 合并规则 + 配置期校验 |
| **P2** | AD DN 批量推导 `org_level`（把 P0 的人工成本降下来）+ 推导预览 |
| **P3** | `sys_user_scope_grant`（派驻/兼任/临时代理）+ 用户表单岗位多选 + 缓存失效接线 |
| **P4** | 写侧与导出逐域确认 |
| **弃用** | 模式 1（固定深度，被模式 5 取代）、模式 3（`is_external_org` 判据，被 `org_level` 取代）、新建机构表、`DataScope` 扩位 `=6` |

> **一句话**：v2 的锚点算法是对的（"最近节点 + 子树展开"），错的只是**判据**（用"第几层"或"有没有职场"，而不是"这是哪级机构"）。v3 补上 `org_level` 这个判据后，三层机构用一个岗位即可各就各位；代价是必须先把机构层级标注出来，且必须处理"中支含分公司本部"这类特例。
