## Issue 1 — CR-01: InfoWindow Storage XSS (SECURITY)

**File:** `xingran-react-frontend/src/pages/operations/building-spaces-3d/components/HubeiMap.tsx:415-431`
**Also affected:** `xingran-react-frontend/src/pages/operations/building-spaces-3d/components/HubeiMapGL.tsx:408-424`

**Symptom (verified):** `building.name` and `building.address` are interpolated directly into template literal strings used to set `InfoWindow` content via Baidu Maps API. No HTML escaping is applied. If `building.name` or `building.address` contains malicious HTML/JS (e.g., `<img src=x onerror=alert(1)>`), it will execute in the context of the map InfoWindow DOM.

**Root cause:** Two identical template literal constructions at the cited line ranges:
- HubeiMap.tsx line 418: `${building.name}` inside an `<h3>` tag
- HubeiMap.tsx line 421: `${building.address || "暂无地址"}` inside a `<div>` tag
- HubeiMapGL.tsx line 411: `${building.name}` inside an `<h3>` tag
- HubeiMapGL.tsx line 414: `${building.address || "暂无地址"}` inside a `<div>` tag

The `onclick` handlers also embed `building.id` directly (lines 432 and 425 respectively), which while not HTML-injectable, could be a second vector if id format is ever user-controlled.

**Recommended fix:** Escape HTML entities before interpolation. Add a helper:
```ts
const escapeHtml = (s: string) =>
  s.replace(/&/g, "&amp;").replace(/</g, "&lt;").replace(/>/g, "&gt;").replace(/"/g, "&quot;").replace(/'/g, "&#39;");
```
Then replace `${building.name}` with `${escapeHtml(building.name)}` and `${building.address}` with `${escapeHtml(building.address)}` at all four sites. Apply to both HubeiMap.tsx and HubeiMapGL.tsx.

**Regression risk:** Low — only affects display text; escaped characters render normally. Ensure existing Chinese/ASCII names still display correctly after escaping.

**Verification:** Inject `<script>alert(1)</script>` as a building name via API; reload map and open InfoWindow — alert should NOT fire.

## Issue 2 — WR-01: my-notices/detail.tsx permanent Spin

**File:** `xingran-react-frontend/src/pages/my-notices/detail.tsx:29-47`

**Symptom (verified):** `setLoading(false)` at line 34 only executes inside the `if (noticeData)` block (line 32). The `catch` block (line 42) does call `setLoading(false)` at line 46, but there is NO `else` branch for the case when `noticeData` is falsy (e.g., API returns `{code: 0, data: null}`). In that path, `setLoading(false)` is never called, leaving the page in a permanent Spin state.

**Root cause:** Lines 32-41:
```ts
if (noticeData) {
  setNotice(noticeData);
  setLoading(false);
  // ...
}
// No else branch — setLoading(false) omitted when noticeData is falsy
```

**Recommended fix:** Move `setLoading(false)` outside the `if` block, or add an `else` that handles the falsy case:
```ts
if (noticeData) {
  setNotice(noticeData);
} else {
  message.error("通知不存在");
  navigate(USER_NOTICES);
}
setLoading(false); // always runs
```
The `setLoading(false)` at line 34 can be removed and placed once at the end of the try block (before the catch), or after the whole try/catch.

**Regression risk:** Low — the new `else` branch adds explicit error handling that should have existed; `setLoading(false)` being unconditional is the correct behavior.

**Verification:** Mock API to return `{code: 0, data: null}` for a valid notice ID — page should navigate away instead of spinning forever.

## Issue 3 — WR-02: my-duty/index.tsx stale closure

**File:** `xingran-react-frontend/src/pages/duty/my-duty/index.tsx:138-152`

**Symptom (verified):** `handleSearch` (line 142-145) calls `setCurrent(1)` then immediately calls `loadSchedules()`. The `useEffect` at line 134-139 also calls `loadSchedules()` reactively when `paginationProps.current` changes. The stale closure issue: `loadSchedules` is defined at line 113 with default args `(page?: number, size?: number)`, and internally references `paginationProps.current` and `paginationProps.pageSize` at lines 118-119. However, in `handleSearch`, it is called with no args (using the stale captured `paginationProps` values), and the call order is: `setCurrent(1)` triggers re-render, but `loadSchedules()` uses the OLD `paginationProps.current` value from before the re-render.

**Root cause:**
- `handleSearch` (lines 142-145): calls `setCurrent(1)` then `loadSchedules()` synchronously — `loadSchedules` captures `paginationProps.current` from the current render, not the updated one.
- `handleTableChange` (lines 148-152): same pattern — calls `setCurrent(pagination.current ?? 1)` then `loadSchedules()` synchronously.

The fix is to pass explicit args to `loadSchedules` in both handlers:
```ts
const handleSearch = () => {
  setCurrent(1);
  loadSchedules(1, paginationProps.pageSize); // pass explicit page
};

const handleTableChange = (pagination: TablePaginationConfig) => {
  const newCurrent = pagination.current ?? 1;
  const newPageSize = pagination.pageSize ?? 10;
  setCurrent(newCurrent);
  setPageSize(newPageSize);
  loadSchedules(newCurrent, newPageSize);
};
```
The `useEffect` dependency `[paginationProps.current, paginationProps.pageSize]` would still trigger on change but would use the correct values since it calls `loadSchedules()` without args (falling through to the store values).

**Regression risk:** Medium — `handleTableChange` also calls `setPageSize` which triggers a re-render; the explicit args bypass the stale closure. Existing behavior of using stored pagination values in `useEffect` is preserved.

**Verification:** Click "Search" with page > 1 active — should reset to page 1 and load correctly. Change page size from 10 to 20 — should load with new page size immediately.

The map transforms backend `Building` objects into `BuildingItem` objects for the 3D visualization. **Regression risk:** Low — the `viewLevel` store value is already used by `renderView()` to determine which visualization to show; wiring it into the map transform is consistent with existing architecture.

**Verification:** With `viewLevel=1` (province view), load buildings — they should appear on the map. With `viewLevel=2` (city view), same test.

## Issue 5 — WR-04: DashboardScopeSelector constraint invariant

**File:** `xingran-react-frontend/src/components/dashboard/settings/DashboardScopeSelector.tsx:57-88`

**Symptom (verified):** `handleIsSystemChange` (lines 76-88) enforces "system dashboard must be global" in the enable direction only (lines 83-85: `if (isSystem) { newValue.scope = "global"; }`). There is NO symmetric enforcement when `isSystem` is set to `false` and the current `scope` is `"global"`. Additionally, the Select's `disabled` prop at line 102 (`disabled={disabled || (value?.isSystem && value?.scope === "global")}`) prevents the user from changing scope while `isSystem` is true, but does NOT prevent them from disabling `isSystem` while scope is `"global"`, creating a state where `isSystem=false` and `scope="global"` — a contradictory invariant violation.

**Root cause:** Asymmetric constraint. The enable direction (`isSystem=true`) forces scope to global, but the disable direction does not restore scope to a valid default (e.g., `"private"`). The guard at line 102 only disables the scope Select when `isSystem && scope===global`, but `handleIsSystemChange` does not reset `scope` when `isSystem` becomes `false`.

**Recommended fix:** In `handleIsSystemChange`, reset scope to a valid default when system is disabled:
```ts
const handleIsSystemChange = (isSystem: boolean) => {
  const newValue: { scope: DashboardScope; isSystem: boolean; deptId?: string } = {
    scope: value?.scope || "private",
    isSystem,
  };

  if (isSystem) {
    newValue.scope = "global";
  } else if (newValue.scope === "global") {
    // Prevent contradictory state: system=false + global is invalid
    newValue.scope = "private";
  }

  onChange(newValue);
};
```

**Regression risk:** Low — the change only affects the `isSystem=false` case, restoring scope to "private" which is a valid state. Existing `isSystem=true` behavior is unchanged.

**Verification:** Enable "system dashboard" switch — scope should lock to "global" and Select should be disabled. Then disable "system dashboard" — scope should reset to "private" and Select should become enabled again.
