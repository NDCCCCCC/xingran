   读 /proc/stat)。问题 4 的"gopsutil pitfalls"实际是**差值采样零增量**问题,与库无关(见 §4)。
2. **`internal/templates/templates_74_08_test.go` 内没有 QUIRK 注释**(grep 证实)。15 项
   QUIRK 正典清单分布在 74-08-SUMMARY(9 项)+ 74-09/74-12 SUMMARY 与各测试注释中;
   v1.27 修复范围以 PROJECT.md D-03 列举的为准。
3. **`internal/agent/pkg/retry` 目前零生产调用方**(全仓 grep,唯一 import 是它自己的测试)。
   retry QUIRK 修复的业务影响面 = 0,但 v1.26 测试**锁定了 QUIRK 行为**(见 §5 P-10)。

## 1. miniredis(core 包,RedisCache 52.6% → 70%)

### 1.1 本仓库实际用到的 Redis 命令面(pkg/cache/redis.go 实测)

GET/SET/DEL/EXISTS/MGET/MSET/INCR/INCRBY/DECR/DECRBY/**EVAL Lua(INCR+EXPIRE,
IncrementWithExpire)**/EXPIRE/TTL/**SCAN(COUNT=500, Keys() 与 DirectRedisKeys)**/
FLUSHDB/HGET/HSET/HGETALL/HDEL/HKEYS/**INFO(server/memory/stats/keyspace 四段)**/
DBSIZE/**XADD**(RPA task_service.go:333 + DirectRedisXAdd)。

### 1.2 陷阱表

| # | 陷阱 | 严重度 | 缓解 |
|---|------|--------|------|
| R-1 | **TTL 不自动流逝**:miniredis 里 key 永不自发过期,`time.Sleep` 等 TTL 测试会假绿或假红 | 高 | 用 `mr.FastForward(d)` 推进全部 TTL;EXPIREAT 换算基准用 `mr.SetTime(t)`。现 core_74_08_test 用 sleep 的写法迁移时要改 |
| R-2 | **INFO 只返回 clients 段的 connected_clients 一个字段** | 中 | `RedisCache.GetStats()`(redis.go:427-486)解析的 redis_version/used_memory/keyspace_hits 全部拿不到;err==nil 但 map 稀疏 → hit_rate=0.0。测试只断言 err==nil + key 存在性,不断言具体数值;缓存监控页数值路径留给真实 Redis |
| R-3 | **CLIENT */CONFIG * 不支持**;go-redis ≥v9.5 连接时自动发 `CLIENT SETINFO`,旧版 miniredis 报 unknown command | 中 | 用最新 miniredis(v2 最新,已将 CLIENT SETINFO 实现为 no-op);或在测试专用 Options 加 `DisableIdentity: true`(注意旧版本拼写 DisableIndentity)。本仓库 go-redis v9.7.0 命中此区间(go-redis issue #2911) |
| R-4 | SCAN 游标语义:miniredis 通常一次返回全部 key、cursor 直接归零,不会像真 Redis 分批 | 低 | 本仓 `scanKeys()` 循环到 next==0 为止,兼容;但不要写"分批大小"类断言 |
| R-5 | EVAL/Lua:支持(gopher-lua 内嵌),INCR/EXPIRE 组合脚本可跑;但 Lua 内不支持的命令会报错 | 低 | IncrementWithExpire 的 Lua 只用 INCR/EXPIRE,安全 |
| R-6 | XADD/XREAD 支持,XREAD 带 BLOCK 的行为与真 Redis 有差异(消费方是 RPA agent 不在 Go 测试内) | 低 | Go 侧只测 XADD 生产路径即可 |
| R-7 | **MultiLevelCache 构造即启动 L2WriteWorker goroutine**(redis.go:530-543) | 中 | 测试用 `NewMultiLevelCacheSimple`(不启 worker)或 t.Cleanup 里 Close(),否则 -race 下 goroutine 泄漏告警 |
| R-8 | "glebarez-style"纯 Go 假件通病:行为按文档子集实现,和真件差异只在边角暴露 | 中 | miniredis 有 integration 目录对照真 Redis;单测过了 ≠ 生产过,保留一层真实 Redis 冒烟(dev config 已有) |

**结论**:miniredis 覆盖本仓命令面 ≥95%,可直接支撑 RedisCache 全方法测试;注意 R-1/R-2/R-3 三点即可。来源:miniredis README(HIGH)、go-redis issue #2911(MEDIUM)。

## 2. 嵌入式 LDAP server(addomain 2415 stmts 21.78% → 70%)

### 2.1 现状与已验证事实

- 已有 `LDAPClientIface`(ldap_iface.go)+ mockLDAPClient(ldap_client_mock_test.go),
  service 层同步逻辑已可测;**缺口在 `*LDAPClient` 具体实现**:Connect /
  dialConnection(ldap://、ldaps://、StartTLS 三分支)/ tryBindAttempts(UPN 与
  DOMAIN\user 双格式)/ searchWithPaging+错误回退 / FailoverClient 顺序遍历。
- **go-ldap v3.4.12 没有官方 server 子包**(本地 module cache 目录树证实,只有 client)。
  网传"go-ldap 自带 Server"不适用于当前 pin 版本(HIGH)。

### 2.2 选项对比与陷阱

| 选项 | 保真度 | 陷阱 | 判定 |
|------|--------|------|------|
| vjeantet/ldapserver(进程内) | simple-bind + search | **unmaintained,自称 WIP**;无完善 TLS;asn1-ber 老版本;search result 无服务端限制(测不了 size-limit 分支) | 可用但需 fork 心理准备(MEDIUM) |
| glauth 单二进制 | LDAPS/StartTLS + simple bind + search | 非 library,config 文件驱动,每测试场景起停开销大;分页行为与 AD 有差(LOW 置信) | Windows 无 Docker 时的备选 |
| testcontainers + osixia/openldap | 最高(真 slapd) | **必须 Docker**;Windows dev 无 Docker 即断;CI 时长 +2~4min;容器起停 flake | 只做 CI 侧可选加层,不作主路径 |
| **推荐:自写 ~200 行 embedded server**(go-ldap client + asn1-ber 已在依赖树) | 按需 | 需自己处理 ber 编解码 bind/search response | dialConnection 默认分支就是 `ldap://` 明文,127.0.0.1+随机端口可直连;bind 可配置"接受/拒绝第 N 次"即可覆盖 tryBindAttempts/FailoverClient/熔断 |

关键依据:`dialConnection`(ldap_client.go:98-126)UseSSL/UseTLS 均为 false 时走明文
`ldap.DialURL("ldap://"+addr)` → embedded 明文 server 无 TLS 也能测 80% 连接逻辑;TLS 两
分支用 `tls.Config{InsecureSkipVerify}` + 自签证书本地 listener 即可覆盖,不需要真 AD。

## 3. scrapligo / SSH fake(device 1249 stmts 39.07% → 70%)

### 3.1 已验证事实(pinned scrapligo@v1.4.0 源码,module cache)

- **StandardTransport 就是 golang.org/x/crypto/ssh**(transport/standard.go:12-16 import +
  注释"standard (crypto/ssh) transport")。网传"scrapligo 自带 SSH 协议栈"是错的 →
  **用 x/crypto/ssh 写 fake server 与生产客户端同栈,线级兼容性最好**(HIGH)。
- 密码认证同时挂 `ssh.Password` + `ssh.KeyboardInteractive`(自动用密码回答,standard.go:143-153)
  → fake server 必须实现 PasswordCallback;要模拟华为式交互认证再加
  KeyboardInteractiveCallback。
- 挂了 ExtraCiphers(aes*-ctr + aes*-cbc + 3des-cbc + blowfish-cbc,scrapli_wrapper.go:134-145)。
  实测 x/crypto v0.46.0 只实现 aes128-cbc / 3des-cbc 两个"insecure"cbc 模式,**blowfish-cbc
  与 aes192/256-cbc 会被静默忽略**(ssh/common.go:552-553 "Ignore the cipher if we have no
  cipherModes definition")→ 代码注释宣称的老设备 CBC 覆盖面比实际窄;fake server 走默认
  chacha/aes-gcm 即可,不受影响。

### 3.2 陷阱表

| # | 陷阱 | 严重度 | 缓解 |
|---|------|--------|------|
| S-1 | FileTransport(已有 e2e_helpers.go + v1.19/v1.20 的 TestE2E_*)**只覆盖命令解析层**:不经过 auth/kex/channel 开关/超时/privilege 升降提示符 | 高(预期管理) | FileTransport 继续管 SendConfigs/parseConfigError;x/crypto/ssh fake 专管 ScrapliWrapper.Open/createConnection/连接池握手 |
| S-2 | NetworkDriver open 后会探测 privilege level,期望 prompt 形态(以确定性字符结尾) | 高 | fake server 的 session channel 必须在 pty-req+shell 请求后输出 `<host>#` 类提示符,否则 open 阶段 hang 到超时 |
| S-3 | auth 回调写法:PasswordCallback 里返回 error 会让 x/crypto 直接断连,触发"Too many authentication failures"形态(scrapligo issue #168 同族) | 中 | 拒绝时返回 (nil,false) 而非 error;区分 wrong-password 与 no-supported-method |
| S-4 | ScrapliWrapper 持具体 `*network.Driver` 不可注入(v1.26 阻塞根因) | 高 | SSH fake 之外还需要小重构:把 NewNetworkDriver 工厂提为可注入函数类型(var 或 option),否则 fake 没有入口。这是 device 包能否到 70% 的**前置条件** |
| S-5 | fixture 路径:Windows 上 filepath.Join 与 fixture 内记录的 `/` 分隔符差异 | 低 | e2e_helpers 已有先例;新 fixture 用 filepath 或统一 `/` + cd 到包目录 |
