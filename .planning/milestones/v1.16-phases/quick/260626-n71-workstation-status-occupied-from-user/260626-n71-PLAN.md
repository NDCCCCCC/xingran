## 1. 目标

工位（sys_workstation）写入 user_id（所属人员）后，**自动**把 status 字段联动为 `WorkstationStatusOccupied = 1`（占用）；清空 user_id 时联动为 `WorkstationStatusAvailable = 0`（空闲）。`Maintain = 2`（维护）由管理员手动设置，**不受联动影响**。

**核心约束**：
- ✅ 不新增枚举值（`WorkstationStatusOccupied=1` 已存在）
- ✅ 不引入新 OperType（复用 `OperTypeUpdate`）
- ✅ 不破坏现有 Excel 导入流程
- ✅ 不引入缓存失效逻辑（sys_workstation 无缓存)
- ✅ 不破坏 Maintain 状态的语义

### 3.2 后端 Service 层改动（核心）

#### 改动 1：`workstation_service.go` Update 方法（169-178 行）

```go
func (s *workstationService) Update(ctx context.Context, workstation *models.Workstation) error {
    var existing models.Workstation
    if err := s.db.WithContext(ctx).Where("id = ?", workstation.ID).First(&existing).Error; err != nil {
        return err
    }
    // 保留创建时间和创建人
    workstation.CreatedAt = existing.CreatedAt
    workstation.CreatedBy = existing.CreatedBy

    // ✨ NEW: user_id ↔ status 联动（保留 Maintain 状态）
    applyWorkstationOccupancyLink(workstation, existing.Status)

    return s.db.WithContext(ctx).Save(workstation).Error
}

// applyWorkstationOccupancyLink 联动工位状态与所属人员
// 规则:
//   - 如果 user_id 有值 → status = Occupied(1)
//   - 如果 user_id 为空 → status = Available(0)
//   - 如果当前 status = Maintain(2)，**保留维护状态不变**
func applyWorkstationOccupancyLink(w *models.Workstation, currentStatus models.WorkstationStatus) {
    if currentStatus == models.WorkstationStatusMaintain {
        // 维护状态不受联动影响
        return
    }
    if w.UserID != nil && *w.UserID != "" {
        w.Status = models.WorkstationStatusOccupied
    } else {
        w.Status = models.WorkstationStatusAvailable
    }
}
```

#### 改动 2：`workstation_service.go` Create 方法（156-159 行）

```go
func (s *workstationService) Create(ctx context.Context, workstation *models.Workstation) error {
    // ✨ NEW: 新建时若指定 user_id,自动设为占用
    applyWorkstationOccupancyLink(workstation, workstation.Status)
    return s.db.WithContext(ctx).Create(workstation).Error
}
```

**说明**：新建工位默认 status=0（空闲）。如果用户在创建时同时指定了 user_id，则联动为 1（占用）。

#### 改动 3：`excel_service.go` prepareRecordsForUpsert

在 `preparedRecord["updated_at"] = time.Now()` 之后，根据 `user_id` 是否有值自动设置 `status`：

```go
// ✨ NEW: user_id ↔ status 联动
if userID, ok := preparedRecord["user_id"]; ok && userID != nil && userID != "" {
    preparedRecord["status"] = int(models.WorkstationStatusOccupied)
} else {
    preparedRecord["status"] = int(models.WorkstationStatusAvailable)
}
```

**注意**：Excel 中的 `status` 列（如果填写了）将被自动覆盖。Excel 配置 `excel_config.go:147` 的 status 列仍然保留用于显示，但导入时实际写入由 user_id 决定。

```go
package migrations

import (
    "gorm.io/gorm"

// Migration_260626_n71_BackfillWorkstationStatus
// 修复历史数据:user_id 有值但 status 仍为 Available(0) 的工位
//
// 触发条件:WorkstationStatusMaintain(2) 不修改（保留维护语义）
func Migration_260626_n71_BackfillWorkstationStatus(db *gorm.DB) error {
    return db.Exec(`
        UPDATE sys_workstation
        SET status = 1, updated_at = NOW()
        WHERE user_id IS NOT NULL
          AND user_id != ''
          AND status = 0
          AND deleted_at IS NULL
    `).Error
}
```

## 4. 关键设计决策（请用户审核）

### 决策点 1：Maintain（维护）状态的处理

**问题**：如果工位当前 `status=2`（维护），管理员又给这个工位分配了人员，状态该如何变化？

**选项**：
- **A. 保留维护状态**（推荐）：维护中分配人员 → status 仍为 2；用户分配但工位不可用，符合"维修中不可用"语义
- **B. 强制改为占用**：维护 + 分配用户 = 占用；维护状态被人员分配破坏

**我的推荐**：**A 保留维护状态**。理由：维护是运维流程强语义，人员分配是资产管理语义，两者独立。但用户可能希望 B（统一规则）。

### 决策点 2：Excel 导入时 status 列的行为

**问题**：Excel 模板有"状态"列，用户填写时是按用户填的算，还是按 user_id 自动算？

**选项**：
- **A. 以 user_id 为准**（推荐）：导入时忽略 Excel 中填写的 status 列，按 user_id 联动
- **B. 保留 Excel 中的 status**：如果 Excel 填了 status=2 (维护) 则保留

**我的推荐**：**A 以 user_id 为准**。理由：Excel status 列保留仅作为模板展示与提示，实际写入由 user_id 驱动。如果未来需要支持 Excel 维护覆盖，可以再加 flag。

### 决策点 3：历史数据迁移的范围

**问题**：是否修复 `user_id IS NOT NULL AND status=0` 的工位？

**选项**：
- **A. 修复**（推荐）：把所有这种工位改为 status=1，符合新规则
- **B. 不修复**：只对新数据生效，历史不一致数据保留

**我的推荐**：**A 修复**。理由：用户的真实期望是"状态与人员一致"，不一致的历史数据是 bug。但需要确保迁移 SQL 只改 `deleted_at IS NULL` 的活数据。

### 决策点 4：前端是否在 userId 改变时立即联动 status

**问题**：前端表单中，userId Select 改变时是否立即在 UI 上联动 status？

**选项**：
- **A. 前端联动**（推荐）：用户改变 userId 时立即看到 status 变化，体验更好
- **B. 仅后端联动**：前端不联动，提交后由后端决定；UI 可能显示不一致

**我的推荐**：**A 前端联动**。理由：UX 一致性。但保留后端 Service 层联动作为兜底（防止前端被绕过）。

### 决策点 5：是否新增 OperType

**问题**：status 变更是否需要专门的操作日志类型？

**我的判断**：**不需要**。当前 status 变更通过 `Update` 接口提交，操作日志已经是 `OperTypeUpdate`。没必要新增。
