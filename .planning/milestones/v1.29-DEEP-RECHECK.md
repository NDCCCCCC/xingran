## Critical（6 项，全部经独立源码验证）

### C-1 [Phase 93 新增] 同设备恢复互斥非原子
`config_restore_task_service.go:59-79` — `First()` 查后 `Create()` 写，无事务/锁/部分唯一索引，并发 StartRestore 可双开任务，执行顺序可能倒挂（设备最终落在旧配置）。修复：PG partial unique index `(device_id) WHERE status IN ('pending','running')` + 冲突即失败。

### C-2 [Phase 93 新增] 崩溃恢复遗漏 pending → 设备永久死锁
`config_restore_task_service.go:316-332` — `RecoverStaleRunningTasks` 只收敛 `running`；进程在 Create(pending) 后、goroutine 置 running 前崩溃，残留 pending 永远阻塞该设备互斥（D-34 无取消端点）。修复：WHERE 收敛条件补 pending。

### C-3 [Phase 93 新增] restore 端点 ANY-of 权限，只读可触发高危下发
`network_router.go:158-164` + `permission.go:292-298` — `POST /:id/restore` 挂 4 权限点 ANY-of 组内，仅持 `network:backup:list` 的用户可发起配置恢复；专用 `network:backup:restore` 权限点已定义从未单独强制。修复：restore 子组单独 RequirePermissions。

### C-4 [Phase 91 引入] workstation List 分页上限 10000→100，平面图/3D 静默丢数据
`requests/common.go:25-27`（MaxListPageSize=100）+ commit edc51fd — 迁移前 clamp 上限 10000，typed 化收紧为 100；前端 3 处以 `pageSize:1000` 请求全集：`useWorkstationView.ts:38`、`useWorkstationData.ts:158`（平面图）、`FloorView3D.tsx:70`（3D）。**工位数 >100 的楼层静默丢失第 101+ 工位**（total 正确、无告警、测试无法捕获）。超出"零行为变更"授权，代码注释自称 checkpoint 确认但前端未同步、无 OVR 台账。修复：恢复 10000 上限或前端改专用全集端点。

### C-5 [存量] WS 双读者+双写者竞态，可 panic 打崩进程
`ws_notice_handler.go:112-134` + `notice_hub.go:176-180` — hub 已启动 readPump/writePump，handler 又起自己的读循环并直写 pong（第二写者）。gorilla 单读者/单写者约束被破坏，并发写直接 panic（goroutine 无 recover → 进程崩溃）。属被改文件中的存量缺陷，非 v1.29 引入。修复：删除 handler 读循环，keep-alive 全权交 hub。

### C-6 [Phase 89 覆盖缺口] network 三个 List 端点分页零归一化
`discovery_handler.go:91-92` / `command_handler.go:167-168` / `execution_handler.go:64-65` — `getIntField(rawReq,"pageSize",10)` 内联默认值，network 包对 NormalizePagination/分页常量引用数为 0。`pageSize=10^9` 全表加载、`pageSize=-1` GORM 负 Limit=无 LIMIT 全表、`current=-5` 负 Offset。违反 Phase 89"唯一入口"不变量（该 Phase 的"12+ 处全覆盖"声明在这三处不成立）。修复：三处统一走 NormalizePagination。
