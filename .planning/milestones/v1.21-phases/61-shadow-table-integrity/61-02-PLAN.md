<objective>
落地 SHADOW-01 的必要配套——四类 upsert 路径的「软删行复活」：61-01 引入清理 writer 后，一条被软删的行若同 DN/同名在 AD 端复现，默认作用域 existing 查询查不到它 → 走 Create 分支 → 撞**不含 deleted_at 的唯一约束**：OU/Group 裸 Create 让整轮同步失败；User/Computer OnConflict 把更新打到软删行上（永久不可见，每轮重演）。复活机制 = existing 查询 Unscoped 化（软删行进入 update 分支）+ OnConflict AssignmentColumns 补 deleted_at（零值 INSERT 值 NULL → SET deleted_at=NULL）。

Purpose: 没有复活路径，清理本身在生产上不可上线（Pitfall 1 是本 phase 最高风险）。顺带修复 `sys_ad_group` 的存量潜伏缺陷（handleDeletedGroups 今天就在软删组，同 DN 组复现会让 createGroupsInBatches 裸 Create 撞约束）——研究 Q3 推荐一并修，同一 Pattern、增量成本低（属 SHADOW-01「配套」范畴，非 scope 扩张）。

Output: sync.go / computer.go / group_sync_service.go 三文件复活化；两个 D-78-05c 既有用例翻转；TestSync_Resurrect* 用例五条。

**部署耦合约束（执行器必读）**：61-01 落地后本 plan 完成前不得单独部署生产——清理已激活而复活未就绪，软删行复现即撞约束。本 phase 三个 plan 必须整体部署。执行期内该窗口仅存在于本地工作树，无生产影响。

既定口径：禁 partial unique index（cleanupOldConstraints 42704 雷区）；禁 PG TRIGGER（用户硬约束：数据一致性修复走 Go 层）；Phase 62 边界文件只抄写模式、不引用。
</objective>
