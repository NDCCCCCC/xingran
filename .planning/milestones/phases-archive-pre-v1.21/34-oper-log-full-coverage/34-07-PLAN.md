    **WARNING 3 — oper_log_handler.Clean chicken-and-egg:**
    The async insert (RecordAsync) lands AFTER the synchronous Clean query. The row will be visible after the next insert cycle but will NOT survive the same Clean batch — the Clean deletes everything older than its cutoff (typically 30 days), and the async insert has a timestamp that is current, so it survives the cutoff... unless the Clean's cutoff is "today" or the system clock skews. The safer pattern: **synchronous insert BEFORE the Clean runs.**
    
    Concrete implementation: in oper_log_handler.Clean, BEFORE the actual Clean DB delete runs, call `operLogSvc.Record(...)` (NOT RecordAsync — the synchronous variant) with module="操作日志", operType=OperTypeClean, and a JSON body like `{"cutoff":"2026-06-14","deletedCount":N}`. This guarantees the audit row commits to the DB before the Clean transaction starts.
    
    Add an explicit verification step: after Clean completes, query `SELECT id FROM sys_oper_log WHERE title='操作日志' AND business_type=9 ORDER BY oper_time DESC LIMIT 1` — if the row is missing, the synchronous fallback is broken; print a hard error to stderr and add a TODO comment for follow-up. Document this in a code comment at the Clean call site.

    Add a code comment at the Record call: "Self-referential safeguard: this row is inserted SYNCHRONOUSLY before the Clean delete runs, so it survives the cleanup transaction. Do not change to RecordAsync without understanding the chicken-and-egg risk."

    **File naming note:** Use the singular filenames above. Do NOT use `rpa_task_handler.go` — the actual file is `internal/api/v1/rpa/task_handler.go`.
