## 1. COMP-03 — PageTable 契约

### 决策 1：API 面 = 受控 props + 插槽，非 children 组合式

```tsx
// src/components/shared/PageTable.tsx
interface PageTableProps<T> {
  /** 列表请求：入参含 current/pageSize/filters/排序；返回 { list, total } —— 即 useTableManager 的 loadFunction 签名 */
  request: (params: Record<string, unknown>) => Promise<{ list: T[]; total: number }>;
  columns: ColumnsType<T>;
  /** 搜索区 schema（§2）；与 searchChildren 二选一，同时传时 schema 优先并告警 */
  searchFields?: SearchField[];
  /** schema 覆盖不了的复杂搜索区逃生口（自行渲染 Form.Item，配合 searchForm） */
  searchChildren?: React.ReactNode;
  /** 工具栏左区（新增/导入等业务按钮）；右区（刷新/列设置）由组件内建 */
  toolbar?: React.ReactNode;
  rowKey: GetRowKey<T>;
  /** 行操作列；组件注入 record，返回 ActionButton[]（含经 createDeleteAction 的删除 → 自动走 ConfirmDelete） */
  rowActions?: (record: T) => ActionButton[];
  /** 批量删除：传入即渲染 BatchDeleteButton（65 内部已走 confirmDelete），并内建 selectedRowKeys 管理 */
  batchDelete?: { onDelete: (keys: React.Key[]) => Promise<void>; target: string };
  /** 初始 pageSize（默认 10）；排序元数据透传 useTableManager（64 FIX-03 服务端排序口径） */
  pageSize?: number;
  sorterMetas?: Array<SorterMeta<T> | undefined>;
  defaultSort?: { orderByColumn: string; isAsc?: boolean };
  /** 额外固定筛选（如部门树联动），变化时回第 1 页重载（对应 applyFilters(extra)） */
  extraFilters?: Record<string, unknown>;
  /** 空态引导动作（转发 EmptyStateWithAction） */
  emptyAction?: React.ReactNode;
  /** 透传 Table 其余 props（scroll/expandable/rowSelection 等），rest 全透传不吞 */
}
```

| Prop | 契约 |
|------|------|
| `request` | 失败由组件内部 catch → `handleApiError(error, "加载列表数据")` + 渲染 `ErrorAlertWithRetry`（重试=重新 loadData）+ 表格清空——即 useTableManager 现有 catch 兜底逻辑（`useTableManager.ts:260-267`）升格为错误态 UI |
| `searchFields` / `searchChildren` | 见 `## 2`；搜索/重置/刷新按钮由组件内建（`layout="inline"` 搜索 Card，`marginBottom:16` 惯例） |
| `batchDelete` | 确认文案由 BatchDeleteButton→confirmDelete 模板承接（`将删除选中的 {N} 项…`），**PageTable 不自建第二套删除确认**（65 §6 边界 ①） |
| 分页 | 组件内部按 63 §1 口径渲染 `showTotal`：`total > 0 → 共 {total} 条 / {pages} 页`；`total = 0 → 不渲染`。页码/pageSize 经 useTableManager 持久化（切 tab 恢复，既有行为） |
| 三态 | loading = Table 原生蒙层（64 FIX-01 唯一口径，**禁 Skeleton/整页 Spin**）；空态 = antd 默认 `暂无数据`（可选 EmptyStateWithAction）；错误态 = ErrorAlertWithRetry。三态互斥：loading 期间不渲染空态（antd 天然区分，64 §1 口径） |
| rest | 透传 antd Table 其余 props；**封装不吞、不改名**（与 65 AppInput rest 策略同一纪律） |

### 决策 2：useTableManager 的裁决——保留为底层引擎，PageTable 内部实例化，不重写

- **不吸收进组件内部重写**：useTableManager 已内建 filters sessionStorage 持久化、服务端排序接参、MISC-03 惰性初始化、unhandled-rejection 兜底——这些是被 64/63 验证过的行为资产，重写=重置回归面。25 个存量消费页也要求它保持独立可用。
- **不保留「页面自行调 hook 再喂 PageTable」的双轨**：新页面通过 PageTable 只写 `request`，hook 在组件内部调用（`searchForm` 等经 render-props 或受控 ref 暴露给 searchChildren 逃生口）。理由：双轨会让「三态/分页契约内建」落空——页面仍可能绕过组件手写数据层。
- **结论**：useTableManager 从「页面级 hook」降格为「PageTable 的内部实现细节 + 存量页兼容层」。Phase 67 迁移完成后，新代码禁止直接 import（届时可加 no-restricted-imports，本 phase 不加——25 个存量页还在用）。

示例（试点页目标形态，~120 行量级）：

```tsx
<PageTable
  request={postApi.list}
  columns={columns}
  searchFields={[
    { name: "postCode", label: "岗位编码", type: "input" },
    { name: "status", label: "状态", type: "select", options: STATUS_OPTIONS },
  ]}
  toolbar={<Button type="primary" icon={<PlusOutlined />} onClick={openCreate}>新增</Button>}
  rowActions={(r) => [editAction(r), createDeleteAction({ id: r.id, label: r.postName })]}
  batchDelete={{ onDelete: (keys) => postApi.batchDelete(keys), target: "岗位" }}
  rowKey="id"
/>
```

## 2. SearchForm 并入形态——schema 驱动为主，children 逃生

**决策：受控 schema（`SearchField[]`）为默认形态。** 理由：SC2 的行数下降只有 schema 能给出可静态验收的量化（每个字段 1 行配置 vs 4-6 行 JSX）；抽样三页搜索区全部是「label + Input/Select + 占位符」同构样板，无一需要逃生口才能表达。schema 覆盖不了的（级联/树选择联动）走 `searchChildren` 自行渲染。

```ts
type SearchField =
  | { type: "input"; name: string; label: string; placeholder?: string }                    // → AppInput
  | { type: "select"; name: string; label: string; options: Option[] }                      // → AppSelect
  | { type: "remoteSelect"; name: string; label: string; fetcher: ...; ...RemoteSelectProps } // → RemoteSelect（§4）
  | { type: "custom"; name: string; render: (value: unknown, onChange: (v: unknown) => void) => React.ReactNode }; // → 任意受控控件（render 收 value/onChange，由 SearchForm 接入 filters 状态）
```

- 渲染端点**只允许** AppInput / AppSelect / RemoteSelect / custom.render——SearchForm 内部不出现裸 `<Input>`/`<Select>`（65 §3 lint 豁免只覆盖 `components/ui|shared` 目录，SearchForm 落在 shared 内天然豁免，但契约上仍禁止）。
- 提交行为：搜索 → `useTableManager.handleSearch`（filterEmpty 过滤空值、回第 1 页）；重置 → `handleReset`（清 filters 持久化 + 清排序）；Enter 触发搜索（AppInput `onPressEnter`）。
- 搜索/重置按钮文案：`搜索` / `重置` / `刷新`（63 既有惯例，含 aria-label+title，64 FIX-05 口径）。

## 3. COMP-04 — FormModal 契约

### 决策：BaseEditModal 之上的契约化升级，非替换

FormModal **内部渲染 BaseEditModal**（底座职责不变：maskClosable=false / keyboard=false / destroyOnHidden / memo），在其上补三件 BaseEditModal 没有的契约：内建 Form 实例、脏检查确认、提交防重的标准实现。BaseEditModal 对外保留（存量 2 消费页零破坏），新代码一律 FormModal。

```tsx
// src/components/shared/FormModal.tsx
interface FormModalProps {
  open: boolean;
  title: string;
  /** 提交动作：收到 validateFields 结果；抛错即失败路径（弹窗保持打开） */
  onFinish: (values: Record<string, unknown>) => Promise<void>;
  onCancel: () => void;
  /** 编辑回填：open 变 true 时 setFieldsValue */
  initialValues?: Record<string, unknown>;
  width?: number;
  okText?: string;   // 默认 "保存"
  /** 脏检查开关（默认 true）；纯只读/确需静默关闭的场景显式 false + 注释原因 */
  dirtyCheck?: boolean;
  children: React.ReactNode | ((form: FormInstance) => React.ReactNode);  // Form.Item 集合；form 实例两种获取方式二选一：children 传函数 `(form) => ...`，或业务侧 `useFormModalForm()`（组件内部暴露 form 实例 hook）
}
```

| 维度 | 契约 |
|------|------|
| confirmLoading 防重 | **onOk 返回 Promise 路线**（63 STOP-04 方案 1）：组件内部包装 onFinish，antd 自动 loading + 拦截重复 onOk；提交期间取消按钮禁用（`cancelButtonDisabled` = 提交中，BaseEditModal 既有 prop）——不再要求业务页手写 `submitting` state |
| 脏检查 | **isFieldsTouched 路线（决策）**：`onCancel` 触发时若 `form.isFieldsTouched()` 且非提交中 → 弹 `Modal.confirm`（文案见 Copywriting）确认后才关闭；未触碰则直接关。**与 64 T3 口径的一致性**：64 的「关死遮罩/ESC」保留为底座（BaseEditModal 默认值不变，遮罩/ESC 永不发 onCancel 语义上的静默关闭——它们不触发脏检查弹窗，直接无响应）；FormModal 的脏检查只覆盖**显式取消按钮**路径——这正是 64 UI-SPEC §2 留下的「关闭动作归 Phase 66 脏检查」的承接点，两条路径互补不冲突。`dirtyCheck={false}` 是显式逃生口（同行注释原因），对应 64 对「只读详情类」的豁免口径 |
| destroyOnHidden | BaseEditModal 已内建 `destroyOnHidden`；FormModal 补齐语义：open=true 时 `resetFields()` + `setFieldsValue(initialValues)`，杜绝上次编辑残留（STOP-04 时代手写弹窗的高频 bug） |
| 提交失败 | onFinish 抛错 → FormModal 内部 `isFormValidationError` 前置分流（表单校验静默，antd 行内提示）→ 其余 `handleApiError(error, "保存")`（64 FIX-04 catch 三分支），**弹窗保持打开可重试**；成功路径由调用方在 onFinish 内 `message.success`（成功文案句式归 Phase 68，不强制） |
| 确认按钮防重语义 | 与 65 ConfirmDelete 的 onOk Promise 同一规则——提交中不可关闭、不可重复提交（63 STOP-04 同源） |

脏检查确认弹窗文案：

| Element | Copy |
|---------|------|
| 标题 | `更改尚未保存` |
| 内容 | `当前修改尚未保存，关闭后将丢失，是否确认关闭？` |
| okText / cancelText | `放弃更改` / `继续编辑` |
| ok 按钮语义 | 默认非 danger（丢弃更改是普通确认，不是删除；不套 ConfirmDelete 模板） |

## 4. RemoteSelect 实现契约（兑现 65 §2.3 锁定 API）

**API 逐字兑现 65 §2.3，不另起**：`fetcher(keyword) => Promise<Option[]>`、`debounceMs=300`、`initialOptions`，props 为 `AppSelectProps` 子集（`Omit<"options"|"onSearch"|"loading">`）——可无缝替换 AppSelect 位置。

| 维度 | 契约 |
|------|------|
| 防抖 | 输入经 `debounceMs`（默认 300）防抖后调 fetcher；**竞态守卫必须内建**：仅采纳最后一次请求结果（递增 requestId 比对），慢响应不得覆盖新结果 |
| 首屏 | 渲染 `initialOptions`（无则空态）；keyword 清空（allowClear 或删空输入）→ 回退 `initialOptions` 并**不发请求** |
| loading | 请求中 antd `loading` 态内建（透传 Select loading） |
| 失败 | catch → `handleApiError(error, "搜索选项")`（64 FIX-04 唯一出口）+ **保留上次成功选项**；不得清空、不得静默 console |
| 缓存 | **不做跨实例/持久缓存（决策）**：每次防抖触发都真实请求。理由：fetcher 语义是后端实时搜索，缓存会引入脏数据面（字典/用户列表随时变更），且无消费方提出性能诉求；单实例内的「上次选项保留」已是失败路径的最小兜底。Phase 67 迁移中出现真实性能问题再加，不预先设计 |
| 与 SearchForm 接入 | SearchField `type: "remoteSelect"` 直接铺张本组件；`initialOptions` 由页面在打开时传入（如打开编辑弹窗时已知的当前值选项），避免回显丢 label |
