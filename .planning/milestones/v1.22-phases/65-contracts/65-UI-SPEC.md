## 1. COMP-01a — AppInput 契约

### API 表

```tsx
// src/components/ui/AppInput.tsx
import { Input } from "antd";
import type { ComponentProps } from "react";

export type AppInputProps = ComponentProps<typeof Input>;

/** 契约封装：默认 allowClear，其余 props 全量透传 antd Input */
export function AppInput({ allowClear = true, ...rest }: AppInputProps) {
  return <Input allowClear={allowClear} {...rest} />;
}
```

| Prop | 类型 | 默认 | 契约 |
|------|------|------|------|
| `allowClear` | boolean | `true` | **唯一由封装接管默认值的 prop**；显式传 `false` 必须仍然生效（逃生口，见下） |
| 其余全部 props | `ComponentProps<typeof Input>` | antd 默认 | **rest 全透传**，封装不吞、不改名、不包装任何其它 prop（`placeholder`/`prefix`/`onPressEnter`/`status`/`className`/`ref`/`onChange` 等行为与裸 Input 完全一致） |

### 行为契约

1. **rest 策略（决策）**：只接管 `allowClear` 一个默认值，其余 antd Input props 一律透传。理由：接管面越大，与 antd 升级的漂移面越大；根因只是「antd 默认 false、逐处手写必然漏」，一个默认值就解决 219 处缺失的根因。同理**不引入 `AppTextarea`/`AppPassword` 等子组件封装**——`Input.TextArea` 等 40 处通过 `AppInput` 不覆盖，本 phase 不扩面（审查方案 §「必抽 6 项」仅点名 AppInput/AppSelect；TextArea 的 allowClear 需求归 Phase 66 FormModal 按需评估）。
2. **显式覆盖合法性**：`allowClear={false}` 是合法逃生口（业务确需无清除框时），但必须**同行注释原因**（沿用 64 FIX-02 对 BaseEditModal 显式 `true` 的注释惯例）。lint 不拦截显式 `false`。
3. **同名同签名别名**：`src/components/ui/` 目录与其 `index.ts` 均为**本 phase 新建**（现网无此目录，checker 已核）；index.ts 导出 `export { AppInput as Input }`（审查方案 §523 迁移策略），供存量迁移退化为只改 import 行；**新代码必须用具名 `AppInput`**（别名仅供 Phase 67 存量迁移降险，lint 规则认 import 路径不认局部名）。
4. **ref/受控语义不变**：forwarded component（React 19 可直接 `ref` 透传），`value/onChange` 受控行为与 antd 完全一致——这是「行为与全站一致」（SC1）的硬性要求，封装不得加 debounce/trim 等隐性行为。

示例：

```tsx
// 零配置：自动可清除
<AppInput placeholder="请输入用户名" value={q} onChange={(e) => setQ(e.target.value)} />

// 逃生口：显式关闭 + 注释原因
<AppInput allowClear={false} /* 密码框清除会连剪贴板一起暴露 */ type="password" />
```

## 2. COMP-01b — AppSelect 契约

### API 表

```tsx
// src/components/ui/AppSelect.tsx
import { Select } from "antd";
import type { ComponentProps } from "react";

export type AppSelectProps = ComponentProps<typeof Select>;

/** 契约封装：默认 allowClear + showSearch 自动策略，其余全透传 */
export function AppSelect({ allowClear = true, showSearch, options, ...rest }: AppSelectProps) {
  const count = Array.isArray(options) ? options.length : 0;
  return (
    <Select
      allowClear={allowClear}
      showSearch={showSearch ?? count >= 8}
      optionFilterProp={rest.optionFilterProp ?? "label"}
      options={options}
      {...rest}
    />
  );
}
```

| Prop | 类型 | 默认 | 契约 |
|------|------|------|------|
| `allowClear` | boolean | `true` | 同 AppInput，显式 `false` 合法（同行注释原因） |
| `showSearch` | boolean | `options.length >= 8` 时自动 `true` | **自动策略（决策）**：采纳审查方案 §374 的「选项数 ≥ 8 自动开搜索」；显式传 `true`/`false` 覆盖自动值。理由：Select 399 处 showSearch **0 命中**说明靠自觉已证伪；阈值 8 是审查报告给定的最佳实践口径 |
| `optionFilterProp` | string | `"label"` | showSearch 开启时必须有过滤维度，默认按 `label` 过滤；`filterOption` 自定义函数照常透传（传入时优先于 prop 过滤，antd 原生语义） |
| `mode="multiple" \| "tags"` | — | — | 合法透传；多选模式下 allowClear 默认行为由 antd 原生处理（有值显示清除），封装不特判 |
| 其余全部 props | `ComponentProps<typeof Select>` | antd 默认 | rest 全透传（`loading`/`onSearch`/`labelInValue`/`fieldNames` 等），含泛型 options |

### 行为契约

1. showSearch 自动开启时**必须**有可用过滤路径（默认 `optionFilterProp="label"`）；如果页面 options 的展示字段不叫 `label`（用了 `fieldNames`），由调用方显式传 `optionFilterProp` 或 `filterOption`——这是透传而非接管。
2. 远程数据（options 异步到达）同样适用 ≥8 阈值：数据到达前 count=0 不开搜索、到达后自动开——无额外成本。
3. 不接管任何数据请求行为；远程搜索（输入触发请求）**不在 AppSelect 职责内**，归 RemoteSelect（§2.3）。

### 2.3 RemoteSelect — 仅定契约，本 phase 不交付（决策）

**决策**：RemoteSelect 本 phase **只锁定 API 契约，不写实现**。理由：

1. ROADMAP Notes locked 说「useDebouncedSearch 并入 RemoteSelect 不单独抽」——这约束的是**抽件边界**（不造独立 hook），不是交付时限；且现网 `useDebouncedSearch` 0 命中，无存量消费者等待迁移。
2. 它的真实消费方是 Phase 66 PageTable 的 SearchForm 远程字典/搜索字段。没有消费方的组件提前交付 = 无验收锚点；Phase 66 交付 SearchForm 时按本契约实现，天然有集成验收。
3. **锁定契约**（Phase 66 实现必须满足，不得另起 API）：

```tsx
interface RemoteSelectProps extends Omit<AppSelectProps, "options" | "onSearch" | "loading"> {
  fetcher: (keyword: string) => Promise<Option[]>;  // 搜索词 → 选项；内部自带 debounce（并入语义，无独立 useDebouncedSearch）
  debounceMs?: number;                               // 默认 300
  initialOptions?: Option[];                         // 首屏预置选项（打开即见，无需先输入）
}
```

- 行为要求：首屏渲染 `initialOptions`（无则空）；输入经 `debounceMs` 防抖后调 `fetcher`；请求中 `loading` 态（antd 内建）；失败走 `handleApiError`（64 FIX-04 出口）并保留上次选项；keyword 清空时回退 `initialOptions`。
- API 即 `AppSelectProps` 的子集 + `fetcher`——保证它可无缝替换 AppSelect 的位置（SC1「行为与全站一致」的延伸）。

**规则边界说明**：

2. **豁免清单放 eslint 配置的目录 override（决策）**，不放组件内部白名单：

4. `<Input.TextArea|Search|Password|OTP>` 的 JSX 名字是 `Input.TextArea` 等成员表达式，**不在本 selector 命中面**（本 phase 有意不拦，见 §1 行为契约 1；Phase 66 评估后如需拦截再加成员表达式 selector）。
5. **存量处置**：规则以 error 上线当日，存量命中（`<Input` ~265 文件命中、`<Select` ~80 文件、`Modal.confirm` 74 处）会使 lint 全红。两个合法选项，PLAN 二选一：**(a)** 存量命中文件列入 eslint 配置的「存量豁免 override」`files` 数组并注释 `// P67 收敛后移除`（可脚本生成，规则严格、清单可见）；**(b)** 规则先 `warn` 上线、Phase 67 完成迁移后转 `error`（零清单维护，但 warn 期 SC2 的「拦截」弱化为「提示」）。**推荐 (a)**——SC2 原文是「被 lint 拦截**或**有明确豁免清单」，(a) 两者兼得且清单自带偿还期限。

## 4. COMP-02 — ConfirmDelete 契约

### 决策：声明式组件 + 命令式 helper 双形态，确认口径衔接 63 的 Modal.confirm

**63 落地口径优先（任务书要求）**：63 T4 实际落地是「handler 内包 `Modal.confirm`」而非替换 BatchDeleteButton（`63-P0-SUMMARY.md:16/:26` D3），文案 `确认批量删除 / 将删除选中的 {N} 项，删除后不可恢复，是否继续？/ 删除 / 取消 / danger`。**ConfirmDelete 把这个事实口径契约化，不另起炉灶**：内部仍是 `Modal.confirm`（App 上下文实例），把 74 处复制样板（确认文案 + okButtonProps.danger + onOk Promise loading + 成功 message + 失败 handleApiError）收敛为一处实现。选 `Modal.confirm` 而非 Popconfirm 作统一确认形态的理由：① 63 全量批删与多数存量单删已是 Modal.confirm，迁移成本最低；② Modal 容纳「操作对象 + 不可恢复警示 +（可选）extra 内容」的长文案，Popconfirm 气泡承载不了 SC4 要求的文案模板；③ 02 分片审计结论同向（「Popconfirm 仅用于行内轻量删除」的旧建议被 SC3 的「无绕过入口」取代——行内删除也必须走同一入口）。

### API 表

**声明式（默认形态，按钮内嵌场景）**：

```tsx
interface ConfirmDeleteProps {
  /** 操作对象描述，进入确认文案。如 "用户 张三"、"选中的 3 项资产" */
  target: string;
  /** 确认后执行的删除动作；抛错即失败路径 */
  onDelete: () => Promise<void>;
  /** 触发按钮内容；缺省渲染 danger "删除" 按钮（icon=DeleteOutlined） */
  children?: React.ReactNode;
  /** 确认标题，默认 "确认删除" */
  title?: string;
  /** extra 确认内容（如 menu 级联删除的复选项，01 分片 :81 的 hack 收敛点） */
  extra?: React.ReactNode;
  disabled?: boolean;
}
```

**命令式（handler 内场景，63 风格）**：

```ts
// @/components/shared/confirmDelete.ts
interface ConfirmDeleteOptions {
  target: string;                       // 操作对象（必填，进文案）
  onDelete: () => Promise<void>;
  title?: string;                       // 默认 "确认删除"
  extra?: React.ReactNode;
}
export function confirmDelete(opts: ConfirmDeleteOptions): void;
```

| 维度 | 契约 |
|------|------|
| 确认形态 | `Modal.confirm`（组件与 helper 共用 `confirmDelete.ts` 内部唯一实现；业务代码直接 `Modal.confirm` 被 §3 lint 拦截） |

### 行为契约与示例

```tsx

```

1. `BatchDeleteButton` **保留组件本体**（页面已接它的调用点零破坏），内部 Popconfirm 替换为 `confirmDelete` helper，`selectedCount` 自动进 target → 按钮文案 `批量删除 ({N})` 保留；确认文案含 N 的行为由迁移后的 target（`选中的 {N} 项…`）承接——注意现状 `confirmTitle` 默认是 `BATCH_DELETE_CONFIRM.title` 常量、**不含 N**，含 N 确认文案是 63 handler 内 `Modal.confirm` 的既有行为（63 SUMMARY:16），本迁移把两者统一到 helper（增量化改造，props 全部不变）。
2. `createDeleteAction`（`ActionButtons.tsx:113`）对外 `ActionButton` 接口不变，内部 `render` 改为渲染 ConfirmDelete——ActionButtons 全部消费页自动获得 SC3 合规（63/64 已给 ActionButtons 建立「改一处全片生效」先例）。
3. **不新建 `useConfirmAction`/`withConfirmSubmitting` 等 hook**（63 SUMMARY:89 与 01 分片 :220 均提过候选）：ConfirmDelete 双形态已覆盖声明式与命令式两个场景，再抽 hook 就是第三条路径，违反「唯一入口」。
