### §1.5 Popconfirm → Modal 强确认（用户可感知的行为变更）

**变更前**：轻量气泡确认（`Popconfirm`），点击目标即弹，无遮罩，气泡被页面滚动/遮挡时可能点不中，危险按钮与普通按钮同权重。

**变更后**：Modal 强确认（`ConfirmDelete` / `confirmDelete`），有遮罩、标题固定、内容含对象与不可恢复警示、确认按钮为 danger、提交期间禁用取消与重复提交、失败有明确反馈并保持弹窗可重试。

**用户预期**：删除动作从"随手一点的小气泡"变成"必须确认的正式弹窗"——这是**有意加强**，不是回归。回归判据：点删除后弹窗**不出现**或**文案缺对象名**才算缺陷。**已知形态变更**：原气泡按 Esc 即取消，新弹窗按 Esc **不关闭**（`keyboard: false`，§1.7），须点「取消」——属同一方向的加强，一并登记在 §8 第 10 条。

**14 处目标清单**（FACTS A.1⑤，含 `src/components/shared/ImageGallery.tsx:175-176` 的「确定要删除这张照片吗？」，该处为 65-VERIFICATION 已点名残留）以 FACTS 为准，PLAN 阶段逐条列 文件:行号。

**不设例外**：删除类 Popconfirm 一律升级为 Modal 强确认（用户 2026-10-26 裁定）；FACTS A.1⑤ 另记 1 处**非删除** Popconfirm（`src/components/operations/WorkstationDeviceTable/index.tsx:479`「设为主设备」），按 §1.1 判定口径属非删除非危险，不在本 phase 升级范围，但须补 `eslint-disable-next-line` 理由注释并登记进 §4 理由表。

### §1.7 提交中的表现

- `onOk` 返回 Promise → antd 自动给确认按钮 loading 并防重复提交（`confirmDelete.ts:40-50` 依赖此行为）。
- 提交期间**取消按钮必须禁用**（Phase 63 STOP-05 / Phase 64 FIX-02 契约）——`confirmDelete` 现状未见 `cancelButtonProps.disabled`（`confirmDelete.ts:34-40` 的 `Modal.confirm` 参数里无该键），本 phase 需补齐；写法与仓库既有载体一致：`cancelButtonProps: { disabled: true }`（参照 `src/components/modal/BaseEditModal.tsx:57` 的 `cancelButtonProps={{ disabled: cancelButtonDisabled }}`）。
- 弹窗在提交期间**不得被遮罩点击或 Esc 关闭**（`maskClosable: false` / `keyboard: false`）。仓库既有 20+ 处已用该写法（如 `src/pages/network/devices/components/DeviceModals.tsx:91-92`），本 phase 沿用同一 prop 名以与 Phase 64 FIX-02 口径一致（注：antd 6.6.4 已提供新式 `mask.closable`，但既有代码未迁，本 phase 不引入新写法以免同页两种口径）。
- 失败时弹窗**保持打开**可重试（`confirmDelete.ts:48` rethrow）。

### §1.8 失败反馈

- 唯一出口 `handleApiError(error, "删除")`（`src/utils/errorHandler.ts:136`）。
- 禁止在调用点写裸 `message.error` / `console.error`。
- 批量删除失败的文案需体现"批量"语义（"删除"动作词可保留，但需在 SC 验收中确认与单删可区分——**待 Lead 定稿，见 Checker Sign-Off 开放问题 Q4**）。现状 `confirmDelete.ts:47` 的 context 硬编码为「删除」。

### §1.9 非删除类破坏性操作变体（10 处）

「清空缓存 / 清空日志 / 恢复配置 / 取消执行 / 撤回通知」等操作语义不是"删除"，直接套用「将删除X，删除后不可恢复」文案不贴切。

**10 处清单**：FACTS A.1③（`68.1-FACTS.md:104-113`）—— `src/pages/monitor/cache/index.tsx:188`、`src/pages/monitor/logs/hooks/useLogActions.tsx:44`、`src/pages/monitor/logs/index.tsx:184`、`src/pages/network/backups/index.tsx:197`、`:238`、`src/pages/network/backups/modals/RestoreModals.tsx:161`、`src/pages/network/command/columns.tsx:101`、`src/pages/network/executions/columns.tsx:127`、`src/pages/system/notice/components/NoticeList.tsx:236`、`src/pages/system/manager-orgs/index.tsx:196`。

**契约要求**：
1. 复用同一入口（`confirmDelete` / `ConfirmDelete`），**不新建第三套确认组件**（Phase 65 已 locked「不新建 useConfirmAction / withConfirmSubmitting 第三路径」）。
2. 允许在 `ConfirmDeleteOptions` 上做**向后兼容的可选扩展**：`actionLabel?: string`（确认按钮文案，默认「删除」）、`contentText?: string`（正文模板，默认 `将删除${target}，删除后不可恢复，是否继续？`）。
3. 非删除类破坏性操作取用：`actionLabel` = 「清空」/「恢复」/「取消」等动词，`contentText` = `将{target}，操作不可恢复，是否继续？`。
4. `okButtonProps.danger` 语义保持：破坏性操作一律 danger。
5. 成功后提示沿用 `getAppMessage().success(...)`，文案按动作词区分（「已清空」等）——注意现状成功文案硬编码在 `confirmDelete.ts:43`（`"已删除"`）、失败 context 硬编码在 `:47`（`"删除"`），扩展 `actionLabel` 时这两处须同步派生，否则会串成「已删除」/「删除失败: …」。

> 实现层 API 命名与是否合并到同一 options 接口，由 PLAN 阶段定稿；**不得**为此新建第二个组件文件。

### §4.4 落地机制（约束，不指定具体实现）

- 豁免清单的**权威落点**在 `eslint.config.js` 锚点段（lint 需要它），理由**不得**写在会被生成脚本覆盖的位置。

- 幂等要求：连续两次跑生成脚本，锚点段与理由清单均无 diff（Phase 67 已建立该基线：P65 140 / P66 41）。

## §7 无障碍与键盘

- 确认弹窗：Tab 循环不逃出弹窗由 antd Modal 原生提供；Esc 行为与 `keyboard` 透传一致（危险操作默认 Esc 不关闭，Phase 64 FIX-02 口径，§1.7）。**焦点落点现状未定义**——`confirmDelete.ts:34-40` 的 `Modal.confirm` 参数未设焦点策略；antd 6.6.4 支持 `focusable={{ autoFocusButton: "ok" }}`（`node_modules/antd/es/modal/interface.d.ts:161-163`；旧的 `autoFocusButton` 已 @deprecated），本 phase 建议显式设为 `"ok"`，使读屏用户先听到 danger 确认按钮。
- 行操作删除按钮：Phase 64 FIX-05 口径（`64-UI-SPEC.md:28`、其 §5）是「**icon-only 按钮**必须带 `aria-label` + `title`，且 `aria-label` = 按钮动作名（人类可读中文，如「刷新」「删除」），**非 icon-only 按钮不强制**」。本 phase 要求在 64 口径之上加严为「删除按钮的 `aria-label` 须含对象名（如「删除 楼宇A座」）」——**现状不满足**：`src/components/shared/ConfirmDelete.tsx:40` 取 `aria-label={typeof title === "string" ? title : "删除"}`，而 `createDeleteAction` 传入的 `title` 是确认弹窗标题 `DELETE_CONFIRM.title`（`ActionButtons.tsx:136-147`），实际可访问名为「确认删除」：既不等于动作名「删除」，也不含对象名。修法三选一，见 Checker Sign-Off 开放问题 Q1。
- 弹窗提交中：`aria-busy="true"` 挂在确认按钮容器。antd 的 `confirmLoading` 只加 loading class、**不**产出 `aria-busy`，需显式补。
- 批量删除按钮：按钮是**非 icon-only**（可见文本 `批量删除 (N)`，`src/components/shared/BatchDeleteButton.tsx:68`），数量已在可见文本内；按 64 FIX-05「非 icon-only 按钮不强制 `aria-label`」，现状（`BatchDeleteButton` 无 `aria-label`）**已满足**契约。若 Lead 仍要求冗余 `aria-label`（如「批量删除 3 项」），见开放问题 Q2。
- 错误态：错误提示用 antd `Alert` / `message` 的可读文本，不只用颜色区分。
- 本 phase 迁移页不得引入 `aria` / `role` / `tabIndex` 为 0 的新交互元素。可访问性基线出处修正：Phase 63 把可访问性整体归 Phase 64 FIX-05（`63-UI-SPEC.md:222`），其事实基线是「全前端（非测试）`aria-label|role=|tabIndex` 合计仅 **20 处**，`pages/monitor` + `components/network` 域为 **0**」（`64-UI-SPEC.md:28`）——计数低是**缺口**不是达标，故新增交互元素必须带语义。
