<objective>
Wave 1 of operlog full coverage: instrument 47 write endpoints across the 6 system core modules (user / role / dept / menu / dict / post) with one-line `operlog.Record` calls. Each module's handler gains 1 recordOperLog line per write handler at the end of its success path, before the success response. Module names in Chinese match the audit report and the existing AD pattern (e.g., "用户管理", "角色管理"). Each handler that does not yet have a `core *core.Core` field is updated to add one (and its constructor and router are updated accordingly).

**WARNING 4 addressed (SM2+SM4 compatibility):** `operlog.RecordWithBody` (the new helper from Plan 34-01) reads `c.Request.Body` via `c.GetRawData()` and restores it with `io.NopCloser(bytes.NewBuffer(...))`. This must be compatible with the SM2+SM4 encryption middleware that ALSO reads and replaces `c.Request.Body` during decryption. The two are compatible AS LONG AS RecordWithBody is called AFTER the SM2+SM4 middleware runs (i.e., in the handler itself, not in another middleware) — the middleware decrypts first, restoring the body to plaintext; then the handler reads the plaintext body via RecordWithBody and restores it again; then the handler's `ShouldBindJSON` reads from the restored plaintext body. This plan includes an explicit integration test (TestResetPassword_SM4MiddlewareCompat) that POSTs through the full middleware chain and verifies the round-trip works.

Purpose: System core is the highest-traffic, most-audited module set. Without operlog coverage on user/role/dept/menu/dict/post, the system cannot answer "who changed role X yesterday" or "who deleted user Y" — the two most-asked questions in any admin audit. This wave delivers those answers with the minimum code change per endpoint.

Output: 6 handler files + 6 router files modified; 47 endpoints instrumented; 1 integration smoke test verifying SM2+SM4 compatibility; module-level go test still passes; build still passes.
</objective>

    Use `operlog.RecordWithBody(c, h.core.OperLogService, h.core.GetDB(), "用户管理", operlog.OperTypeReset)` — this is the body-aware helper from Plan 34-01 that:
      1. Reads c.Request.Body via c.GetRawData() (which works whether the body is plaintext OR has been decrypted by SM2+SM4 middleware running earlier in the chain).
      2. Restores c.Request.Body via io.NopCloser(bytes.NewBuffer(raw)) so downstream c.ShouldBindJSON still reads from a valid reader.
      3. Applies operlog.FilterSensitiveParams(string(raw)) to mask password fields before recording.

    The handler flow for ResetPassword becomes:
    ```
    func (h *UserHandler) ResetPassword(c *gin.Context) {
        var req ResetPasswordRequest
        if err := c.ShouldBindJSON(&req); err != nil { ... }   // 1. SM2+SM4 middleware has decrypted the body; bind reads plaintext
        if err := h.userService.ResetPassword(...); err != nil { ... }
        operlog.RecordWithBody(c, h.core.OperLogService, h.core.GetDB(), "用户管理", operlog.OperTypeReset)  // 2. After all binding is done
        response.Success(c, nil)
    }
    ```
    Note: RecordWithBody is called AFTER ShouldBindJSON, so it does NOT interfere with binding. It also restores the body, so any downstream middleware/handlers that re-read c.Request.Body still get valid data.
