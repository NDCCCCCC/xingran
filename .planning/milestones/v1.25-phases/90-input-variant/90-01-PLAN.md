# Plan 01 — W0 基线与工具：90-QUANT-SNAPSHOT 起点 + 矩阵工具 90 化 + before 快照

## Context

Phase 90 是 **Input 域**的变体交还 + 圆角统一（W1 单一 commit）。本 plan **零业务代码改动**，只做三件事：

1. **落起点快照**（M1-M16 口径沿用 89，避免 90 终值无法归因）。
2. **把 89 的矩阵工具改造成 90 口径** —— 关键差别有两条：
   - 89 的判据是「**light 差异必须 = 0**，dark 差异 > 0」（浅色零漂移红线）；**90 的变更本来就是明暗双向**（圆角 6→8 在 light/dark 都变）→ 90 的判据改为「**light 与 dark 差异都 > 0，且每条差异都必须归入登记类别 a/b/c，未归类 = exit 1**」，并保留「差异总数 = 0 = 恒等空跑 = FAIL」的防空跑红线。
   - 89 的登记表只有 A/B 两类；90 按**变更类别**登记三类：**a 圆角 6→8 / b InputNumber 错误态红 / c 可选 font-size**。
3. **采 before 快照**。此处做一处**对 Lead 约束的显式裁定**：Lead 的文件边界写 `.planning/phases/90-input-variant/89-visual-evidence/`，而 90-RESEARCH.md §1 写 `90-visual-evidence/`（与 88/89 的 `<phase>-visual-evidence/` 命名惯例一致）→ **本 phase 一律用 `90-visual-evidence/`**，`89-visual-evidence/` 视为 Lead 笔误；两个目录名不得同时存在。

**before 快照不复用 89 的 `after-*.json` 直接复制**（研究 §6 W0 原写「复制 89 after-*.json → 90 before-*.json」），理由：90 的 fixture 要新增 `f22_input_number_status_error` 形态（VISFIX-05 的 b 类落点），89 的 21 形态快照里没有该形态，复制后 f22 会被判「结构缺失」而误 FAIL。改为**在 90 的 fixture 下重采一次 before**，并把「89 `after-*.json` 与 90 `before-*.json` 的 21 形态交集逐格一致」作为**防串基线核对**（证明 90 起点确实等于 89 终态）。
