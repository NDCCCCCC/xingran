# Plan 04 — PMODEL-01：用户列表接入 data_scope

## Context 与关键裁定

**模式来源（不从零设计）**：`internal/api/v1/vdi/vm_handler.go:87-101`（handler 从 gin context 提取 `user_id`/`data_scope` 作函数参数传 service）+ `internal/services/vdi/vm_data_scope_filter.go:17-100` + 测试样板 `vm_service_test.go:498-543`。**不接** `ApplyDataScopeFromContext`（c.Set 只进 gin.Context，service 拿不到；且其 Self 分支有 bug）。

**⚠️ `ApplyDataScope` Self 分支 bug（permission.go:575）**：`case DataScopeSelf: return db.Where(deptField+" = ?", userID)` —— deptField 是部门列名却比对 userID（user id ≠ dept id）。**不得照抄**。本 plan 对 users 表的正确语义是 `sys_user.id = ?`（= userID）。permission.go 侧只在注释标注该函数「Self 分支仅适用于用户维度字段」并指向 filter 的新实现，**不做大重构**。

**⚠️ 列表缓存是最大隐性坑（user_cache_impl.go:157-191）**：`buildListCacheKey`（:172-191）key 由 username/nickname/phone/status/dept… 组成，**不含 scope/用户维度**；scope 过滤进 service 而 key 不加维度 = 跨用户数据泄漏。**方案裁定：缓存 key 加 scope 维度**（`data_scope` 维度 + userID；scope=1 时可省 uid 段）——保留 10min 缓存收益，且 V3 验证可直接测「同 params 异 scope 双用户不串」。

**挂载点裁定（研究 §A6 影响面圈定表，locked）**：只接 **usersRead 的 list（必须）+ statistics（同批同 query builder，成本≈0）**；usersWrite 不接（handler 均按 id 操作，无列表语义；data_scope 对写的语义超范围）；depts 不接（router.go:262 显式「组织全树低敏感」决策）；vms 已消费不动；其它列表不做（Phase 85 边界）。

**实现路径**：DeptChild 走 `sys_dept.ancestors` 5 条件单查询（复用 user_service.go:427-435 RecursiveDeptID 同款），**不用**递归 getChildDepts（每请求 N 次往返）。过滤分支必须插在 `Count`（:449）**之前**，否则 total 仍全量（假过滤）。

**回归红线**：admin（isSuperAdmin 早退、context 无 data_scope → params 零值 → 不过滤）与 data_scope=1（All 原样返回）行为零变化；v1.24 #16 验收角色行为不受 403 判定影响（scope 过滤在权限中间件之后的 service 层）。零新依赖。

## Threat model

本 plan 直接触碰**数据可见性**，两个必须被测试锁死的威胁：
1. **跨用户数据泄漏（最高）**：scope 过滤进 service 而缓存 key 无维度 → A 用户的受限列表被 B 用户从缓存命中。防线 = Task 4.3 的 ScopeIsolation 测试（must_have 级，双用户互查断言）。
2. **scope 绕过 / 假过滤**：过滤加在 Count 之后（total 泄漏全量规模）；Self 写成 `dept_id = userID`（id 空间错位，可能意外匹配或漏匹配）；未知枚举值不 fail-closed。防线 = 逐档 count 断言 + fail-closed 用例 + 源码 diff review（Count 前置、`sys_user.id` 形态）。
3. **输入伪造**：DataScope/DataScopeUserID 必须 `json:"-"`，只由 handler 从中间件写入的 gin context 提取——客户端不能通过请求体注入 scope（acceptance 里 json tag 断言即为此设）。
