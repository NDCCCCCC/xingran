# Plan 03 — RBAC-01：全站写组 ANY-of 拆分（按域分批）

## Context

规模（源码重扫口径，85-RESEARCH §B）：受保护挂载组 34 个中 ANY-of 混合读写组 29 个（~91 条写路由）+ system 4 组（85-02 已拆 ~20 条）≈ **33 组 / ~110 条写路由**。本 plan 处理 system 4 组之外的 ~29 组，主要分布：ops 13 组（router.go:590-961 区段）、network 8 组（network_router.go:63/84/105/127/159/196 等）、system ad_domain/manager_rule 6 组（其中 ad account edit/delete 组已逐动作单码，只差 Require→Strict 一词）。

**⚠️ 「全站」边界（Lead 裁决 2）**：= **已有权限挂载的路由**。duty/knowledge/rpa/monitor cache 等无任何权限中间件的模块**不纳入 RBAC-01**（见「不做」）。

**⚠️ router.go 共享文件约束**：85-02 改 :230-289，本 plan 改 :590-961 区段 → **85-02 未合入前不得开工**（depends_on 已声明）；本 plan 内部 ops/network/system 三批也因共享 router.go 而**串行执行**，同域内各 `*_router.go` 互不相干可并行。

**⚠️ 窗口期显式声明**：与本 phase 全部拆分批次同源——拆分后、87 播种前，凡只持组级读码或页面本体 C 型码的现有角色，其对应域写操作会 fail-closed（新动作码无 F 型菜单则无法授予）。85 内不做数据补授（播种+`GrantNewMenuToRolesHavingParent` 补授归 87，菜单播种范式 `internal/core/db/migrations/menu_grant_helpers.go:26` 已带 PG-sqlite 双路径测试）。

**每域执行节奏（统一 SOP）**：
1. 动手前**重扫该域源码**（`node scripts/scan-routes.cjs`，tmp_routes.json 不可作事实源——system 4 组 0 条系统性缺口已实证）；
2. 拆路由：读组保留组级 ANY-of（含 WithQuery 的 queryExtra 读放行）；组内写路由搬出到 authorized **兄弟**写组，逐动作 `RequireStrictPermissions([单一码])`（gin Group 继承父中间件链，写组绝不做成读组子组）；
3. 权限码：**优先复用已有常量码**（单码组如 network:backup:restore 只需 Require→RequireStrict 一词，零新码）；仅当 ANY-of 组内无语义匹配的写码时新增常量 + TS 同批声明（零豁免，见 85-02 task 2.1 裁决）；
4. 登记死表 + 重扫 route-registry.json，TestRouteRegistry / check-route-registry.mjs 绿。

## 不做（边界）

- **不给无权限中间件模块加 RBAC**：duty / knowledge / rpa / monitor cache 等连 ANY-of 都没有的组（~411 条扫描口径路由）不在本 phase——给它们加保护是功能新增（REQUIREMENTS Out of Scope），登记为后续 phase 候选。
- 不改 RequirePermissions / RequirePermissionsWithQuery / checkUserPermission 既有语义（纯增量加 Strict 挂载，Phase 78 先例）；不动 data_scope（84 已完成）。
- 不播种 F 型菜单、不补授角色（87）、生产库零写入；不碰前端门控（86）。
- sqlite 不跑 API 级夹具（`ON CONFLICT` 方言坑，role_service.go:425-430）；决定性对照实验归 87 在 PG 跑（#79 范式：单事务夹具 + 清理自检）。
