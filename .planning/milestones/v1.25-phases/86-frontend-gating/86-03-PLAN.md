# Plan 03 — W3：network 域有码页三态门控铺开（7 页）

## Context

network 域是**动作语义最杂**的一域：既有标准 CRUD（凭据 / 模板 / 发现任务），也有非标准动作（备份「还原」「版本对比」、命令「快速命令」「取消执行」、凭据「设为默认」、模板「克隆」）。W3 因此不只是复制 W1/W2 的模式，还要处理**三类**特殊点（降级解析保留 / 非标准动作归码 / **还原与删除的区分 + 死 modal 甄别**）。

### 三个特殊点

#### 特殊点 1：devices 页的「门控键降级」机制必须保留（不是删除）

`hooks/useDeviceRowActions.tsx:104-117` 已实现一套**降级解析**：

```
readyPermissions = permGate.state === "ready" ? menuPermissions : []
editPerm = resolveDeviceActionPerm(readyPermissions, DEVICE_PERMISSION_CODES.edit)
// resolveDeviceActionPerm（:77-84）：权限集含动作粒度码 → 用动作码；否则 → 退回页面级码
```

这是 v1.24 已交付的**窗口期兼容**机制：87 播种前多数角色只有页面级码（如 `network:device:list`），若硬绑 `network:device:edit` 则编辑入口对所有现役角色消失（比后端 fail-closed 更严，破坏性更大）。**86 保留该机制，只扩面**（把采集端口 / 批量删除 / 批量导出 / 快速创建纳入门控），**不得**把降级解析改成硬绑动作码。

⚠️ 但降级解析里 `menuPermissions` 来自 `useMenuStore((s) => s.permissions)`（`:107`）—— 这是一处**旧式直读**（不是 `hasPermission` 自造判定，且不违反「唯一判定入口」的精神，但确实是第二真相源的一角）。本波**不删除**它（删了就破坏降级语义），但要在该行加注释说明「此处的 `permissions` 仅用于门控键降级解析，最终门控判定仍由 `useActionPermission` 的三态承担」。

#### 特殊点 2：非标准动作的码归属

| 动作 | 归属码 | 理由 |
|---|---|---|
| 备份「还原」（行操作 `:437`） | `networkBackup.restore` | 85-03 显式声明（`permissionCodes.ts:195`），后端有 F 型来源 → 零窗口期 |
| 备份「**还原确认**」（`confirmDelete` `:197` / `:240`、`RestoreModals.tsx:163-179`） | `networkBackup.restore` | **这两处 `confirmDelete` 不是删除** —— `title="确认恢复配置"` / `actionLabel="恢复"` / `successText="已恢复配置"`，内部调 `confirmRestore()` 落库 → 与还原同码（详见「特殊点 3」） |
| 备份「版本对比」 | `networkBackup.diff` | 同上（`:196`） |
| 命令「快速命令」 | `networkCommand.execute` | 执行类动作，TS 只有 `execute` 一个写码 |
| 命令 / 执行记录「取消执行」 | `networkCommand.execute` | 取消执行属于命令执行动作域；**不得**为它自造 `network:command:cancel` 码（86 零新增码） |
| 设备「采集端口」 | `networkDevice.edit` | 采集是对设备连接的操作，无独立码 → 归 `edit` |
| 凭据「设为默认」（`:322-327`） | `networkCredential.edit` | 状态写动作，无独立码 → 就近归 `edit`（该码组无 `setDefault` 键） |
| 模板「克隆」（`columns.tsx:125-130`） | `networkTemplate.edit` | 写动作（会落库），无独立码 → 就近归 `edit`（该码组无 `clone` 键） |

#### 特殊点 3：backups 页**没有删除入口** —— 「还原」绝不可挂 `networkBackup.delete`（MEDIUM-4）

`backups/index.tsx` 全文**没有任何真正的删除动作**：页面只有「还原」「版本列表」「版本对比」三个行操作 + 「创建备份」工具栏按钮 + 导出。两处 `confirmDelete`（`:197` / `:240`）的语义经源码核实为**还原 / 恢复配置**：

| 位置 | 语义证据 | 正确归码 |
|---|---|---|
| `backups/index.tsx:191-208` `handleConfirmRestore` | `confirmDelete({ title: "确认恢复配置", actionLabel: "恢复", actionContext: "恢复配置", successText: "已恢复配置", onDelete: async () => { await confirmRestore(); } })` | `networkBackup.restore` |
| `backups/index.tsx:238-254` `handleRestore` | `confirmDelete({ title: "确认恢复配置", actionLabel: "恢复", successText: "已恢复配置", onDelete: async () => { openRestoreModal(backup); await confirmRestore(backup); } })` | `networkBackup.restore` |
| `backups/modals/RestoreModals.tsx:163-179` | `confirmDelete({ title: "确认恢复到此版本", actionLabel: "恢复", successText: "已恢复配置", onDelete: async () => { await handleRestore(record); } })` | `networkBackup.restore` |

> ❌ **按字面执行会同时造成「误拒」与「越权」**：`confirmDelete` 的形参名天然诱导人把它当「删除」→ 若把 `:197` / `:240` 挂 `networkBackup.delete`（`permissionCodes.ts:194` 确有该键），则
> ① **持 restore 无 delete** 的用户**被误拒**（明明有权还原，按钮却消失）；
> ② **持 delete 无 restore** 的用户**可还原**（越权写 —— 把设备配置恢复到任意历史版本）。
>
> ✅ **正确口径**：`:197` / `:240` 一律标「**还原确认**」→ `networkBackup.restore`；决策变量名 `permDelete` → **`permRestore`**；源码注释写明「**本页无删除入口**，这两处 `confirmDelete` 承载的是还原动作」。

### 铺开模式

与 W1/W2 一致：`permission:` 传参（ActionButtons）+ 页面层条件渲染（工具栏 / 批量 / Excel）+ `decide().disabled`（独立按钮）。**`confirmDelete` 无 permission 位** → 调用点前置条件渲染（不改编排）。
