# Plan 05 — 批次二（7 条）补播 + 白名单归零（**默认挂起，等待 OQ-6 用户确认**）

## Context

### 本 plan 的前置是**人的确认**，不是代码

OQ-6（用户裁定，2026-10-30）：批次二的 7 条码**在播种清单内**，但其父菜单**待人工确认** —— 推断值是「楼层管理」（`perms='ops:floor:list'`，依据：前端 `src/pages/operations/floors/index.tsx:57` 使用 `PERMISSION_CODES.opsFloorPlan.edit`；后端写路由在 `internal/api/router.go:1146-1152 / 1178-1184 / 1206-1211` 挂在 `ops` 组下），但 **CAD 平面图编辑器的实际管理入口页可能是「楼宇空间」页而非「楼层管理」页**。

⇒ **父错了会导致「树展示错位 + Step 2 继承错位」⇒ 挂起优于猜错**（OQ-6 原裁定）。
⇒ 本 plan 的第一个 task 是 **`checkpoint:human-verify`**：向用户确认这 7 条的父菜单后才可执行后续 task。**未确认前不得播这 7 条。**

### 为什么是独立 migration 而不是并进 226

- 226 已落库执行（第一批 65 条已生效），**追加进 226 的种子表不会重新执行已记录的迁移**（`runAndRecord` 无版本比较、但记录表已写入 ⇒ 启动时仍会重跑 —— 这一点取决于 `runAndRecord` 的实现口径，**执行期须先读 `internal/core/db/database.go:1318-1335` 确认**）。
- **无论重跑与否**，独立的 227 让「哪 7 条、哪个父」这件事在代码与 git 历史里**单独可审计**，也与 `87-STATE.md` 的「批次二」登记一一对应。
- 227 沿用 226 的**全部**构造（双方言 / 幂等 / 精确父定位 / `NOT EXISTS` 精准授权 / 非阻断降级 / `visible` 归零 / 入口硬断言），**不引入任何新机制**。

| 时点 | `PENDING_SEED_WHITELIST` | `PENDING_SEED_HOLD_CODES` | 脚本硬断言状态 |

| 87-03 收口 | 7（= 挂起集合） | 7 | 规则 A 生效（集合外任何一条残留即 exit 1）；规则 B 待命 |

> ⇒ 87-05 的脚本改动**只有两处**：把 `PENDING_SEED_HOLD_CODES` 置空、把 `PENDING_SEED_WHITELIST` 置空；**硬断言逻辑本身一行不改**（规则 B 已由 87-03 实现为「挂起集合为空 ⇒ 白名单必须为空」）。
