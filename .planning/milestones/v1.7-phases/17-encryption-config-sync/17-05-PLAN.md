# Response Decryption Pattern

From xingran-react-frontend/src/lib/api.ts (existing request encryption):
- Request encryption stores SM4 key/IV in `encryptionKeyStore` Map
- Key is request ID (X-Request-ID header)
- Response should use same key/IV from request for decryption
- SM4 decryption utilities exist in `@/utils/sm4.ts`

From pkg/middleware/response_encryption.go (backend):
- Encrypted response format matches `crypto.EncryptedRequest` structure
- Response includes `encrypted: true, data: base64, sm4Key: base64, iv: base64`
- Backend uses same SM4 key/IV from request for response encryption
- Sets `X-Response-Encrypted: true` header

From research response handling:
- Frontend must check `X-Response-Encrypted` header
- Decrypt using stored SM4 key/IV from corresponding request
- Handle decryption errors gracefully
- Only decrypt if request was encrypted
</context>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| API→Client | Encrypted responses must be authenticated and integrity-checked |
| client memory | SM4 keys stored in Map must be cleared after use |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-17-17 | Tampering | Encrypted response modified in transit | mitigate | HTTPS protects in-flight data, SM4 provides encryption, decryption failure returns error |
| T-17-18 | Spoofing | Fake encrypted response injection | mitigate | Only decrypt responses with valid header and matching request ID, key store prevents cross-request decryption |
| T-17-19 | Information Disclosure | Key store memory leak | mitigate | Keys are removed immediately after decryption, Map is garbage collected |
| T-17-20 | Denial of Service | Forced decryption of invalid responses | mitigate | Decryption failures return error and don't crash, only decrypt responses with valid header |
| T-17-21 | Repudiation | Manual refresh bypasses security | accept | Manual refresh just fetches config, doesn't change encryption behavior, user already has permission to edit configs |

**Security Considerations:**
- Response decryption only happens for encrypted requests (same key/IV)
- Keys are single-use and removed after decryption
- Decryption failures return error to caller (fail-safe)
- Manual refresh is explicit action, requires config edit permissions
- HTTPS is mandatory for production deployment
</threat_model>
