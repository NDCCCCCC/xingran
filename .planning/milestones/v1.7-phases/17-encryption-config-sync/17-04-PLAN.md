## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| API→Client | Encrypted responses must be decryptable by client |
| middleware→DB | Config reads must be cached to avoid performance impact |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-17-12 | Information Disclosure | Response encryption config | accept | Config is non-sensitive boolean, same as request config |
| T-17-13 | Tampering | Config in transit | mitigate | HTTPS + backend cache + frontend validation |
| T-17-14 | Denial of Service | Response encryption performance | mitigate | Uses same 30-second cache as request encryption, only encrypts JSON responses |
| T-17-15 | Spoofing | Forced encryption downgrade | accept | Client will fail to decrypt if config mismatch, user will notice errors |
| T-17-16 | Repudiation | Encrypted response logging | mitigate | Existing logs don't include response body (security best practice) |

**Security Considerations:**
- Response encryption is disabled by default (backward compatible)
- Uses same config as request encryption (unified control)
- Only encrypts success JSON responses (200-299)
- Error responses are never encrypted (security best practice)
- Frontend can detect encrypted responses via `X-Response-Encrypted` header
</threat_model>
