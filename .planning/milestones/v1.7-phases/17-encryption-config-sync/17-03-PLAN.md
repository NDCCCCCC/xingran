# TokenManager Pattern

From research Pattern 3 (Token Manager Integration):
- Token refresh should fetch latest config before calling `/system/auth/refresh`
- Use `getCachedEncryptionConfig()` to get potentially stale config
- Config refresh happens automatically if cache expired (5-minute TTL)
- Graceful error handling: log warning but continue with cached config

From existing authStore.ts:
- TokenManager class with `refreshToken()` and `performRefresh()` methods
- Performs POST request to `/system/auth/refresh`
- Already integrated with API client encryption logic
- Located in `xingran-react-frontend/src/store/authStore.ts`
</context>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| tokenManager→API | Token refresh requests must use correct encryption |
| browser memory | Config cache can be manually cleared by user code |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-17-09 | Tampering | Config cache before token refresh | accept | Cache is memory-only, tampering causes 400 error not security breach, user will refresh page |
| T-17-10 | Denial of Service | Excessive config refresh calls | mitigate | 5-minute TTL on cache, manual refresh is explicit action, backend has 30-second cache |
| T-17-11 | Information Disclosure | Config status exposed to other modules | accept | Config is non-sensitive boolean, utility functions just provide convenience wrappers |

**Security Considerations:**
- Token refresh is critical operation, but config fetch failure shouldn't block it (graceful degradation)
- Manual refresh is explicit action, not automatic, preventing abuse
- Fail-safe defaults to "enabled" for security
- Cache clearing is atomic, no race conditions
</threat_model>
