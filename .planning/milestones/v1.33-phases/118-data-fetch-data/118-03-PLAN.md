在 useColumnConfig.ts loadConfig 函数中，将 :134-160 的网络加载逻辑整体 wrap 进 `if (cached) { /* network block */ } else { /* fallback */ }` 结构。

现状（:121-160）：
```typescript
// :121-132 缓存加载
if (enableCache) {
  const cached = getFromLocalStorage(pageKey);
  if (cached && isConfigSane(cached)) {
    setConfig(cached);
    // ← DATA-03: 这里应该直接 return，不走下面
  }
}
// :134-160 无条件执行（BUG: 即使缓存命中也发网络请求）
const response = await columnConfigApi.getByPageKey(pageKey);
// ...
```

改为（DATA-03）：
```typescript
// :121-132 缓存加载
if (enableCache) {
  const cached = getFromLocalStorage(pageKey);
  if (cached && isConfigSane(cached)) {
    setConfig(cached);
    return;  // ← DATA-03: 缓存命中直接返回，不发网络请求
  }
}
// :134-160 网络加载（仅缓存未命中时执行）
const response = await columnConfigApi.getByPageKey(pageKey);
// ...
```

关键约束：
1. 只改 loadConfig 函数内的控制流：在 `setConfig(cached)` 后立即 `return`
2. `saveConfig` 和 `resetConfig` 函数逻辑不变（它们需要写缓存后调用 API）
3. `setLoading(true)` 行为不变：缓存命中时 `setLoading(false)` 在哪行调用需确认——缓存命中时 :125 setConfig 后直接 return，:108 setLoading(true) 在 :107 enter，:166 setLoading(false) 在 finally。现在 return 前需要 setLoading(false)，但缓存同步执行没有 try/catch，所以需要在 return 前调用 `setLoading(false)`（在 setConfig 后）
4. 现有测试 useColumnConfig.test.tsx 的 "loads from localStorage first" 测试用例必须继续通过
5. `isConfigSane` 检查仍然执行（这是正确的安全 guard，不能跳过）
6. 注意缓存读取在 `setLoading(true)` 之后，所以 loading 状态在缓存命中时会变为 false
