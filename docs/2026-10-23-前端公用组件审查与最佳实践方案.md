# 前端公用组件审查与最佳实践方案

> 审查日期：2026-10-23 ｜ 范围：`xingran-react-frontend/src`（636 个非测试源文件）
> 方法：全量静态扫描（脚本统计） + 公共层源码精读 + 4 个业务模块抽样深审

---

## 0. 摘要

### 0.1 一句话结论

**项目缺的不是"抽组件"，而是"组件契约 + 默认值注入 + 强制约束"。**

已有 20 个 shared 组件、29 个 hooks，但使用率断崖：`EmptyStateWithAction` 只被 3 个文件用，而页面里裸 `<Empty>` 有 39 处；`BaseEditModal` 只被 3 个文件用，而 `<Modal>` 有 88 个文件。**抽出来的组件没人用，是顶层设计问题，不是执行力问题。**

### 0.2 用户反馈的两个原话问题，根因已定位

| 用户反馈 | 事实数据 | 根因 |
|---|---|---|
| 分页组件不显示总数量 | 76 个分页列表中，**51 个（67%）通过 `usePagination` 拿到的是「共 N 页」**（页数当条数），仅 19 个手写正确的「共 N 条」 | 全局分页 Hook 的默认文案错误 + 展示层无统一注入点 |
| 文本输入框没有一键清除 | 285 个 `<Input>`，仅 66 个带 `allowClear`（23%），**219 个缺失** | 直接使用 AntD 裸控件，而 AntD 的 `allowClear` 默认 false，页面必须逐处手写，必然漏 |

### 0.3 六条核心发现

1. **统一骨架覆盖率 26%**：76 个分页列表页只有 20 个用 `useTableManager`，其余 56 个各自手写 loading/data/total/搜索/分页/排序。
2. **公共件"抽而不用"**：`shared/` 下 12 个组件，使用文件数从 36（ActionButtons）到 1（GlobalSearch）不等，三态与弹窗类组件几乎闲置。
3. **展示层缺位**：`useTableManager` 管好了状态，但不提供 `<Table>` 的渲染，于是 20 个"已接入"页面里仍有 19 个手写 `pagination={...}` 对象。
4. **反馈与交互不一致**：`Popconfirm` 18 处 vs `Modal.confirm` 62 处；`message.*` 静态调用 512 次，与 `App.useApp()` 215 次混用（静态调用无法消费暗色主题）。
5. **设计令牌未落地**：`design-system/tokens` 里 175 个颜色定义，页面内硬编码 hex 颜色 **913 处 / 95 个文件**。
6. **深审另发现 27 条 P0 功能缺陷**（超出「组件不完善」范畴，但同源）：**10 个页面批量删除无二次确认**、3 处翻页数据不可达、6 处假功能/断头路、27 个弹窗提交无 loading。清单见 §2.7。

### 0.4 建议的投入产出

| 阶段 | 工作量 | 收益 |
|---|---|---|
| P0 修基础缺陷（5 项） | 0.5～1 天 | 20 个页面分页文案立即正确；新增修改不再漏 allowClear |
| P1 建 `ui/` 增强控件层 + codemod | 2～3 天 | 219 处 Input、278 处 Select 一次性获得默认能力 |
| P2 建 `PageTable` 一站式列表页组件 | 3～4 天 | 56 个手写列表页可按模块渐进收敛，单页平均减 150～250 行 |
| P3 推广 + ESLint 守卫 | 持续 | 覆盖率不随时间衰减 |

### 2.2 分页总量显示（用户主诉之一）

22 处 `showTotal` 的语义分布：

| 形态 | 处数 | 位置 |
|---|---|---|
| `共 N 条`（正确，但各写各的） | 19 | ad-domain×3、asset/reconciliation×3、monitor×2、system×4、vdi×2、其他×5 |
| `共 N 页`（**语义错误**） | 1 | `hooks/usePagination.ts:122` —— **51 个列表页**通过 `paginationProps` 继承该错误文案 |
| 未识别 | 2 | `system/notice/components/NoticeList.tsx` 等 |

**覆盖率真相**：76 个分页列表中，51 个（67%）显示的是「共 N 页」，19 个（25%）手写的「共 N 条」才是对的，6 个（8%）完全不显示总数。**只有四分之一的页面能告诉用户「一共多少条」。**

这表明 `usePagination` 的 `showTotal` 实现是"负资产"：它把**页数当条数**展示，而 AntD 的 `showTotal` 回调参数 `total` 是**记录总数**，`Math.ceil(t / pageSize)` 是页数，二者语义不同。用它渲染"共 N 页"，用户看到的数字与实际数据量无关。

```ts
// hooks/usePagination.ts:122 —— 现状（错误）
showTotal: (t) => `共 ${Math.max(1, Math.ceil(t / pageSize))} 页`,

// 期望
showTotal: (t) => `共 ${t} 条`,
```

## 3. 根因分析

### 3.1 病因一：抽了组件，但没抽"默认值"

`ActionButtons` 被 36 个文件使用（成功），`EmptyStateWithAction` 只有 3 个（失败）。差别在哪？

- `ActionButtons` 解决的是**「多按钮收纳」这个只有写多列操作列才会痛的问题**，用它的收益立竿见影；
- `EmptyStateWithAction` 解决的是**「空状态文案要不要带按钮」这个几乎无痛的问题**，而 AntD 的 `<Empty>` 一行就能写，于是没人愿意多 import 一次。

**更硬的证据**：system 域 14 个列表页里，`EmptyStateWithAction`、`ErrorAlertWithRetry`、`Skeleton` 的使用量分别是 **0 / 0 / 0**；`useColumnConfig`、`useTableQuery` 也是 **0 / 0**。组件写了、规范写了，一个都没用。

**结论**：组件的价值 = 它替你省下的代码量 × 使用频率。省不下代码的抽象，注定闲置。**所以下一步不该再「造新组件」，而该把默认值下沉到 import 层——改一行 import 就自动获得能力。**

### 3.2 病因二：逻辑层有，展示层无

`useTableManager`（410 行）把状态、搜索、重置、排序、分页、选中行都封了，但**它不渲染任何东西**。页面拿到 20 多个返回值后，仍要自己写：

```tsx
<Table
  rowKey="id"
  columns={columns}
  dataSource={data}
  loading={loading}
  pagination={{ ...paginationProps, showTotal: (t) => `共 ${t} 条` }}  // ← 每页都要写
  onChange={handleTableChange}
/>
```

**缺失的是"页面级组件"，不是"页面级 Hook"。** 提供了 Hook 却没有组件，等于把"记得补 showTotal"的责任又推回给了 76 个页面。

### 3.3 病因三：AntD 默认值与业务期望相反

| 属性 | AntD 默认 | 业务期望 | 后果 |
|---|---|---|---|
| `Input.allowClear` | false | true | 219 处缺失 |
| `Select.allowClear` | false | true | 278 处缺失 |
| `Select.showSearch` | false | 选项多时 true | 44/400 |
| `Pagination.showTotal` | 无 | 「共 N 条」 | 51 页显示「共 N 页」 |
| `Modal.destroyOnHidden` | false | true（表单弹窗） | 42/88 |
| `Modal.maskClosable` | true | 表单弹窗应为 false | 1/88 |

只要继续直接使用裸 AntD 控件，这些偏差就**必然**逐页发生。**必须在 import 层做一次收口。**

### 3.4 病因四：没有强制约束，覆盖率必然衰减

现状：无 ESLint 规则限制控件来源，无 Code Review checklist，无页面模板。于是：
- 新页面由不同人写 → 风格分叉（Popconfirm / Modal.confirm 并存就是证据）
- 老页面没人回头改 → 覆盖率只降不升

**任何"最佳实践"如果不带 lint 守卫，半年后就会退回现状。**

## 4. 抽取必要性分析

### 4.1 ROI 评估矩阵

下表「可减代码量」取自 system 域 14 个列表页的实测估算（单页重复行数 × 涉及页数），用于横向比较优先级，不是全局加总。

| 候选能力 | 现状重复度 | 可减代码量（system 域实测） | 结论 |

### 6.1 L1 基础件 API 契约

```tsx
// components/ui/AppInput.tsx
import { Input } from "antd";
import type { ComponentProps } from "react";

export type AppInputProps = ComponentProps<typeof Input>;

/**
 * 企业级文本输入框
 * - 默认 allowClear（一键清除）
 * - 传 maxLength 时自动 showCount
 * - 默认 trim 首尾空格（onBlur）
 */
export function AppInput({ allowClear = true, showCount, maxLength, ...rest }: AppInputProps) {
  return (
    <Input
      allowClear={allowClear}
      maxLength={maxLength}
      showCount={showCount ?? (maxLength ? { formatter: (v) => `${v.length}/${maxLength}` } : undefined)}
      {...rest}
    />
  );
}
```

```tsx
// components/ui/AppSelect.tsx —— 选项数 ≥ 8 自动开搜索
export function AppSelect<T>({ options, showSearch, allowClear = true, ...rest }: AppSelectProps<T>) {
  const count = options?.length ?? 0;
  return (
    <Select
      allowClear={allowClear}
      showSearch={showSearch ?? count >= 8}
      optionFilterProp="label"
      options={options}
      {...rest}
    />
  );
}
```

### 6.2 L2 组合件：PageTable

```tsx
export interface PageTableProps<T> {
  /** 列定义 */
  columns: ColumnsType<T>;
  /** 数据源 */
  dataSource: T[];
  /** 行键 */
  rowKey?: keyof T | ((r: T) => string) | string;
  /** 加载态 */
  loading?: boolean;
  /** 错误对象（自动渲染 ErrorAlertWithRetry） */
  error?: unknown;
  onRetry?: () => void;
  /** 分页配置（必传，来自 useTableManager/usePagination） */
  pagination: TablePaginationConfig;
  /** 行选择 */
  rowSelection?: TableRowSelection<T>;
  /** 工具栏左侧（新增/批量删除） */
  toolbar?: ReactNode;
  /** 工具栏右侧（刷新/列配置/导出） */
  extra?: ReactNode;
  /** 查询表单，传给 SearchForm */
  search?: ReactNode;
  /** 空状态文案 */
  emptyText?: string;
  emptyAction?: { label: string; path?: string; onClick?: () => void };
  /** 滚动宽度，默认 'max-content' 防挤压 */
  scrollX?: number | string;
  /** 关闭分页（树表用） */
  paginated?: boolean;
}
```

### 6.3 硬性规范（Code Review 一律按此检查）

| # | 规则 | 强制等级 |
|---|---|---|
| 1 | 分页列表页必须通过 `PageTable` 或 `paginationProps` 渲染分页，禁止手写 `pagination={{...}}` | 必须 |
| 2 | 分页总数文案唯一来源为 `AppPagination/usePagination`，统一「共 N 条」 | 必须 |
| 3 | 禁止从 `antd` 直接 import `Input/Select/Table/Pagination/Modal/DatePicker/TreeSelect`（ESLint 拦截） | 必须 |
| 4 | 所有文本/下拉输入默认 `allowClear` | 必须 |
| 5 | 选项数 ≥ 8 的 Select 必须 `showSearch` | 必须 |
| 6 | 表单弹窗必须 `destroyOnHidden` + `maskClosable={false}` + 提交按钮 `loading` | 必须 |
| 7 | 删除/危险操作必须二次确认（统一 `ConfirmDelete`） | 必须 |
| 8 | 列表页必须有 loading / empty / error 三态 | 必须 |
| 9 | 颜色禁止 hex 字面量，必须用 `design-system/tokens` 或 AntD 语义色 | 必须 |
| 10 | 状态渲染统一 `<StatusTag status={x} kind="enableDisable" />`，禁止裸三元 | 必须 |
| 11 | 日期统一 `formatDateTime()` / `dayjs` 封装，禁止手写 `YYYY-MM-DD HH:mm:ss` | 建议 |
| 12 | 组件内提示必须 `App.useApp()`，禁止静态 `message.*` | 必须 |
| 13 | 查询参数提交前必须清空 `""/undefined/null` | 必须 |
| 14 | 请求必须可取消或在卸载后不 setState | 建议 |
| 15 | 禁止 `any`（ESLint `@typescript-eslint/no-explicit-any`） | 建议 |

## 8. 风险与兼容

| 风险 | 说明 | 缓解 |
|---|---|---|
| 包装组件透传不全 | 自研组件漏透传某 prop 导致行为变化 | 用 `ComponentProps<typeof Input>` 全量继承，仅覆盖 1～2 个默认值 |
| codemod 误伤 | `Input.TextArea`/`Input.Search`/`Select.Option` 静态成员 | 包装组件保留静态成员挂载（`Input.TextArea = AppTextarea`） |
| 抽屉/弹窗内表格样式 | 包装后默认 `size` 变化 | 默认值只加功能属性，不改尺寸类 |
| 业务页面特殊需求 | 个别页面确实需要无清除框 | 组件保留 `allowClear={false}` 逃生口 |

## 9. 结论

1. **必须抽取**，但重点不是"再写更多组件"，而是**把默认值下沉 + 提供页面级组合件 + 加 lint 守卫**。
2. **优先级**：先修 `showTotal`（1 行，20 页受益）→ 再建 `ui/` 层（codemod 覆盖 497 处控件）→ 再建 `PageTable` 收敛 56 个列表页。
3. **不要做的事**：不要重写 design-system，不要造页面生成器，不要为统一而统一树形表格。
4. 预计总投入 **8～12 人天**，可把列表页平均行数降低 40%+，并让「分页不显示总数」「输入框无清除」这类问题**在 import 层被结构性消灭**。
