## 0. 阅读说明

将启动流程的每一步标记为三类之一：

| 分类 | 含义 | 典型场景 |
|------|------|---------|
| 🔴 **每次必跑** | 进程每次启动都必须执行，缺则功能不可用 | 配置加载、连接池初始化、Cron 注册 |
| 🟢 **一次性** | 仅首次部署 / schema 变更时执行，后续应被跳过 | DB 创建、模型迁移、菜单 seed |
| 🟡 **混合/幂等** | 每次都调用但内部有"已应用则跳过"逻辑，零开销或低开销 | `count > 0 跳过` seed、幂等 SQL migration |

> 当前 dev 环境 DB schema 频繁变化，因此 🟢 类仍走启动路径。
> 未来若上线生产，建议将 🟢 类拆分到独立 `setup` 命令（如 `make db-init`），仅在 CI/CD 部署阶段执行。

## 4. 风险清单（每次启动可能触发的问题）

> 按严重度从高到低排列

| 风险 | 触发条件 | 当前缓解 | 改进建议 |
|------|---------|---------|---------|
| 🔴 **MV 阻塞 AutoMigrate** | GORM ALTER 被 MV 引用列 | `dropDependentMaterializedViews()` 前置 DROP | 验证当前 MV 列表完整性 |
| 🔴 **SM4 默认 key 启动** | `SM4_KEY=dGVzdC1zZWNyZXQxNiEhIQ==` | ERROR 日志提醒 | CI 检查强制非默认值 |
| 🟠 **GORM unique 约束命名冲突** | SQL `UNIQUE` + GORM `uniqueIndex` tag | `cleanupOldConstraints()` 前置清理 | 新 migration 强制显式命名 `CONSTRAINT uni_*` |
| 🟠 **MV refresh statement_timeout** | `RefreshView` 30s+ 超时 | `StartupRefreshView` 独立 30s context | 增加 statement_timeout 配置 |
| 🟡 **81 个显式 migration 顺序耦合** | 中间一条失败阻断后续 | 仅 log error 不阻断 | 监控 log 中"X 迁移失败"汇总告警 |
| 🟡 **AD 账号池空启动** | `sys_ad_service_accounts` 为空 | WARN 不阻断 | 可选 `Config.StrictMode` 启动失败 |
| 🟢 **InitData seed 每次全表扫描** | count 查询 × 10+ 表 | 仅一次性场景有开销 | dev 可接受，prod 应拆分 |
| 🟢 **Cache 预热阻塞 goroutine 启动** | WarmUpEnabled=true + 大数据量 | `time.Sleep(2 * time.Second)` + 异步 | 可观察耗时，超时熔断 |

## 5. 优化建议（未来若拆分 setup/start）

### 5.1 可拆分到 `setup` 命令的步骤

适合做成独立 CLI（如 `xingran-backend setup --db`）：

1. **DB 创建** — `createDatabaseIfNotExists()`
2. **AutoMigrate + 81 migrations** — `c.DB.AutoMigrate()` 全部
3. **InitData 全部 seed** — `c.DB.InitData()`
4. **Permission 默认角色菜单** — `permissionSvc.InitDefaultRolesAndMenus()`
5. **`initMACHistoryRetentionConfig()`** — cmd 末尾的 seed
6. **`importOUIData()`** — cmd 末尾的 seed

### 5.2 拆分后启动流程

```bash
# CI/CD 部署阶段（仅首次 / schema 变更）
xingran-backend setup --db
xingran-backend setup --seed

# 服务启动阶段（每次部署 + 本地 dev）
xingran-backend serve
```

### 5.3 dev 环境保留兼容

为了 dev 环境体验，建议：
- `serve` 默认仍跑全套（含 setup）— 现状不变
- 新增 `XINGRAN_SKIP_SETUP=1` 环境变量跳过 5.1 全部步骤
- 配合 `migrate-sm4-key` 等命令已存在的运维能力

### 5.4 生产环境建议

- 部署阶段：`setup --db --seed` → 启动 `serve`
- 启动监控：核心路径（[1] DB / [2] AutoMigrate / [5] Cache / [10] Scheduler）任一失败 → 立即告警
- 风险监控：每条 migration 失败 log 接入运维告警

- ✅ **DB 连接池 / Cache / Cron 注册 / HTTP** — 这些是真正的每次必跑
- ✅ **RefreshView 异步刷新** — R1 冷启兜底

### 6.3 使用场景

| 场景 | SkipSetup 取值 | 原因 |
|------|--------------|------|
| dev 本地开发 | `false` (默认) | DB schema 频繁变,InitData 幂等检查开销小 |
| 生产首次部署 | `false` | 让 InitData 创建默认管理员/角色/菜单 |
| 生产后续部署 | `true` | DB 已稳定,跳过 10+ 表 count 检查 |
| CI 自动化测试 | `true` | schema 已在 setup 阶段应用 |
| 临时调试 DB | `true` | 防止 InitData 把误删数据重建 |

### 6.4 后续路径

- 短期：用 `SERVER_SKIP_SETUP=true` 控制
- 中期：实现 `xingran-backend setup --db --seed` 子命令，将 InitData/migrate 逻辑抽出
- 长期：完整的 setup/serve 两阶段 CLI
