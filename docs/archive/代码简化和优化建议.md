## 1. 仪表盘处理器 (dashboard_handler.go)

### 问题识别

**重复代码模式:**
- 每个处理方法都重复获取用户上下文 (`userID`, `userDeptID`, `dataScope`, `isAdmin`)
- 相同的错误处理逻辑在多个方法中重复
- 类型断言 `userID.(string)` 在10+处重复

**代码示例 (当前):**
```go
func (h *DashboardHandler) Update(c *gin.Context) {
    userID, exists := c.Get("user_id")
    if !exists {
        response.Error(c, http.StatusUnauthorized, "未授权")
        return
    }

    id := c.Param("id")
    if id == "" {
        response.Error(c, http.StatusBadRequest, "仪表盘ID不能为空")
        return
    }

    var req systemServices.UpdateDashboardRequest
    if err := c.ShouldBindJSON(&req); err != nil {
        response.Error(c, http.StatusBadRequest, "请求参数错误: "+err.Error())
        return
    }

    err := h.service.UpdateDashboard(c.Request.Context(), userID.(string), id, req)
    if err != nil {
        if err.Error() == "dashboard not found" {
            response.Error(c, http.StatusNotFound, "仪表盘不存在")
            return
        }
        // ...更多重复的错误处理
    }
}
```

### 优化建议

**1. 提取用户上下文获取逻辑**
```go
// UserContext 用户上下文信息
type UserContext struct {
    UserID     string
    UserDeptID string
    DataScope  string
    IsAdmin    bool
}

// getUserContext 从gin上下文中提取用户信息
func (h *DashboardHandler) getUserContext(c *gin.Context) (*UserContext, error) {
    userID, exists := c.Get("user_id")
    if !exists {
        return nil, http.ErrNotSupported
    }

    userIDStr := userID.(string)
    // ... 获取 dept_id 和 data_scope

    return &UserContext{
        UserID:     userIDStr,
        UserDeptID: userDeptID,
        DataScope:  dataScope,
        IsAdmin:    isAdmin,
    }, nil
}

// requireUserContext 获取用户上下文,失败时返回错误响应
func (h *DashboardHandler) requireUserContext(c *gin.Context) (*UserContext, bool) {
    ctx, err := h.getUserContext(c)
    if err != nil {
        response.Error(c, http.StatusUnauthorized, "未授权")
        return nil, false
    }
    return ctx, true
}
```

**2. 统一错误处理**
```go
// handleServiceError 统一处理服务错误
func handleServiceError(c *gin.Context, err error) error {
    if err == nil {
        return nil
    }

    errMsg := err.Error()
    switch errMsg {
    case "dashboard not found":
        response.Error(c, http.StatusNotFound, "仪表盘不存在")
    case "permission denied: not the owner":
        response.Error(c, http.StatusForbidden, "权限不足")
    default:
        response.Error(c, http.StatusInternalServerError, errMsg)
    }
    return err
}
```

**3. 简化后的处理方法**
```go
func (h *DashboardHandler) Update(c *gin.Context) {
    userCtx, ok := h.requireUserContext(c)
    if !ok {
        return
    }

    id := c.Param("id")
    if id == "" {
        response.Error(c, http.StatusBadRequest, "仪表盘ID不能为空")
        return
    }

    var req systemServices.UpdateDashboardRequest
    if err := c.ShouldBindJSON(&req); err != nil {
        response.Error(c, http.StatusBadRequest, "请求参数错误: "+err.Error())
        return
    }

    err := h.service.UpdateDashboard(c.Request.Context(), userCtx.UserID, id, req)
    if handleServiceError(c, err) != nil {
        return
    }

    response.Success(c, gin.H{"message": "更新成功"})
}
```

### 收益

- 减少重复代码约 **150行**
- 提高可维护性: 用户上下文逻辑集中在一处
- 降低错误率: 统一的错误处理减少遗漏

### 优化建议

**1. 提取通用方法**
```go
// getDashboardWithOwner 获取仪表盘并验证所有权
func (s *DashboardServiceImpl) getDashboardWithOwner(ctx context.Context, id, ownerID string) (*models.Dashboard, error) {
    var dashboard models.Dashboard
    if err := s.db.WithContext(ctx).Where("id = ?", id).First(&dashboard).Error; err != nil {
        if errors.Is(err, gorm.ErrRecordNotFound) {
            return nil, fmt.Errorf("dashboard not found")
        }
        return nil, fmt.Errorf("failed to fetch dashboard: %w", err)
    }

    if !dashboard.IsTemplate && dashboard.OwnerID != ownerID {
        return nil, fmt.Errorf("permission denied: not the owner")
    }

    return &dashboard, nil
}

// invalidateDashboardCache 清除仪表盘缓存
func (s *DashboardServiceImpl) invalidateDashboardCache(ctx context.Context, dashboardID string) {
    s.cache.Delete(ctx, dashboardCachePrefix+dashboardID)
}
```

**2. 统一权限检查**
```go
// AccessContext 访问上下文
type AccessContext struct {
    UserID     string
    UserDeptID string
    DataScope  string
    IsAdmin    bool
}

// CheckAccess 检查访问权限
func (s *DashboardServiceImpl) CheckAccess(dashboard *models.Dashboard, ctx *AccessContext) bool {
    // 创建者可以访问
    if dashboard.OwnerID == ctx.UserID {
        return true
    }

    // 全局可见
    if dashboard.Scope == models.DashboardScopeGlobal {
        return true
    }

    // 部门可见
    if dashboard.Scope == models.DashboardScopeDept {
        if ctx.DataScope == "all" || ctx.DataScope == "custom" {
            return true
        }
        if dashboard.DeptID != nil && *dashboard.DeptID == ctx.UserDeptID {
            return true
        }
    }

    return false
}
```

**3. 简化后的方法**
```go
func (s *DashboardServiceImpl) UpdateDashboard(ctx context.Context, userID string, id string, req UpdateDashboardRequest) error {
    dashboard, err := s.getDashboardWithOwner(ctx, id, userID)
    if err != nil {
        return err
    }

    updates := make(map[string]interface{})
    if req.Name != nil {
        updates["name"] = *req.Name
    }
    // ... 其他更新字段
    updates["updated_by"] = userID

    if err := s.db.WithContext(ctx).Model(&dashboard).Updates(updates).Error; err != nil {
        return fmt.Errorf("failed to update dashboard: %w", err)
    }

    s.invalidateDashboardCache(ctx, id)
    return nil
}
```

### 收益

- 减少重复代码约 **100行**
- 提高可读性: 权限逻辑集中在一处
- 更容易测试: 权限检查方法可以独立测试

## 3. 前端状态管理 (dashboardStore.ts)

### 问题识别

**复杂的状态更新:**
- 每次更新widget都需要展开整个state和layout
- 重复的对象展开操作
- 缺少辅助函数来处理常见的更新模式

**代码示例 (当前):**
```go
addWidget: (widget) => {
    set((state) => {
        if (!state.currentDashboard) return state;

        const updatedDashboard = {
            ...state.currentDashboard,
            layout: {
                ...state.currentDashboard.layout,
                widgets: [...state.currentDashboard.layout.widgets, widget],
            },
        };

        return {
            currentDashboard: updatedDashboard,
            hasUnsavedChanges: true,
        };
    });
},
```

### 优化建议

**1. 提取辅助函数**
```typescript
// 创建更新后的仪表盘对象
const createUpdatedDashboard = (
    dashboard: Dashboard,
    updates: Partial<Dashboard>
): Dashboard => ({
    ...dashboard,
    ...updates,
});

// 更新仪表盘列表中的项
const updateDashboardInList = (
    dashboards: Dashboard[],
    id: string,
    updates: Partial<Dashboard>
): Dashboard[] =>
    dashboards.map((d) => (d.id === id ? createUpdatedDashboard(d, updates) : d));

// 更新当前仪表盘的widgets
const updateWidgets = (
    layout: LayoutConfig,
    updater: (widgets: WidgetConfig[]) => WidgetConfig[]
): LayoutConfig => ({
    ...layout,
    widgets: updater(layout.widgets),
});
```

**2. 简化后的方法**
```typescript
addWidget: (widget) => {
    set((state) => {
        if (!state.currentDashboard) return state;

        return {
            currentDashboard: createUpdatedDashboard(state.currentDashboard, {
                layout: updateWidgets(state.currentDashboard.layout, (widgets) => [
                    ...widgets,
                    widget,
                ]),
            }),
            hasUnsavedChanges: true,
        };
    });
},

updateDashboard: async (id, data) => {
    await dashboardService.updateDashboard(id, data);

    set((state) => ({
        dashboards: updateDashboardInList(state.dashboards, id, data),
        currentDashboard:
            state.currentDashboard?.id === id
                ? createUpdatedDashboard(state.currentDashboard, data)
                : state.currentDashboard,
        hasUnsavedChanges: false,
    }));
},
```

### 收益

- 减少代码行数约 **30%**
- 提高可读性: 更新逻辑更清晰
- 更容易维护: 通用模式集中在一处
- 减少错误: 避免手动展开对象时的遗漏

## 4. 适配器模式 (adapters.go)

### 问题识别

**不必要的适配器:**
- `passwordManagerAdapter` 仅仅是简单的方法转发,没有添加任何价值
- `cacheInvalidatorAdapter` 使用匿名接口,缺乏类型安全
- 增加了代码复杂度和维护成本

### 优化建议

**1. 移除 passwordManagerAdapter**
```typescript
// 当前代码 (❌ 不好的做法)
type passwordManagerAdapter struct {
    *security.PasswordManager
}

func (a *passwordManagerAdapter) HashPassword(password string) (string, error) {
    return a.PasswordManager.HashPassword(password)
}

// 优化后 (✅ 好的做法)
// 直接使用 *security.PasswordManager
type UserService struct {
    pwdManager *security.PasswordManager
}
```

**2. 重构 cacheInvalidatorAdapter**
```typescript
// 当前代码 (❌ 不好的做法)
type cacheInvalidatorAdapter struct {
    userCacheService interface {
        InvalidateUserCache(ctx context.Context, userID string) error
    }
}

// 优化后 (✅ 好的做法)
type UserCacheInvalidator interface {
    InvalidateUserCache(ctx context.Context, userID string) error
}

type CacheInvalidator struct {
    userCache UserCacheInvalidator
}
```

### 收益

- 减少代码行数约 **50行**
- 提高类型安全性: 使用明确的接口而非匿名接口
- 降低维护成本: 减少间接层和抽象

## 5. 其他发现和建议

### 5.1 错误处理一致性

**问题:** 不同方法使用不同的错误处理方式
- 有些返回自定义错误字符串
- 有些使用 `fmt.Errorf` 包装
- 有些直接返回原始错误

**建议:**
```go
// 定义明确的错误类型
var (
    ErrDashboardNotFound = errors.New("dashboard not found")
    ErrPermissionDenied  = errors.New("permission denied")
    ErrInvalidParameter  = errors.New("invalid parameter")
)

// 使用errors.Is和errors.As进行错误检查
if errors.Is(err, ErrDashboardNotFound) {
    response.Error(c, http.StatusNotFound, "仪表盘不存在")
    return
}
```

### 5.2 常量定义

**问题:** 字符串字面量散落在代码中
```go
"dashboard not found"
"permission denied: not the owner"
"未授权"
```

**建议:**
```go
const (
    ErrMsgUnauthorized      = "未授权"
    ErrMsgDashboardNotFound = "仪表盘不存在"
    ErrMsgPermissionDenied  = "权限不足"
    ErrMsgInvalidParams     = "请求参数错误"
)
```

### 5.3 日志记录

**问题:** 缺少结构化的日志记录
- 大部分错误没有记录日志
- 难以追踪问题

**建议:**
```go
import "log/slog"

func (h *DashboardHandler) Update(c *gin.Context) {
    // ...
    err := h.service.UpdateDashboard(c.Request.Context(), userCtx.UserID, id, req)
    if err != nil {
        slog.ErrorContext(c.Request.Context(),
            "failed to update dashboard",
            "user_id", userCtx.UserID,
            "dashboard_id", id,
            "error", err,
        )
        handleServiceError(c, err)
        return
    }
}
```

## 总结

通过这次代码审查,我们识别出了多个可以显著提高代码质量的优化机会:

1. **减少重复代码** - 通过提取通用方法和辅助函数
2. **提高可读性** - 通过更清晰的命名和结构
3. **增强类型安全** - 通过明确的接口定义
4. **降低维护成本** - 通过减少间接层和抽象

这些优化不会改变任何功能,而是让代码更易于理解、测试和维护。建议优先实施高优先级项目,并在每次重构后运行完整的测试套件以确保功能不受影响。
