## 1. 根因定位

### 1.1 基线行（固定 UUID）来源

`internal/core/db/migrations/menu_catalog_seed.sql` 用**固定 id** + `ON CONFLICT DO NOTHING` 幂等插入基线：

- `menu_catalog_seed.sql:27` → `c4a5ff39-…`（值班池管理，`component='duty/pools/index'`，`visible=0,status=1`，`meta.hidden=true`）
- `menu_catalog_seed.sql:108` → `25bc16b7-…`（节假日管理，`component='duty/holidays/index'`，`0/1`，`meta.hidden=true`）
- `menu_catalog_seed.sql:143` → `abaf31f3-…`（值班配置，`component='duty/config/index'`，`0/1`，`meta.hidden=true`）

这三条是 v1.56 迁移体系认定的「应保留的规范菜单行」。

### 1.2 随机 UUID 重复行来源

随机 UUID 来自**早期（归档）初始化/迁移代码**，与基线 seed 不是同一套 id 生成机制：

1. **归档 SQL `018_unify_duty_menus.sql`**（`internal/core/db/migrations/archive/legacy-2026-06-15/`）
   - `:28`、`:174`、`:320`、`:466` 等处对「值班池管理 / 排班管理 / 节假日管理 / 值班配置」C 行统一用 **`gen_random_uuid()`** 生成主键；
   - 防重仅靠单条 `INSERT … SELECT … WHERE NOT EXISTS (menu_name + parent_id 口径)`（如 `:44-50`），**只在该 SQL 执行瞬间、按名称+父节点判重**，没有数据库唯一约束兜底。
2. **归档 SQL `028_merge_duty_menus.sql`**
   - `:33` 用 `gen_random_uuid()` 创建「值班管理」统一页；`:293-308` 把排班/节假日/值班配置 `UPDATE … SET visible=0`（**只改 visible，不动 status**），`:329-357` 批量把新菜单与按钮授权 `INSERT INTO sys_role_menu` 给所有 `status=0` 角色。
   - 这些脚本在不同启动期、按不同口径（menu_name / path / component）各自防重，顺序或父节点一变就可能漏判。
3. **Go 初始化代码 `internal/core/db/init_data.go`**
   - `:645-651` 的 `createDutyManagementMenus` 已标注「**已废弃**，请使用 `018_unify_duty_menus.sql`」，但注释同时说明旧函数「不会在菜单已存在时重复创建」——即历史上它曾负责创建这些值班菜单；
   - 现存同文件 `createOperationsManagementMenus` 仍保留 `db.Create(&menu)` 补种路径（`:736`、`:823`），并配套 `db.Create(&opsMenu)`（`:675`）；
   - 主键由 `internal/models/base.go:22-26` 的 `BaseModel.BeforeCreate` 钩子在 `ID == ""` 时 **`uuid.New().String()`** 随机生成——这正是「随机 UUID 行」的另一种来源。
4. **结论性判断**：这些历史行**从未被软删**，一直滞留在生产库；当 migration_207 的固定 id seed 以 `ON CONFLICT DO NOTHING`（**仅按主键 `id` 判重**）执行时，因随机行 id 与固定 id 不同，固定 id 行顺利插入 → 同名、同 `component` 的 C 行并存，形成「固定基线 + 若干随机副本」。

### 1.3 为什么没有唯一约束挡住重复

查 `internal/models/menu.go`（`:60-87`）：

- 主键仅 `ID`（`gorm:"type:uuid;primary_key"`，见 `base.go:12`），`ON CONFLICT DO NOTHING` 只按主键判重；
- 所有索引 tag 都是 `index:idx_sys_menu_parent_status_visible` —— 这是 `ParentID`/`Visible`/`Status` 三列的**联合普通索引**（`index:` 而非 `uniqueIndex:`，`:64`、`:69`、`:70`）；
- `MenuName`（`:63`）、`Path`（`:66`）、`Component`（`:67`）、`Perms`（`:71`）**均无任何 `unique`/`uniqueIndex` 约束**；
- `internal/models/role.go:25-26` 的 `sys_role_menu` 同样是 `index:idx_sys_role_menu_role_id_menu_id` 普通联合索引，非唯一。

因此「同名 + 同 component + 同 perms、不同随机主键」在数据库层完全合法，`NOT EXISTS` 防重又只是**应用层、单条语句级、口径不统一**的软防线。只要父节点 id 变化、行被软删后复活、或不同脚本按 menu_name / component / perms 各自判断，就会漏判并再插一条。**没有任何数据库层约束能阻止重复**，这是重复行能累积到 9 条的根本原因。

### 1.4 状态不一致如何形成

- `migration_241` 只改 `visible`，`242/243` 改 `visible+status`；`migration_243` 用 `Find` 按 `component IN ?` 捞出**所有未软删匹配行**逐一 UPDATE（见 `migration_243_low_density_menus.go` 隐藏逻辑），故基线 `0/1` 与随机行早期 `0/0` 残留并存；
- `migration_228_server_sort_menus.go` 的 `ensureMenuVisible` 会把 `duty/pools/index` 强制激活为 `visible=1/status=0`，且 `internal/core/db/database.go:1559` 的 `runAndRecord` **不检查版本是否已应用、迁移每次启动重跑**，导致基线 `c4a5ff39` 也由 `0/1` 被改成 `1/0`（与 T2 背景一致）；
- 叠加结果即快照所见：同一菜单名下，可见/隐藏、正常/停用四种组合混存。

### 1.5 根因结论

> **随机 UUID 重复 C 行是 2026-06-15 归档期 `018_unify_duty_menus.sql` / `028_merge_duty_menus.sql`（`gen_random_uuid()`）与更早 `init_data.go` 的 `createDutyManagementMenus`（`uuid.New()`）在「无数据库唯一约束、仅靠应用层 `NOT EXISTS`/`First` 查重、且各脚本判重口径不一致」的条件下多次补种、且历史行从未软删回收所遗留；随后 migration_207 固定 id 基线 seed 按主键 `ON CONFLICT DO NOTHING` 插入，因主键不同而与随机副本并存。241/242/243/228 对不同存活行分别 UPDATE，最终暴露出同名多状态。**

## 2. 影响评估

### 2.1 `sys_role_menu` 是否引用随机 id（核查 SQL，只写不执行）

> 以下 SQL 均为**只读 SELECT**，本任务未执行。快照 id 为前缀，正式执行前补全完整 UUID。

```sql
-- (R1) 逐个随机 id 是否被授权行引用，以及被哪些角色引用
SELECT rm.menu_id, m.menu_name, m.component, m.visible, m.status,
       rm.role_id, r.role_name, r.status AS role_status
FROM sys_role_menu rm
JOIN sys_menu  m ON m.id = rm.menu_id
JOIN sys_role  r ON r.id = rm.role_id
WHERE rm.menu_id::text LIKE ANY (ARRAY[
        '9b0e9cdf%','4564a5ba%','8f53df97%',       -- 值班配置
        'b1fa3b40%','a810df1b%','bfdeb558%',       -- 节假日管理
        'e099746d%','1148ad3b%','e80a0801%','a089251e%' -- 值班池管理
      ])
ORDER BY m.menu_name, rm.menu_id, rm.role_id;

-- (R2) 按菜单名汇总：每个同名菜单下「基线 id 授权数」vs「随机副本授权数」
SELECT m.menu_name, m.id, m.component, m.visible, m.status,
       COUNT(rm.role_id) AS granted_roles
FROM sys_menu m
LEFT JOIN sys_role_menu rm ON rm.menu_id = m.id
WHERE m.menu_type = 'C'
  AND m.menu_name IN ('值班配置','节假日管理','值班池管理')
  AND m.deleted_at IS NULL
GROUP BY m.menu_name, m.id, m.component, m.visible, m.status
ORDER BY m.menu_name, m.created_at;

-- (R3) 孤儿授权探测：授权行指向不存在/已软删菜单（回收前必须为零容忍基线）
SELECT rm.menu_id, COUNT(*) AS orphan_refs
FROM sys_role_menu rm
LEFT JOIN sys_menu m ON m.id = rm.menu_id AND m.deleted_at IS NULL
WHERE m.id IS NULL
GROUP BY rm.menu_id;

-- (R4) 同名重复 C 行全景（含软删状态，确认哪些是活行）
SELECT id, menu_name, component, visible, status, created_at, deleted_at
FROM sys_menu
WHERE menu_type = 'C'
  AND menu_name IN ('值班配置','节假日管理','值班池管理')
ORDER BY menu_name, created_at;
```

判读要点：若 (R1) 非空，说明**回收/软删重复行会直接破坏这些角色的授权**（须先合并到基线 id）；
(R3) 是任何删除方案的硬门槛——既有孤儿授权必须先于回收处理，否则删除后残留更多孤儿。

### 2.2 `GetTree` 不过滤 visible/status → 授权树同名重复

`internal/services/system/menu_service.go:181-190` 的基础 `GetTree` 直接 `Order("order_num ASC").Find(&menus)`，
**没有 `status` / `visible` / `deleted_at` 之外的业务过滤**（软删由 GORM 全局 scope 处理），
把同名、同 component 的基线行与随机副本全部读出并 `buildMenuTree`。于是菜单管理页 / 角色授权树里，
「值班配置」「节假日管理」「值班池管理」各出现 3~5 个同名节点，管理员无法分辨该给哪个 id 打勾，
且勾选到 `status=1` 或隐藏行时授权「看似生效、实际不生效」。

> 补充：缓存版 `menuCacheService.GetTree`（`menu_cache_impl.go:36-41`）走 `queryTree(ctx,false)`，
> 后者在 `menu_cache_impl.go:56-58` 才加 `status=normal` 过滤；两版口径不一致，也是「授权树 / 运行时菜单」表现不同的原因之一。

### 2.3 `/my-menus/all` 只按 `status=0` 过滤 → 幽灵路由

`internal/services/system/menu_service.go:494-501` 的 `/my-menus/all` 用
`Where("id IN ? AND status = ?", menuIDs, MenuStatusNormal)`：随机副本 `status=0`（正常）的行
**仍会被返回并生成前端路由**，指向已并入宿主 Tab 的旧页面（如 `duty/pools`、`duty/holidays`、`duty/config`），
形成「独立旧页 + Tab」双入口与幽灵路由。仅把 `visible` 改 0 挡不住它——真正挡路由的是 `status`。

### 2.4 `findHostMenuID` 选错宿主风险

`internal/core/db/migrations/migration_243_low_density_menus.go:139-156`：

```go
db.Where("component IN ?", components).
   Where("menu_type = ?", models.MenuTypeMenu).
   Order("created_at").First(&host)   // 取创建时间最早的一条
```

当同 `component` 存在多条未软删 C 行（本例 3~5 条）时，`Order(created_at).First` 只取**最早创建**的一条。
若随机副本的 `created_at` 早于基线（历史归档行通常早于 207 seed），宿主 id 会指向随机副本而非规范基线，
`reparentButtonPermissions`（`:158-164`）随之把 F 按钮权限整体挂到重复行下 → 权限树归属错乱、
后续 248/249 按 perms 复用时也可能命中错误载体。这是「重复行不清理就继续跑迁移」的最大隐性风险。

### 2.5 侧边栏重复项

`xingran-react-frontend/src/components/layout/sidebar.tsx:94-99`：

```ts
menus.filter((menu) => menu.menuType !== "F" && menu.visible === 1).map(convertToMenuItem)
```

只按 `visible===1` 过滤。值班池管理 4 条随机行 + 基线均为 `visible=1`，
叠加 `MENU_CACHE_VERSION=1`（`src/constants/storage.ts:50`）的 sessionStorage 30min 缓存
（`DynamicRoutes.tsx:35`）不会因数据变更失效 → 侧边栏稳定出现多条同名「值班池管理」，且用户强刷前持续可见。

## 3. 候选方案对比（≥3 种）

> 前提：三种方案均为「**彻底回收**」范畴，按用户决策须**单独评审通过后方可执行**；本任务只评估、不执行。
> 隐藏策略（保留行 + 改 visible/status + 不回收授权）是**当前已选定的过渡态**，不在下列三方案内。

| 维度 | A 软删重复行 + 授权合并到基线 id | B 物理删重复行 + 清理孤儿 role_menu | C 保留行 + 加唯一约束 + 统一状态 |
| --- | --- | --- | --- |
| 做法 | `deleted_at=now()` 随机副本；`INSERT … ON CONFLICT DO NOTHING` 把其 `sys_role_menu` 合并到基线 id；重复授权去重 | `DELETE FROM sys_menu WHERE id IN(随机行)`；`DELETE FROM sys_role_menu WHERE menu_id IN(随机行)`；清孤儿 | 不删行；先把所有同名 C 行统一到 `visible=0/status=1`；再加 `(menu_name, component, parent_id)` 唯一/部分唯一索引防复发 |
| 可回滚性 | **高**：软删可 `UPDATE deleted_at=NULL` 复活；合并授权可凭备份逆向 | **低**：物理删不可逆，只能靠备份恢复 | 中：状态/约束可回退，但**加唯一约束前必须先消除存量重复**，否则 DDL 直接失败 |
| 对授权的破坏 | **可控**：合并后授权仍在基线 id 上，权限集不丢；需处理 `(role_id,menu_id)` 重复 | **大**：删除授权行，若漏合并则角色直接失权；孤儿清理进一步删数据 | **无**（不动授权），但重复授权仍指向多个 id，授权树重复问题不解决 |
| 停机窗口 | 短：单事务内完成，建议低峰；前端 30min 缓存需强刷/重登 | **长**：涉及物理删 + 外键/孤儿清理，建议维护窗口 + 全量备份 | 短（状态）；**加约束阶段需停机**，存量重复未清则无法建索引 |
| 主要风险 | 合并授权时若基线 id 已有同角色授权需去重（依赖 (R1) 结果）；软删行仍占 `GetTree`（GORM 自动过滤，风险低） | 不可逆、403 回归风险最高；`runAndRecord` 每次启动重跑迁移，若迁移里再按名称补种会「删了又长」 | 唯一约束与 241/242/243/228 的补种逻辑冲突；`meta` / 路径变体（如 `duty/pools/index` 与带斜杠变体）需先归一，否则约束口径难定 |
| 是否解决根因 | 部分（清存量，但无约束仍可能复发） | 部分（同上） | **防复发最强**，但不能单独回收存量 |

### 推荐项与理由

**主推荐：方案 A（软删 + 授权合并到基线 id），但必须作为「彻底回收独立评审」通过后的灰度执行项；
并把方案 C 的唯一约束作为 A 完成后的「防复发第二阶段」。**

理由：

1. **可逆性优先**：`deleted_at` 软删 + 授权合并是三类里唯一「出问题能原地复活」的方案，符合本项目 `runAndRecord` 每次启动重跑迁移、状态可能被再次改写的现实（T4 运维须知）。
2. **不丢权限**：把随机副本的 `sys_role_menu` 合并到规范基线 id（`abaf31f3` / `25bc16b7` / `c4a5ff39`），保证 `pkg/middleware/permission.go:144-150`（`m.status=normal` 精确匹配）与 `/my-menus/all`（`status=0`）都落到唯一规范载体上，消除 403 与幽灵路由。
3. **风险可控**：不物理删、不清孤儿在回收动作本身之外，停机窗口短；配合 (R1)/(R3) 核查 SQL 可把「合并了哪些角色、是否本就重复」逐条对账。
4. **不选 B**：物理删不可逆、对授权破坏最大，且与「隐藏策略可逆」的既定决策相悖。
5. **C 的定位**：加唯一约束是**根因级防复发**措施，值得做，但「存量 9 条重复未清时直接建唯一索引必然失败」，因此只能是 A 完成后、且先统一 `component` 变体口径的第二阶段，不能当作回收手段本身。

> 若独立评审否决任何删除，则维持「隐藏策略 + 方案 C 的状态统一（不加约束）」作为长期态，
> 并在 `findHostMenuID` 改用「优先固定基线 id、退化按 `status=0 AND visible` 过滤」规避选错宿主（属代码改动，另立任务）。

## 4. 「彻底回收」独立评审清单

> 本节是**给评审会的清单**，不是执行脚本；所有 `UPDATE/DELETE/DDL` 均标注「拟执行，本任务未执行」。

### 4.1 决策点（评审必须逐项拍板）

1. **是否授权回收**：用户已定「隐藏策略不回收授权」，启动彻底回收需**新的显式确认**，并指定基线 id 为唯一保留载体。
2. **保留哪条 id**：确认保留 `menu_catalog_seed.sql` 固定 id（`abaf31f3`/`25bc16b7`/`c4a5ff39`），随机副本全部为回收对象；确认 `duty/pools` 的期望终态（T2：`visible=0/status=1`）。
3. **授权合并口径**：(R1) 结果中，随机副本被哪些角色引用；同角色已在基线 id 授权时如何去重（`ON CONFLICT DO NOTHING` 或先删重复）；是否保留「授权审计留痕」。
4. **软删 vs 物理删**：确认选 A（软删），**禁止**在本轮执行物理删/清孤儿；孤儿 (R3) 若非空，单独立项。

### 4.2 验收 SQL（只读核查 / 拟执行后的验收，本任务均未执行）

```sql
-- (V1) 回收后：每个同名 C 菜单仅剩 1 条未软删的规范基线行，且状态收敛
SELECT menu_name, COUNT(*) AS live_rows,
       MIN(id::text) AS kept_id, MIN(visible) AS visible, MIN(status) AS status
FROM sys_menu
WHERE menu_type='C' AND menu_name IN ('值班配置','节假日管理','值班池管理')
  AND deleted_at IS NULL
GROUP BY menu_name
HAVING COUNT(*) <> 1 OR MIN(status) <> 1 OR MIN(visible) <> 0;   -- 期望：0 行

-- (V2) 授权完整性：回收前后「每个角色的有效权限码集合」不变（以基线 id 为准）

SELECT role_id, perms FROM tmp_perm_before
EXCEPT
SELECT rm.role_id, m.perms
FROM sys_role_menu rm JOIN sys_menu m ON m.id=rm.menu_id
WHERE m.deleted_at IS NULL AND m.status=0;                       -- 期望：0 行（无权限丢失）

-- (V3) 无孤儿授权
SELECT rm.menu_id FROM sys_role_menu rm
LEFT JOIN sys_menu m ON m.id=rm.menu_id AND m.deleted_at IS NULL
WHERE m.id IS NULL;                                              -- 期望：0 行

SELECT id, menu_name, deleted_at FROM sys_menu

        'b1fa3b40%','a810df1b%','bfdeb558%',

SELECT menu_name, component, COUNT(*) FROM sys_menu

GROUP BY menu_name, component HAVING COUNT(*)>1;                 -- 期望：0 行
```
