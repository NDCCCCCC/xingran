# 开发规范文档

## 1. 概述

本文档定义了XingRan Modern项目的开发规范，包括编码规范、状态值规范、数据库设计规范等，确保项目的一致性和可维护性。

## 2. 状态值统一规范

### 2.1 通用规则

为保持系统一致性，所有模块的状态字段必须遵循以下统一规则：

- **0 = 启用/正常/显示/有效**：表示该数据处于活跃可用状态
- **1 = 禁用/停用/隐藏/无效**：表示该数据处于不可用状态

### 2.2 各模块状态定义

| 模块 | 状态类型 | 0值含义 | 1值含义 | 默认值 | 显示颜色 |
|------|---------|--------|--------|--------|----------|
| **用户模块** | UserStatus | 启用 | 禁用 | 0 | 绿/红 |
| **角色模块** | RoleStatus | 正常 | 停用 | 0 | 绿/红 |
| **菜单模块** | MenuStatus | 正常 | 停用 | 0 | 绿/红 |
| **菜单可见性** | VisibleType | 隐藏 | 显示 | 1 | 红/绿 |
| **部门模块** | DeptStatus | 正常 | 停用 | 0 | 绿/红 |
| **岗位模块** | PostStatus | 正常 | 停用 | 0 | 绿/红 |

### 2.2.1 特殊说明：VisibleType 菜单可见性字段

`VisibleType` 是一个特殊的状态类型，遵循布尔语义而非常规状态值规范：

- **1 = 显示**：表示菜单在界面中可见
- **0 = 隐藏**：表示菜单在界面中不可见
- **默认值**：1（显示）

**设计原因**：可见性字段本质上是布尔类型（is_visible），使用 1 表示 true/可见，0 表示 false/隐藏，更符合编程直觉。

**注意**：这与常规状态值规范（0=启用，1=禁用）相反，是一个特例。在处理菜单可见性时需要特别注意。

### 2.3 后端实现规范

```go

    UserStatusEnabled  UserStatus = 0 // 启用
    UserStatusDisabled UserStatus = 1 // 禁用

// 数据库模型

    // ...其他字段
```


## 3. 数据库设计规范

### 3.1 表设计规范

1. **表命名**：使用 `sys_` 前缀，采用小写字母和下划线
2. **字段命名**：使用小写字母和下划线，见名知意
3. **主键**：统一使用 UUID 类型，默认值为 `gen_random_uuid()`
4. **时间字段**：必须包含 `created_at`、`updated_at`，软删除表包含 `deleted_at`
5. **状态字段**：统一使用整数类型，0表示启用/正常，1表示禁用/停用

### 3.2 字段设计规范

| 字段类型 | 说明 | 示例 |
|---------|------|------|
| **主键** | UUID类型 | `id UUID DEFAULT gen_random_uuid()` |
| **状态** | 整数类型 | `status INTEGER DEFAULT 0` |
| **排序** | 整数类型 | `order_num INTEGER DEFAULT 0` |
| **备注** | 文本类型 | `remark TEXT` |
| **创建时间** | 时间戳 | `created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP` |
| **更新时间** | 时间戳 | `updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP` |

### 3.3 索引设计规范

1. **主键索引**：自动创建
2. **外键索引**：所有外键字段必须创建索引
3. **唯一索引**：业务唯一字段必须创建唯一索引
4. **查询索引**：经常用于查询条件的字段创建索引

### 3.4 唯一约束命名规范(强制)

**背景**: GORM AutoMigrate 与手写 SQL migration 混用时,unique 约束的默认命名规范不一致 ——
- SQL inline `UNIQUE` → PostgreSQL 自动命名 `<table>_<column>_key`
- GORM `uniqueIndex` tag → GORM 拼接 `uni_<table>_<column>`

二者不一致会导致 AutoMigrate 试图 `DROP CONSTRAINT uni_*`(GORM Migrator 没有 IF EXISTS)→ **服务启动 FATA**。

**强制规则**:

#### ❌ 禁止
```sql
CREATE TABLE sys_xxx (
    col VARCHAR(100) NOT NULL UNIQUE,            -- ❌ PG 自动命名,与 GORM 冲突
    UNIQUE (col1, col2)                          -- ❌ PG 自动命名,与 GORM 冲突
);
```

#### ✅ 必须
```sql
CREATE TABLE sys_xxx (
    col VARCHAR(100) NOT NULL,
    col1 VARCHAR(100) NOT NULL,
    col2 VARCHAR(100) NOT NULL,
    CONSTRAINT uni_sys_xxx_col UNIQUE (col),                     -- ✅ 显式命名
    CONSTRAINT uni_sys_xxx_col1_col2 UNIQUE (col1, col2)         -- ✅ 显式命名
);
```

#### 命名格式
- 单列: `uni_<table>_<column>`(完全匹配 GORM 默认)
- 复合列: `uni_<table>_<col1>_<col2>...`
- 表名超长时可缩写,但必须与 GORM model 中 `uniqueIndex:<name>` 显式名一致

#### 模型对齐
```go
// 单列 uniqueIndex —— GORM 自动用 uni_<table>_<column>
DeviceSN string `gorm:"size:200;not null;uniqueIndex"`

// 复合 uniqueIndex —— 必须显式命名
NoticeID string `gorm:"uniqueIndex:uni_sys_notice_ignore_notice_user,priority:1"`
UserID   string `gorm:"uniqueIndex:uni_sys_notice_ignore_notice_user,priority:2"`
```

#### 启动期审计
项目在 `internal/core/db/database.go:auditConstraintNaming()` 中扫描所有 `_key` 后缀的 PG 自动命名约束。新增表如触发审计 INFO 输出,说明命名未遵循此规约,应改正。

#### 历史包袱兜底
已存在的命名不一致约束在 `internal/core/db/database.go:cleanupOldConstraints()` 中维护清单,AutoMigrate 前 `DROP CONSTRAINT IF EXISTS` 兜底。**新表不应进入此清单 — 一律遵循规约即可。**

## 4. API设计规范

### 4.1 RESTful API规范

1. **请求方法**：统一使用 POST 方法，通过路径区分操作类型
2. **路径规范**：使用小写字母和下划线，资源名称使用复数形式
3. **响应格式**：统一使用 JSON 格式，包含固定字段

```go
// 路径设计示例
POST /api/v1/users              // 创建用户
POST /api/v1/users/list         // 查询用户列表
POST /api/v1/users/{id}         // 获取用户详情
POST /api/v1/users/{id}/update  // 更新用户
POST /api/v1/users/{id}/delete  // 删除用户
```

### 4.2 响应格式规范

```json
{
  "code": 200,
  "message": "操作成功",
  "data": {
    // 具体数据
  },
  "timestamp": 1234567890,
  "requestId": "uuid-string"
}
```

### 4.3 状态码规范

| 状态码 | 说明 | 使用场景 |
|--------|------|----------|
| 200 | 成功 | 操作成功 |
| 400 | 请求错误 | 参数错误、格式错误 |
| 401 | 未授权 | 未登录、token无效 |
| 403 | 禁止访问 | 权限不足 |
| 404 | 资源不存在 | 资源未找到 |
| 500 | 服务器错误 | 系统内部错误 |

## 5. 代码规范

### 5.1 Go代码规范

1. **包命名**：使用小写字母，简短且有意义
2. **函数命名**：使用驼峰命名，首字母大写表示公开，小写表示私有
3. **变量命名**：使用驼峰命名，见名知意
4. **常量命名**：使用全大写字母和下划线
5. **注释规范**：公开函数必须包含注释

```go
// UserService 用户服务接口
type UserService interface {
    // CreateUser 创建用户
    CreateUser(ctx context.Context, user *User) error
}

// userService 用户服务实现
type userService struct {
    db *gorm.DB
}

// NewUserService 创建用户服务实例
func NewUserService(db *gorm.DB) UserService {
    return &userService{db: db}
}
```

### 5.1.1 操作日志记录 (强制)

新增 handler 必须遵循 Handler-Service 模式，并且在 success path 末尾、`response.Success(...)` 之前调用 `operlog.Record(...)` 记录操作日志：

```go
import "github.com/xingran-next/xingran-go-backend/internal/utils/operlog"

// success path 末尾，response.Success 之前
operlog.Record(c, h.core.OperLogService, h.core.GetDB(), "用户管理", operlog.OperTypeCreate)
response.Success(c, user)
```

**规则要点:**

1. **所有业务写操作必须埋点** — 创建 / 更新 / 删除 / 状态变更 / 导入导出 / 同步 / 批量 / 授权等（Phase 34 全模块集成后覆盖率 100%）。
2. **敏感端点必须用 `RecordWithBody`** — 密码、密钥、token、SMTP password、API headers 等敏感字段的端点使用 `operlog.RecordWithBody(...)`，自动读取并恢复请求体、对敏感字段值脱敏为 `******`。
3. **敏感字段必须通过 `operlog.WithOperParam(operlog.FilterSensitiveParams(string(body)))` 传入** — 关键词黑名单见 `internal/utils/operlog/operlog.go` 的 `sensitiveKeys`，覆盖 `password / pwd / secret / token / key / salt / privateKey / oldPassword / macKey / sm4Key / sm2Key / adminPassword / clientSecret / accessKey / secretKey / private_key / publicKey`（共 17 个）。
4. **OperType 共 25 个常量**，值固定不可重排（值映射表见 `CLAUDE.md` "操作日志记录约定" 一节）。误用 `OperTypeOther=0` 表示已有语义类型是反模式。
5. **module 参数使用中文模块名**（如 "用户管理"、"楼宇管理"、"网络设备"），与 `sys_oper_log.title` 一致，便于前端按模块筛选。
6. **参考实现:** `internal/api/v1/system/ad_domain_handler.go`、`internal/api/v1/system/apikey_handler.go`。
7. **回归守护:** `internal/utils/operlog/regression_test.go` 锁定公共 API（常量值 / 常量数 / Record 签名 / 敏感关键词），任何静默改动都会立即失败。

## 6. 安全规范

### 6.1 认证授权

1. **JWT Token**：使用双Token机制（访问Token + 刷新Token）
2. **密码加密**：使用SM3国密算法加密
3. **权限控制**：基于RBAC模型的权限控制
4. **API鉴权**：所有API接口必须进行权限验证

### 6.2 数据安全

1. **SQL注入防护**：使用参数化查询
2. **XSS防护**：前端输出内容必须进行转义
3. **CSRF防护**：使用CSRF Token防护
4. **敏感数据**：敏感信息不得在前端存储

## 7. API调用规范

### 7.1 前端API调用

#### 7.1.1 使用统一的API封装函数
项目中已封装了统一的API调用函数，必须使用这些封装函数而不是直接使用axios实例：

```typescript
import { post, get, put, del } from '@/lib/api';

// ✅ 正确写法 - 使用封装函数
const result = await post('/system/users/list', {
    current: 1,
    pageSize: 10
});
// 直接使用 result.data，无需手动检查 code

// ❌ 错误写法 - 直接使用 api 实例
const response = await api.post('/system/users/list', {
    current: 1,
    pageSize: 10
});
if (response.data.code === 0) {
    // 需要手动检查 code
    setUsers(response.data.data.list);
}
```

#### 7.1.2 响应数据处理
```typescript
// 获取数据
const result = await post('/system/users/list', params);
const users = result.data.list;  // 直接使用数据

// 错误处理通过响应拦截器统一处理
try {
    const result = await post('/system/users/create', userData);
    // 成功处理逻辑
    message.success('创建成功');
} catch (error) {
    // 错误已在拦截器中处理，这里可以添加额外逻辑
    console.error('操作失败:', error);
    message.error('操作失败');
}
```

### 7.2 分页数据规范

#### 7.2.1 请求参数
```typescript
interface PageParams {
    current: number;    // 当前页码，从1开始
    pageSize: number;   // 每页大小
    [key: string]: any;  // 其他查询参数
}
```

#### 7.2.2 响应数据结构
```typescript
interface PageData<T> {
    list: T[];         // 数据列表
    total: number;      // 总记录数
    current: number;    // 当前页码
    pageSize: number;   // 每页大小
}

// 使用示例
const result = await post<PageData<User>>('/system/users/list', params);
setUsers(result.data.list);
setTotal(result.data.total);
setCurrent(result.data.current);
```

### 7.3 错误处理规范

#### 7.3.1 错误状态码
- 成功：`code: 0`
- 参数错误：`code: 400` 或 `code: 1001`
- 认证失败：`code: 401` 或 `code: 1007`
- 权限不足：`code: 403`
- 资源不存在：`code: 404`
- 服务器错误：`code: 500`

#### 7.3.2 错误处理最佳实践
```typescript
// 利用统一的错误处理
try {
    const result = await post('/api/endpoint', data);
    return result.data;
} catch (error) {
    // 业务错误已在拦截器中处理，这里处理特殊逻辑
    if (error.message.includes('权限不足')) {
        // 跳转到权限提示页面
        router.push('/403');
    }
    throw error;
}
```

```go
        name    string

    }{
        {
            name:    "成功创建用户",
            user:    &User{Username: "test", Status: 0},
            wantErr: false,
        },

    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            err := userService.CreateUser(context.Background(), tt.user)
            if (err != nil) != tt.wantErr {
                t.Errorf("CreateUser() error = %v, wantErr %v", err, tt.wantErr)
            }
        })
    }
}
```
