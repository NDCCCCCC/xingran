# 跨模块选择器权限处理规范

> 适用场景: 一个业务页面(模块 A)需要加载另一个模块(B)的 list/tree 数据作为下拉/树/统计选择器, 而 A 的角色不持有 B 的权限, 导致选择器接口 403。
>
> 状态: 已落地 (2026-06-17)。本文是新增此类选择器时的强制参考。

---

## 1. 问题定义

「跨模块选择器」指前端某个业务页面内嵌的、用于加载**其他模块**只读数据(下拉选项、组织树、统计计数)的接口调用。典型例子:

| 选择器用途 | 调用接口 | 所属模块 | 调用方页面 |
|-----------|---------|---------|-----------|
| 部门树侧边栏 `<DeptTree>` | `/system/departments/tree` | system (system:dept) | 楼宇/楼层/工位/机房等**所有运维页面** |
| 工位归属用户下拉 | `/system/users/list` | system (system:user) | 工位管理 |
| 字典下拉 `useDict` | `/system/dicts/data/list` | system (system:dict) | **几乎所有表单页面** |
| 信息点关联网络设备 | `/network/devices/list` | network (network:device) | 信息点管理、Dashboard 统计 |
| 信息点关联设备端口 | `/network/ports/list` | network (network:port) | 信息点管理 |

## 2. 根因

权限是**每次请求实时查库** (`pkg/middleware/permission.go` 的 `checkUserPermission`):
```sql
SELECT COUNT(DISTINCT rm.menu_id)
FROM sys_user_role ur
JOIN sys_role_menu rm ON ur.role_id = rm.role_id
JOIN sys_menu m ON rm.menu_id = m.id
WHERE ur.user_id = ? AND m.perms = ? AND m.status = 0
```

选择器接口的路由组用 `RequirePermissions` 严格要求**本模块**权限(如 `/system/departments` 组要求 `system:dept:*`)。而调用方页面的角色(如运维角色持 `ops:*`)与本模块权限**命名空间完全不重叠** → 精确匹配失败 → 403。

这不是 bug, 是**权限模型设计断层**: 可视化/管理页面跨模块复用了 CRUD 接口, 但权限标识没有打通。

## 3. 解决方案: `RequirePermissionsWithQuery`

核心中间件: `pkg/middleware/permission.go` 的 `RequirePermissionsWithQuery(strict, queryExtra, core)`。

**语义**:
- 对**只读查询路径**(URL 末段为 `list` 或 `tree`, 由 `isQueryPath()` 判定) → 在 `strict` 基础上**额外**接受 `queryExtra` 中的任一权限 (OR 逻辑)。
- 对**写操作路径**(末段为 create/update/delete/batch/geocode/import/export 等) → **只**走 `strict` 严格权限, 不放宽。

**安全保证**: 只读放行不会导致越权写。即: 持有运维读权限的角色能读选择器数据, 但无法增删改被选模块的实体。

```go
// pkg/middleware/permission.go
func RequirePermissionsWithQuery(permissions []string, queryExtraPermissions []string, core *core.Core) gin.HandlerFunc {
    // ... 超管 bypass, 未认证拦截 ...
    checkPerms := permissions
    if len(queryExtraPermissions) > 0 && isQueryPath(c.Request.URL.Path) {
        // 只读路径合并 queryExtra; 写路径不合并 → 严格
        checkPerms = append(append([]string{}, permissions...), queryExtraPermissions...)
    }
    for _, p := range checkPerms {
        if checkUserPermission(core, userID, p) { c.Next(); return }
    }
    response.Error(c, response.ErrForbidden, "没有访问权限"); c.Abort()
}
```

## 4. 放行权限集: `OpsSelectorReadPerms` (单一来源)

`pkg/middleware/selector_perms.go` 定义了**导出常量** `OpsSelectorReadPerms`, 作为所有跨模块选择器放行的统一权限集:

```go
var OpsSelectorReadPerms = []string{
    "ops:building:list", "ops:floor:list", "ops:workstation:list",
    "ops:serverroom:list", "ops:infopoint:list", "ops:dedicatedline:list",
    "ops:roomdevice:list", "ops:asset:list", "ops:building:spaces:list",
}
```

**原则**: 持有任一运维模块读权限的角色, 都能读取跨模块选择器(部门树/字典/网络设备等)。
- `router.go` (system/ops 组) 与 `network_router.go` (devices/ports 组) **共用**此常量, 避免重复定义。
- **新增运维模块时**: 只需在此常量追加该模块的 `:list` 权限, 所有跨模块选择器自动对新模块角色放行。

> 例外: 用户列表 `/system/users/list` 因含 PII, queryExtra **收窄**为 `[ops:workstation:list, ops:building:spaces:list]`(仅工位/空间角色), 不用全集; 且仍受 `DataScopePermission` 数据权限限制可见用户范围。

## 5. 当前已处理的跨模块选择器清单

| 接口 | 路由组位置 | 严格权限 (strict) | queryExtra | 备注 |
|------|-----------|------------------|-----------|------|
| `/system/departments/tree` | `router.go` `/departments` | `system:dept:*` | `OpsSelectorReadPerms` | GetTree 不应用数据权限, 返回全树(低敏感) |
| `/system/dicts/data/list` | `router.go` `/dicts` | `system:dict:*` | `OpsSelectorReadPerms` | useDict 全局调用 |
| `/system/users/list` | `router.go` `/users` | `system:user:*` | `[ops:workstation:list, ops:building:spaces:list]` | PII 收窄 + DataScope |
| `/network/devices/list` | `network_router.go` `/devices` | `network:device:*` | `OpsSelectorReadPerms` | 信息点关联 + Dashboard |
| `/network/ports/list` | `network_router.go` `/ports` | `network:port:*` | `OpsSelectorReadPerms` | 信息点关联端口 |
| `/ops/serverRoom/list` | `router.go` `/serverRoom` | `ops:serverroom:*` | `[ops:building:spaces:list]` | 空间角色读机房 |

## 6. 新增跨模块选择器的操作步骤 (Checklist)

当新增一个「页面 A 调用模块 B 的 list/tree 做选择器」的场景:

1. **确认是只读选择器**: 该接口是否仅用于加载下拉/树/统计数据, 不涉及增删改? 是 → 用本方案; 否(需写) → 走正常权限分配。
2. **确认放行范围**: 哪些角色需要读这个选择器? 通常是「持有任一运维读权限的角色」→ 用 `OpsSelectorReadPerms`。
3. **改路由组中间件**: 把目标路由组的 `RequirePermissions(strict, core)` 改为 `RequirePermissionsWithQuery(strict, queryExtra, core)`。
   - 若组内既有读又有写路由, 组级改 `RequirePermissionsWithQuery` 即可(写路径自动严格, 无需拆分)。
4. **PII/敏感数据评估**: 若选择器返回敏感数据(用户列表、凭据等), queryExtra 应**收窄**到真正需要的角色子集, 不要无脑用全集; 并确认是否已有 `DataScopePermission` 兜底。
5. **加回归测试**: 在 `pkg/middleware/permission_query_test.go` 的 `TestRequirePermissionsWithQuery_SelectorEndpoints` 追加子测试, 覆盖「目标角色读 = 200」「写操作 = 403」。
6. **`go build ./...` + `go test ./pkg/middleware/`** 验证。

## 7. 安全原则

- ✅ 只读路径(list/tree)可放宽, 写路径(create/update/delete/batch/geocode/import/export)永不放宽。
- ✅ 选择器返回的数据若敏感, 靠 `DataScopePermission` 或收窄 queryExtra 兜底, 不要放宽到全集。
- ✅ `OpsSelectorReadPerms` 只放运维**读**权限 (:list), 不放写权限。
- ❌ 不要直接给路由组 `RequirePermissions` 追加跨模块权限(那是 OR 逻辑, 会让该角色对整个组——含写操作——全部放行, 构成越权)。
- ❌ 不要为了"省事"把写操作也并入 queryExtra。

## 8. 测试守护

`pkg/middleware/permission_query_test.go: TestRequirePermissionsWithQuery_SelectorEndpoints` (9 子测试) 锁定行为:
- 空间角色读 部门树/用户列表/机房列表 = 200; 写操作 = 403。
- 信息点角色读 网络设备/端口列表 = 200; 写网络设备 = 403。

## 10. 相关但不同的主题

- **菜单 perms 命名对齐**: 同模块的**菜单 seed perms** 必须与**路由 RequirePermissions** 逐字符一致(单数/无连字符/delete), 否则读写全 403。详见 `.planning/debug/ops-perms-alignment.md` 与 migration_159。与本规范(跨模块选择器放行)是两个独立根因, 常被混淆。
